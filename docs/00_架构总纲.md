## 1. 产品定义

| 项 | 定义 |
|---|---|
| 产品形态 | 纯本地物体 3D 扫描建模 App，iOS + Android 双端 |
| 核心能力 | 物体级高精度重建（几何 / 拓扑 / 纹理），全参数用户可调 |
| 网络策略 | **零网络**。无服务器、无上传、无遥测、无崩溃自动上报 |
| 数据留存 | 全部落在应用沙盒目录，卸载即彻底删除 |

| 精度姿态 | 可接受分钟级重建耗时与高内存占用，**不接受任何以精度换速度的妥协** |

### 1.1 优先级铁律（贯穿所有模块的仲裁依据）

```
几何建模精准度  >  模型拓扑完整性  >  纹理质量  >  运行速度
```

**仲裁规则（工程强制）**

| 规则 ID | 内容 |
|---|---|
| R-PREC-1 | 任何参数冲突时，精度侧胜出。速度类参数不得反向约束精度类参数 |
| R-PREC-2 | 严禁引入"快速网格化""降采样预览""低模模式"作为默认路径。简化只能由用户显式触发 |
| R-PREC-3 | 关键帧只要对精度有增益即全量保留，不做自动剔除、不做自动降采样 |
| R-PREC-4 | 低端机降级只允许降低**并行度 / 批大小 / 分块策略**，**不得**降低体素分辨率、特征点数、BA 迭代数、匹配阈值 |
| R-PREC-5 | 内存保护优先使用"分块 + 落盘 + 流式"，不得通过丢弃精度数据来降内存 |
| R-PREC-6 | 所有精度相关阈值必须可被用户覆盖，且覆盖后不发生静默回退 |

### 1.2 R-PREC-4 白名单 / 黑名单（降级操作分类）

| 允许降级（白名单） | 禁止降级（黑名单） |
|---|---|
| 线程池并发数 | TSDF 体素边长 / 分辨率 |
| GPU 批次大小 / workgroup 数 | 特征点提取数量上限 |
| 大分块 → 小分块顺序 | BA 迭代次数 / LM 容差 |
| 稠密匹配的图像金字塔层（仅影响首轮粗搜） | RANSAC 迭代数、内点阈值 |
| 后处理算子的分批粒度 | 泊松重建深度 / 缩放系数 |
| 内存池预分配大小 | 关键帧保留数量 |
| — | 深度图降采样、深度图平滑替代原始深度 |

> 泊松重建深度与体素边长是几何精度的一阶因子，属黑名单。降级只能改**分块策略**，不能改深度。

## 2. 全局术语表

| 术语 | 英文 / 符号 | 定义 |
|---|---|---|
| 采集会话 | Capture Session | 一次从开启相机到确认或取消的完整过程 |
| 帧包 | Frame Packet | 一次采集单元：RGB 图像 + 可选深度图 + 时间戳 + 位姿 + IMU 采样窗口 |
| 深度源 | Depth Source | 深度数据的来源：`HW_LIDAR` / `HW_TOF` / `ALGO_DEPTH`（软件深度） |
| 深度等级 | Depth Tier | 0=无深度、1=纯运动推断软件深度、2=ToF 硬件深度、3=LiDAR 硬件深度 |
| 关键帧 | Key Frame | 通过质量门限**且**对精度有增益（由 03 文档增量判据判定）的帧。**所有**通过质量门限的帧都会被评估，不会被静默丢弃 |
| 质量门限 | Quality Gate | 单帧是否允许进入重建流程的判据（见 02 文档）。门限是**必要条件**，通过后仍需经 03 文档的增益判据决定是否为关键帧 |
| 体素 | Voxel | TSDF 融合网格单元 |
| 尺度因子 | Scale Factor `s` | 单目重建中世界单位与重建单位的比例 |
| 参照物标定 | Scale Calibration | 用已知尺寸物体求解 `s` 的过程 |
| 拓扑完备度 | Topology Completeness | 流形性 + 非流形边数 + 孔洞数 + 边界环数的综合指标 |
| 管线分支 | Pipeline Branch | `BRANCH_RGBD` 或 `BRANCH_MONO` |
| 能力探测 | Capability Probe | 启动时对设备深度/传感器能力的运行时判定 |

## 3. 分层架构

```
┌──────────────────────────────────────────────────────────────┐
│ L6  UI 层 (SwiftUI / Jetpack Compose)                       │
│     采集预览 · 状态文字 · 进度 · 参数面板 · 导出             │
├──────────────────────────────────────────────────────────────┤
│ L5  编排层 Orchestrator (C++，跨端共享)                      │
│     会话状态机 · 任务队列 · 阶段推进 · 取消/恢复             │
├──────────────────────────────────────────────────────────────┤
│ L4  重建核心 recon_core (C++17，静态库)                      │
│  ┌────────────┬────────────┬────────────┬──────────────┐    │
│  │ sync       │ vio        │ sfm        │ mvs          │    │
│  │ 时间同步   │ 紧耦合VIO  │ 稀疏SfM    │ 稠密MVS      │    │
│  ├────────────┼────────────┼────────────┼──────────────┤    │
│  │ rgbd       │ calib      │ mesh       │ postproc     │    │
│  │ RGBD-TSDF  │ 尺度标定   │ 泊松网格化 │ 修复+UV+烘焙 │    │
│  └────────────┴────────────┴────────────┴──────────────┘    │
├──────────────────────────────────────────────────────────────┤
│ L3  计算后端 compute_backend (GPU/CPU 抽象)                  │
│     Metal (iOS) · Vulkan (Android) · CPU 回退                │
│     Shader 统一用一套算法描述，两端分别编译                   │
├──────────────────────────────────────────────────────────────┤
│ L2  平台适配层 platform (C++ 接口 + 平台实现)                │
│     iOS: AVFoundation / ARKit / CoreMotion / Metal           │
│     Android: CameraX / ARCore / SensorManager / Vulkan      │
├──────────────────────────────────────────────────────────────┤
│ L1  平台运行时 (不跨端共享，仅提供系统服务)                  │
│     文件系统 · 传感器服务 · 权限 · 生命周期                 │
└──────────────────────────────────────────────────────────────┘
```

### 3.1 各层职责边界

| 层 | 允许做 | 禁止做 |
|---|---|---|
| L6 UI | 读状态、传参数、显示文字与预览 | 任何几何/图像计算；任何文件 IO 决策 |
| L5 编排 | 状态机推进、并发调度、内存水位管理 | 触碰具体算法数据结构 |
| L4 重建核心 | 全部重建算法 | 调用任何平台 API；直接访问文件系统路径语义 |
| L3 计算后端 | 数值并行、显存管理、shader 调度 | 算法决策（只执行，不判断） |
| L2 平台适配 | 相机、IMU、深度、时间戳、权限的**获取与转换** | 算法决策 |

### 3.2 跨端共享比例

| 内容 | 共享 | 说明 |
|---|---|---|
| 重建核心 L4 | 100% C++ 共享 | 单一 codebase，CMake 构建 |
| 编排 L5 | 100% C++ 共享 | — |
| 计算后端 L3 | 算法 100% 共享，着色器各端分别编译 | Metal `.metal` / Vulkan `.glsl` 两套，算法同源 |
| 平台适配 L2 | 接口 C++ 共享，实现分端 | 一份头文件 + 两份实现 |
| UI L6 | 不共享 | SwiftUI / Compose 各自实现同一套交互契约 |

### 4.2 BRANCH_RGBD（深度设备）

```
RGB 帧 + 深度帧 + IMU
        │
        ▼
┌──────────────────────────────────────┐
│ A. 深度预处理（保真，不平滑替代原始） │
│    置信度掩码 → 飞行点剔除 →          │
│    双边最小区间估计 → 对齐到 RGB      │
│    ※保留原始深度副本，不做降采样     │
└──────────────────────────────────────┘
        │                       │
        ▼                       ▼
┌────────────────┐   ┌──────────────────┐
│ B. RGBD里程计  │   │ C. 深度融合       │
│  帧对ICP+IMU   │   │  TSDF 增量融合    │
│  (尺度天然真实)│   │  全分辨率体素网格 │
└────────────────┘   └──────────────────┘
        │                       │
        └───────┬───────────────┘
                ▼
┌──────────────────────────────────────┐
│ D. 全局优化                          │
│    关键帧位姿图 + TSDF 联合精化      │
│    （尺度由深度锚定，无标定需求）     │
└──────────────────────────────────────┘
                ▼
┌──────────────────────────────────────┐
│ E. 网格化（泊松，深度 = 体素边长×8）  │
└──────────────────────────────────────┘
```

> **关键工程决策（与原始需求的一处偏差，必须知悉）**
> iOS ARKit 的 LiDAR `sceneDepth` 是为 AR 遮挡服务的**低精度**深度（厘米级、低纹理面不可靠），**不能**单独承担"真实物理尺度绝对精准"这一硬性要求。
> 因此 BRANCH_RGBD 在 iOS LiDAR 机型上强制执行**双源融合**：
> **LiDAR 深度只用于①尺度锚定 ②TSDF 几何先验 ③低纹理区补全；真实曲面精度由 RGB 多视图几何（MVS）主导，最终网格由「MVS 深度 + LiDAR 尺度约束」联合生成。**
> Android ToF 硬件深度精度高于 ARKit motion depth，可作为 TSDF 主输入，但仍保留 MVS 精化通道。
> 详见 04 文档 §2「深度源可信度分级」。

### 4.5 无深度传感器机型的一等精度路径

> **本节是全文档的立场声明，直接回应"没有激光雷达的机型也要能用、且精度优先"的产品要求。**

#### 4.5.1 两条分支不是"高精度版"与"兼容版"的关系

常见误判：有 LiDAR = 高精度，无 LiDAR = 降级兼容。**本产品明确否定该模型。**

| 维度 | 有深度传感器 | 无深度传感器 |
|---|---|---|
| **曲面细节精度** | 受限于传感器深度分辨率 | 受限于 MVS 视差精度 + 像素分辨率 |
| **典型曲面误差** | ARKit sceneDepth 厘米级；Android ToF 2–8 mm | 高质量 MVS 可达 0.2–0.5 mm（详见 05 文档 §6） |
| **绝对尺度** | 天然为米制，但**仍需复核**（见 08 约束） | **必须由参照物标定提供** |
| **弱纹理/反光区** | 深度可用，TSDF 可补 | 无深度可用，靠 MVS + 光照引导 |
| **结论** | **在曲面精度上未必更优** | **在曲面精度上可反超** |

**结论**：曲面精度的主战场在多视图几何（MVS），深度传感器提供的是"尺度锚定 + 弱纹理区覆盖"两项增益，而非"曲面精度本身"。因此无深度机型走的是**同一条精度主线的另一种尺度来源**，不构成能力分级。

#### 4.5.2 单目尺度不可观测与 IMU 尺度的真实精度

必须写清楚的三条事实（依据见 08 文档 §8.7）：

1. **单目 SfM**：尺度不可观测（7 自由度规范自由度：3 旋转 + 3 平移 + 1 尺度）。
2. **单目 VIO（紧耦合 IMU）**：在一般运动下尺度**变为可观**（加速度计提供米制参考），但在匀速/匀加速直线运动下尺度**退化不可观**。这是"VIO 尺度会漂"的根因。
3. **消费级 IMU 的尺度精度实测**：直线运动尺度误差约 **9.2%**，圆周约 **6.4%**，8 字轨迹约 **4.8%**（差速机器人 + BNO055，3 m 轨迹，同等实验条件）。

**这三条事实的工程后果（关键）**：

> IMU 提供的尺度精度（5–10%）**远不足以**满足本产品"绝对精准物理尺度"的硬性要求。
> 因此在无深度机型上，**参照物标定不是可选功能，而是精度闭环的必要组成部分**。

| 尺度来源 | 相对不确定度 | 能否单独满足"绝对精准尺度" |
|---|---|---|
| IMU/VIO 尺度先验 | 5% ~ 10% | ❌ 仅作初值与合理性校验 |
| ARCore 运动深度（ALGO_DEPTH） | 2% ~ 5% | ❌ 需参照物复核 |
| ToF 硬件深度 | 1% ~ 2% | ⚠️ 需复核 |
| ARKit LiDAR sceneDepth | 厘米级 | ❌ 仅作锚定与先验 |
| **参照物标定（07 文档）** | **0.3% ~ 0.5%** | ✅ **唯一达标来源** |

**产品决策**：无深度机型的采集流程中，**参照物标定被前置为强制步骤**（可在采集前或采集后补拍），UI 流程与有深度机型一致，不做机型区分。详见 05 文档 §7、07 文档。

#### 4.5.3 无深度机型达到一等精度的六项具体手段

| # | 手段 | 消除的精度损失 | 落地位置 |
|---|---|---|---|
| M1 | **全传感器分辨率采集**，不做 1080p 降采样 | 像素分辨率直接决定 MVS 深度精度上限 | 02 §2.5、11 §3 |
| M2 | **MSCKF 紧耦合 VIO + 预积分**，抑制轨迹漂移 | 位姿漂移 → 三角化误差 | 05 §3 |
| M3 | **SfM 位姿以 VIO 为强先验**做全局 BA | SfM 增量漂移 | 05 §4 |
| M4 | **全视角 PatchMatch MVS + 亚像素细化 + 几何/光度一致性过滤** | 曲面细节精度 | 05 §5 |
| M5 | **强制参照物标定** | 绝对尺度（5–10% → 0.3–0.5%） | 05 §7、07 |
| M6 | **弱纹理区引导补光 + 泊松置信度标注** | 无纹理区的推断区域不可控 | 05 §6.4、03 §4.5、06 §2 |

#### 4.5.4 视角覆盖的物理约束与工程解法

底部视角在手机手持条件下**物理不可达**（无法把镜头置于物体正下方仰视）。工程解法（不得假装可以）：

| 方案 | 做法 | 可达性 | 精度影响 |
|---|---|---|---|
| G1 | 手机贴近支撑面下缘，镜头**朝上**斜向拍物体底部 | 桌面/置物台场景可行 | 中（底部透视畸变大，需专门标定） |
| G2 | 物体置于软质支撑物上，可单手托起翻转至底部 | 通用可行 | 低（需引导用户翻转物体） |
| G3 | 底部由泊松外推填补，**标注为推断区** | 总是可行 | **不可控**，必须在 UI 与导出中标注 |

产品规则：**G1/G2 为首选引导路径，G3 为兜底且必须标注推断区**。UI 需明确告知用户哪些区域是推断的（见 09 文档导出页的置信度说明）。

#### 4.5.5 明确的能力边界（不夸大）

| 场景 | 有深度机型 | 无深度机型 |
|---|---|---|
| 强纹理物体（家具、鞋、玩具） | 一等 | 一等 |
| 纯色/哑光低纹理物体 | 一等（深度补全） | **受限**：需引导补光，否则底部/侧壁由泊松推断 |
| 镜面/透明材质 | **均受限**（物理限制，非工程缺陷） | **均受限** |
| 强光直射造成过曝 | 一等（可换角度） | 一等（可换角度 + 补光） |

该边界在 09 文档 UI 中以文字如实呈现，不做任何超出能力的承诺。

### 4.6 双分支精度能力矩阵（验收口径）

两条分支共用同一套验收指标，**任一分支达不到即判定为缺陷，不得以"机型差异"为由豁免**。

| 验收项 | 指标 | RGBD 分支 | MONO 分支 | 备注 |
|---|---|---|---|---|
| 相对几何误差 | 对称面重投影中位数 | ≤ 0.5 px | ≤ 0.5 px | 同一口径 |
| 尺度相对误差 | 相对参照物真值 | ≤ 1.0% | ≤ 1.0% | MONO 依赖 07 标定 |
| 尺度重复性 | 10 次独立扫描的尺度标准差 | ≤ 0.5% | ≤ 0.5% | — |
| 拓扑完整性 | 非流形边数 | 0 | 0 | — |
| 拓扑完整性 | 未闭合孔洞面积占比 | ≤ 0.05% | ≤ 0.05% | — |

### 5.2 决策表（硬编码，不允许运行时误判）

| 探测结果 | 分支 | 深度源 | 尺度来源 | 主导几何 |
|---|---|---|---|---|
| iOS + LiDAR + sceneDepth 支持 | `BRANCH_RGBD` | `HW_LIDAR`（先验） | LiDAR 锚定 + **强制参照物复核** | MVS 主导，LiDAR 补盲区 |
| iOS + 无 LiDAR | `BRANCH_MONO` | 无 | **强制参照物标定** | MVS |
| Android + ARCore 认证 + Depth API | `BRANCH_RGBD` | `ALGO_DEPTH` 或 `HW_TOF` | 深度锚定 + **强制参照物复核** | MVS + 深度融合 |

| Android + 无 ARCore 认证 | `BRANCH_MONO` | 无 | **强制参照物标定** | MVS |
| 任意机型 + 用户手动强制 | 用户指定 | 用户指定 | 用户指定 | 按分支 |

> **两条分支的尺度均须经参照物复核**：深度传感器的绝对精度同样不足以单独满足"绝对精准尺度"（见 §4.5.2 尺度来源对照表）。参照物标定在**全机型**上均为强制步骤。
> **降级不是分支**。能力探测失败（如 ARCore 未安装、相机被占用）→ 退到 `BRANCH_MONO` + 普通 CameraX 采集，**不**退回"低精度模式"。

### 5.3 降级链条（从最优到最简，全链路精度不塌陷）

```
Tier 0  最优：硬件深度 + MVS 融合 + 全分辨率 TSDF
Tier 1       硬件深度 + MVS 融合 + 分块 TSDF（内存不足时）
Tier 2       纯 MVS（深度不可用时）+ 全局 BA + 尺度标定
Tier 3       纯 MVS + 分块处理 + 延长时间
```

每一档切换只改变**内存占用方式与并发度**，不改变几何算法与精度阈值。

## 7. C ABI 跨语言边界

> **唯一边界文件：`core/include/recon/recon_c_api.h`。** 任何跨端共享逻辑必须经过此文件暴露的函数。
> Swift 与 Kotlin 侧不得直接 include 任何 `core/` 内部头文件。

### 7.1 设计原则

| 原则 | 说明 |
|---|---|
| POD-only | 跨边界只传 POD 结构体与标量，不传 `std::` 容器、不传 C++ 类 |
| 所有权明确 | 所有 `const char*` 由调用方释放；所有返回的缓冲区由 `recon_free_*` 释放 |
| 无异常跨界 | C++ 异常在边界内全部捕获并转为错误码 |
| 线程安全 | 除显式标注的 `*_thread` 函数外，句柄不可跨线程并发调用 |
| 版本号 | `RECON_ABI_VERSION` 随头文件递增，App 与 core 必须同版本 |

### 7.2 核心类型（节选，完整见 01 文档）

```c
typedef struct recon_frame_packet {
    uint64_t          frame_id;
    uint64_t          timestamp_ns;      // 单调时钟，与 IMU 同源
    uint32_t          rgb_width, rgb_height;
    uint32_t          depth_width, depth_height;
    uint32_t          has_depth;
```

## 8. 真实技术约束披露（工程诚实性声明）

> 以下 8 条是经核实的**客观限制**，不是设计选择。每条都给出已落地的应对方案。撰写任何对外文档时不得省略此节。

> **诚实性补充（2026-10-31）**：本节原写「以下 6 条」，但实际列有 8.1–8.5、8.7–8.9 共 8 条（`8.6` 编号被跳过、内容缺失）。已更正为 8 条并补齐 `8.6`。同时 `8.4` 原只披露 CGAL 一个传染点，经 `10_许可与合规.md` §5.2 逐模块核对后**远不止 CGAL**，已按实际风险面重写。**整改原则：宁可暴露更多真实约束，不用「只有一条」的措辞把风险说小。**

### 8.1 ARKit LiDAR 深度 ≠ 高精度测距

- **事实**：ARKit 的 `sceneDepth` / `smoothedSceneDepth` 是为 AR 遮挡服务的，LiDAR 精度为厘米级；无纹理/低反射表面不可靠。ARKit 的 `ARMeshAnchor` 网格面向实时环境理解，**不适合**直接作为物体扫描产物。
- **应对**：见 §4.2 关键工程决策。LiDAR 深度降级为"尺度锚定 + 先验 + 补盲"，主几何由 MVS 承担。

### 8.2 ARCore Depth API 精度随距离与纹理变化

- **事实**：Google 文档明确说明运动深度在 0.5–5 m 区间最准，0–65 m 范围内"可靠但精度下降"；低纹理表面深度不精确；有效深度需设备产生位移后才可用；深度值沿**光轴**投影而非沿视线射线。
- **应对**：深度层级 `Depth Tier` 显式区分 `ALGO_DEPTH` 与 `HW_TOF`；`ALGO_DEPTH` 深度不得单独作为尺度真值，必须由参照物复核；TSDF 融合时对低置信区域降权但不丢弃（保精度，不做伪平滑）。

### 8.3 稠密重建精度上限由 MVS 决定，不由 TSDF 决定

- **事实**：单目/ToF 的物体级曲面精度由多视图几何的深度分辨率与视差精度决定。TSDF 网格再细也无法凭空产生几何。
- **应对**：两条分支都保留 MVS 通道；RGBD 分支中 TSDF 负责融合与去噪，几何精度由 MVS 深度贡献。

### 8.4 COLMAP 的传递依赖链是**最高风险点**（不止 CGAL 一个传染点）

- **事实（上游默认配置）**：COLMAP 3.10 自身是 new BSD，但其顶层 `CMakeLists.txt` 的默认值是
  `CGAL_ENABLED=ON`、`ONNX_ENABLED=ON`、`GUI_ENABLED=ON`（Qt）、`CUDA_ENABLED=ON`、
  **`LSD_ENABLED=ON`**，且 `src/thirdparty/CMakeLists.txt` 会**无条件**
  `add_subdirectory(PoissonRecon)`。
- **事实（保留子树对依赖不封闭）**：COLMAP 保留子树（`{feature,estimators,sfm,util,geometry,sensor,math,scene}`）的
  `PUBLIC/PRIVATE_LINK_LIBS` **对依赖不封闭**。经逐模块核对 3.10，强制引入下列组件：

  | 组件 | 因何引入 | 许可 | 判定 |
  |---|---|---|---|
  | **CGAL** | `CGAL_ENABLED` 默认 **ON** | GPL / 商业双许可 | ❌ 传染 |
  | **FreeImage** | `colmap_sensor/bitmap.cc` 直接 `#include <FreeImage.h>`；`sensor` 被 `feature`/`estimators`/`scene`/`sfm` 传递依赖 | **FIPL-1.0 / GPL-2.0 / GPL-3.0 双许可** | ❌ 传染（走 GPL 分支）或不可控（FIPL §6.1 允许作者改版） |
  | **LSD** | `src/thirdparty/LSD`，`LSD_ENABLED` 默认 **ON** | **AGPL-3+** | ❌ 传染 |
  | **SiftGPU** | `GPU_ENABLED = OPENGL_ENABLED OR CUDA_ENABLED` 时编译 | **UNC Chapel Hill 非商业许可**（原文限定 "educational, research and non-profit purposes"） | ❌ 不可商用 |
  | Qt（GUI） | `GUI_ENABLED` 默认 **ON** | LGPLv3 / 商业双许可 | ⚠️ 静态链接义务复杂化，须关 |
  | ONNX Runtime | `ONNX_ENABLED` 默认 **ON** | MIT，但引入二进制下载 | ❌ 违反 B-2 / B-3（零网络） |
  | SQLite3 / Boost / glog / METIS / lz4 / VLFeat / FLANN | `scene`/`math`/`util`/`retrieval` 传递 | Public Domain / BSL-1.0 / BSD-3 / Apache-2.0 / BSD-2 / BSD-2 / BSD-3 | ✅ 可接受（登记进白名单扩展，10 §5.3） |

  > 上游自身的 `COPYING.txt` 已声明「使用内含依赖构建可能改变产物的许可」，Debian 的
  > colmap 3.10-2 copyright 文件亦逐目录列出上述非 BSD 子树。**因此「COLMAP 是 BSD-3」
  > 这一说法只在裁剪后才成立，裁不掉就是传染。**

- **应对（三条硬性排除，缺一即不合规）**：

  | 编号 | 要求 | 关键动作 |
  |---|---|---|
  | **X-1** | 排除 `src/colmap/sensor/bitmap.{h,cc}`，切断 FreeImage | **单文件**排除，**不排除整个 `sensor/` 目录**——`estimators` 经 PUBLIC 依赖 `colmap_sensor` 的 `camera_models.h`，整目录排除会破坏编译。图像读写改由 OpenCV `imgcodecs`（Apache-2.0）承担（`core/util/image_io.cpp`），COLMAP 的 `Bitmap`（EXIF 等）本项目不使用 → 替换成本为零 |
  | **X-2** | `LSD_ENABLED=OFF`，且 `src/thirdparty/LSD` **不得 vendor** | 本项目不需要线段检测（05 特征提取用 Shi-Tomasi） |
  | **X-3** | `OPENGL_ENABLED=OFF` **且** `CUDA_ENABLED=OFF`（OpenGL 是 SiftGPU 的编译前置）；`src/thirdparty/` **整棵子树不得 vendor** | `src/thirdparty/` 内含 LSD（AGPL）与与白名单 #6 重复的 PoissonRecon |

- **构建期显式开关（逐字使用，不得增删）**：
  `-DCGAL_ENABLED=OFF -DGUI_ENABLED=OFF -DONNX_ENABLED=OFF -DCUDA_ENABLED=OFF
  -DOPENGL_ENABLED=OFF -DLSD_ENABLED=OFF -DMVS_ENABLED=ON
  -DFETCH_FAISS=OFF -DFETCH_POSELIB=OFF -DFETCH_ONNX=OFF -DTESTS_ENABLED=OFF`

- **本产品自身的分工**：采用**自研 MVS 稠密模块**（Metal / Vulkan 后端，05 §5.9），
  COLMAP 仅取其稀疏 SfM 与几何验证能力（05 §4.1.2「复用 COLMAP 稀疏模块作为几何原语层，
  自研求解层与调度层」）。

- **CI 强制校验（不是口头承诺，是构建期事实）**：
  1. `tools/license_scan.py` 阶段 4 用 `nm -C --defined-only` 扫描产物，

  2. `third_party/colmap/` 下**不得存在** `src/thirdparty/` 与 `src/colmap/sensor/bitmap.{h,cc}`；
  3. 「四表一致」（`--check-registry`）：`cmake/ThirdParty.cmake` ↔ `docs/10 §2.1` ↔

  `FORBIDDEN_ARTIFACT_SYMBOLS`）；但 COLMAP **尚未 vendor**（`third_party/colmap/` 目录不存在），
  故这些约束**当前无法在真实树上验证**。vendor 时必须逐条走查。

### 8.5 Eigen 是 MPL-2.0，不属于用户指定的 MIT/Apache/BSD 三类

- **事实**：Ceres Solver（BSD）硬依赖 Eigen；Eigen 自 3.3 起为 MPL-2.0（文件级 copyleft，非传染型，商用可行，但**不在**用户白名单内）。此外，Eigen 的**稀疏 Cholesky**（`src/Cholesky`，`EIGEN_SPARSE` 路径）为 **LGPL-3.0**，与 Eigen 主体的 MPL-2.0 **不同** —— 若不规避，会从「边界项」升级为「传染」。
- **应对**：Eigen 单列为「白名单边界项 **B-1**」，需法务签字。四条处置同时成立才算合规：
  (B1-1) 静态吸收进上层（纯头文件，无导出符号表）；(B1-2) **不修改源文件**（`modified: false` + `vendored_sha256` 锁定）；
  (B1-3) 保留 `COPYING.MPL2` + `COPYING.README` **全文**并嵌入 `THIRD_PARTY_LICENSES.txt`；
  (B1-4) 法务签字记录于 10 文档 §4。
  稀疏求解**不得**走 `EIGEN_SPARSE` / `CX_SPARSE` 路径，只允许 Ceres 内置的 CHOLMOD 子集（Apache-2.0），
  且要求产物中无 `cholmod_supernodal` 符号（10 §5.4）。
  备选方案（自研稀疏线性代数 + 自研 BA）工作量 ≥ 12 人日且精度回归风险显著更高，**不推荐**。见 10 文档 §5.4。

### 8.6 移动端持续扫描的**热与电**约束（决定降级策略的取舍）

- **事实**：连续扫描是**长时满负荷**负载（相机双流 + 特征/VIO + TSDF/MVS + 泊松）。手机上持续数分钟即会升温，
  iOS `ProcessInfo.thermalState` 与 Android `PowerManager.getThermalHeadroom()` 会触发系统降频；
  极端情况下 iOS 会热关机（thermal shutdown）直接杀进程。
- **事实**：**降并行度 ≠ 降精度**，但**降精度省不了多少电反而更慢**。泊松在 GPU 上 60–150 s，CPU 回退 40–90 min
  —— 关掉 GPU 会让发热时间与总耗电**同步恶化**（13 §5.2）。
- **应对（三条，全部已落为可执行规格）**：
  1. **只降并行度/分块，不降精度参数**（硬规则 R-PREC-4 / 13 §5.2 TH-1）：温度降级只允许改
     `perf_thread_pool_size`、`perf_gpu_batch_size`、`perf_max_concurrent_tasks`、`rgbd_max_blocks_in_memory`；
     **绝不**改 `rgbd_tsdf_voxel_size`、`mesh_poisson_depth`、`sfm_feature_count`、`vio_feature_count`、
     `mvs_patch_size`、`mvs_num_views`、`mvs_image_scale` 等精度参数。
  2. **温度降级是临时的**：回落即恢复并发度，迟滞 60 s（TH-2，与内存降级 R-1 同口径）；
     每次降级写入 `recon_mesh_info.json` 的 `degradations`（`reason = "thermal_throttle"` / `"thermal_critical"`）并在 UI 显示提示行（TH-3）。
  3. **`critical` 时暂停采集**而非降分辨率（`Capturing` → `Previewing`，已采帧保留）；采集期帧率由用户在参数面板
     显式设定区间，**不由温度自动改写**（TH-5）。
- **诚实标注**：热/电的**具体阈值与实测曲线**（不同机型升到 `serious` 的耗时）**尚未实测**——
  需真机长时间扫描数据支撑。当前只固化了**策略与参数口径**，数值调优留待移动端联调阶段。
  在此之前，不得宣称「热管理已达标」。

### 8.7 消费级 IMU 的尺度精度实测（决定参照物标定的强制性）

- **事实**：单目 VIO 在一般运动下尺度可观，但在匀速/匀加速直线运动下尺度退化不可观测，这是"VIO 尺度会漂"的根因。实测数据（差速机器人 + 单目相机 + BNO055 消费级 IMU，同等 3 m 轨迹条件）：**直线运动尺度误差 9.2%，圆周运动 6.4%，8 字运动 4.8%**，激励量跨越四个数量级。
- **结论**：消费级 IMU 的尺度精度在 **5% ~ 10%** 量级。
- **工程后果**：IMU 尺度**只能**用作初值与合理性校验，**不能**作为最终尺度来源。参照物标定（07 文档）是达到 0.3% ~ 0.5% 尺度精度的**唯一**途径，在无深度机型上是强制步骤而非可选功能。详见 §4.5.2。

### 8.8 高精度 MVS 的曲面精度可反超深度传感器

- **事实**：ARKit `sceneDepth` 面向 AR 遮挡，精度为厘米级；Android ToF 硬件深度典型精度 2–8 mm。而多视图几何的深度误差约为 `δZ ∝ Z²/(f·B) · δd`，在手机典型参数（f ≈ 2500 px、基线 B ≈ 80–150 mm、Z ≈ 0.3–0.5 m、亚像素视差精度 δd ≈ 0.1–0.2 px）下可达 **0.2–0.5 mm** 量级。
- **结论**：**曲面精度的主战场在 MVS，不在深度传感器**。深度传感器的价值是尺度锚定与弱纹理区覆盖，不是曲面精度本身。
- **工程后果**：两条分支共用同一套 MVS 主线与同一套精度验收口径（§4.6），无深度机型不作能力分级。详见 §4.5.1。

### 8.9 商业许可与"零网络"的自相矛盾点

- **事实**：App Store / Google Play 上架需要声明隐私清单与数据收集情况；部分系统服务（如 Google Play Services for AR）本身可能尝试联网。
- **应对**：`AndroidManifest.xml` **不声明** `INTERNET` 权限（系统级服务不受此限），iOS 不申请任何网络能力；隐私清单声明"不收集数据、不用于追踪"；详见 11 文档。
