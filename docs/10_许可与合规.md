## 1. 合规目标与判定标准

### 1.1 合规目标（四条，逐条可判定）

| 编号 | 目标 | 判定口径 |
|---|---|---|
| G-1 | **闭源商业分发** | App 二进制中不含任何要求使用者公开自身源代码的代码；App 源码不因任何依赖而被迫开源 |
| G-2 | **零版权风险** | 全部第三方代码的许可条款均已被完整满足（保留声明、附许可全文、履行 NOTICE 义务），且不存在需要单独商业授权才能使用的组件 |
| G-3 | **仅 MIT / Apache-2.0 / BSD 系** | 白名单内的每个组件，其 SPDX 标识必须落在 §1.2 白名单类型集合内；不在集合内的，只有 §4 的边界项 B-1（Eigen / MPL-2.0）一个，且已履行四条处置与法务签字 |
| G-4 | **彻底规避 GPL / AGPL** | 产物中不存在任何 GPL / AGPL 组件的代码或链接依赖；不依赖「动态链接」「进程隔离」「仅调用 API」等不确定的技术规避手段 |

### 1.3 判定结论的效力

| 项 | 规定 |
|---|---|
| 判定层级 | 本文 §2 白名单 > §5 传递依赖许可面 > §3 黑名单 > §4 边界项专项处置 |
| 冲突裁决 | 同一组件同时出现在白名单与黑名单时，以黑名单为准（黑名单是「不可接受」的一票否决） |
| 新增依赖的流程 | ① 在本文 §2 增行并给出法律依据 → ② 法务确认（白名单扩展项必须签字）→ ③ 在 12 文档 §2.1 登记版本 → ④ 在 `cmake/ThirdParty.cmake` 登记 → ⑤ 在 `cmake/Licenses.cmake` 加入清单 → ⑥ 扫描器通过 → ⑦ 合并。顺序不可颠倒（12 文档 §2.8） |
| 升级依赖的流程 | 12 文档 §2.8 第 6 步：**许可发生变化即停止发布**，回到本文重新判定并重新签字 |
| 拒绝记录 | 本文 §3 的每条黑名单必须写明「排除理由 + 替代方案」，禁止只写「不用」 |

## 4. 边界项 B-1：Eigen (MPL-2.0)

### 4.1 事实认定

| 项 | 事实 | 来源 |
|---|---|---|
| 上游与版本 | `libeigen/eigen`，tag `3.4.0` | 12 文档 §2.1 #2 |
| 许可 | **MPL-2.0**（Mozilla Public License 2.0），自 Eigen 3.3 起 | 上游 `COPYING.MPL2` |
| copyleft 性质 | **文件级 copyleft**（file-level copyleft），**非传染型**。与 GPL 的「整个组合作品传染」不同 | MPL-2.0 §1.10 定义 Larger Work |
| 白名单关系 | **严格说不在**用户指定的 MIT / Apache-2.0 / BSD 三类内 | 00 §8.5 |
| 不可回避性 | Ceres Solver（BSD-3-Clause）的硬依赖；PoseLib 亦依赖 Eigen | 上游 `CMakeLists.txt` / `FindDependencies.cmake` |
| 传递深度 | Eigen → Ceres → COLMAP `colmap_estimators` / `colmap_scene` / `colmap_math` / `colmap_optim` / `colmap_geometry` / `colmap_util` / `colmap_feature_types`；Eigen → PoseLib → COLMAP `colmap_estimators` | COLMAP 3.10 各模块 `PUBLIC_LINK_LIBS` / `PRIVATE_LINK_LIBS` |

### 4.2 法律分析

| 问题 | 分析 | 结论 |
|---|---|---|
| MPL-2.0 的 copyleft 作用于什么范围 | 仅作用于**被修改的 MPL 文件本身**。MPL-2.0 §3.3 规定：若你修改了某个 MPL 文件，该**修改后的文件**必须以 MPL-2.0 发布；其余文件不受影响 | 本项目**不修改** Eigen 任何文件 → 该条款**不触发**，无需公开任何自有源码 |
| 静态链接组合是否传染 | 不传染。Eigen 是**纯头文件库**（无 `.cpp`、无导出符号表），其模板实例化被编译进调用方的目标文件，产物中不残留 Eigen 的独立模块边界。MPL-2.0 §1.10 明确：把 Covered Code 与不受其条款约束的代码组合成 Larger Work 是**允许**的 | 静态链接进入 `.a` / `.so` / App 可执行文件**不产生传染** |
| 「文件级」在纯头文件库场景下的实际含义 | Eigen 的每个头文件都是独立 MPL 文件。若对其做了本地补丁，义务仅落在被补丁的那个头文件上，会引入「必须提供该头文件源码」的单点义务 | 因此 B1-2「不修改源文件」是**消除该单点义务的唯一手段**，不是形式要求 |
| 专利授权条款的影响 | MPL-2.0 §2.1 附「Initial Developer Grant」含专利授权与专利报复条款；§2.2 的 Contributor Grant 不含专利授权 | 保留完整 `COPYING.MPL2` 全文即自动获得 §2.1 的授权；不修改文件即不产生新的 Contributor 义务 |
| Apache-2.0 兼容性 | MPL-2.0 §3.3 允许 MPL 文件与 Apache-2.0 等条款文件组合 | 本项目自有代码为闭源专有，不影响组合的合法性 |

### 4.4 备选方案评估：自研稀疏线性代数替代 Eigen

**结论：不推荐。量化理由如下。**

自研需完整覆盖 Eigen 提供的、被本项目实际使用的算子集合：

| 需自研的算子族 | 具体需求 | 难度 |
|---|---|---|
| 稠密线性代数 | Cholesky / LDLᵀ（BA 中的正规方程）、QR、LU、特征分解（部分位姿求解）、矩阵逆与条件数估计 | 中 |
| 几何模块 | `Quaternion` / `AngleAxis` / `Isometry3` / `SE3` 的旋转表示与插值、`Transform` 链式求值、投影与反投影 | 高（数值稳定性是主要陷阱：四元数归一化、旋转矩阵的正交化、角度归一化到 (−π, π]） |
| 稀疏线性代数 | `SparseMatrix` 的 CSR/CSC 存储、稀疏 Cholesky（**注意：Eigen 的稀疏 Cholesky 模块是 LGPL-3.0，自研可回避此问题**）、稀疏 LU | 极高 |
| 模板化 SIMD 路径 | Eigen 的向量化路径与自动微分友好性；Ceres 的 `Jet` 类型与 Eigen 的 `Scalar` 模板机制深度耦合 | 极高 |
| 数值特性 | 条件数估计、`NumTraits` 特化、`AutoDiffScalar` 模板 | 高 |

**量化成本与风险**

| 维度 | 量化结论 |
|---|---|
| 实施工作量 | **≥ 12 人日**（12 文档 §2.5 已给出的量级），且为**乐观下界**：真实成本包含「重做 Ceres 的 `Jet` 自动微分对接」与「重标定 05 §4.7 全部求解器配置」两块，均不可压缩 |
| 精度风险来源 1 | Ceres 的 LM 阻尼与 `CostFunction` 模板全部实例化在 `double` 上；换掉线性代数后端后，**Cholesky 的 pivoting 策略、秩判定阈值、条件数阈值**全部改变。这些直接决定 BA 是否收敛、以及收敛到哪个解 |
| 精度风险来源 2 | 05 §4.8 的收敛容差按 **1e-8** 比较（12 文档 FP-3 已承认 Eigen 向量化在不同 CPU 上有末位差异）。换后端后末位差异量级不可预测，**必须重跑全部黄金回归**并重新标定容差 |
| 精度风险来源 3 | 精度指标的传导链是：BA 残差分布 → 三角化精度 → **尺度标定结果**（07 文档）→ 00 §4.6 的「尺度相对误差 ≤ 1.0%」「尺度重复性 ≤ 0.5%」两项硬指标。BA 数值行为的任何不可控变化都会直接冲击这两项 |
| 性能风险 | 自研稀疏 Cholesky 在移动端 ARM 上很难达到 Eigen + Ceres 内置 CHOLMOD 的性能；可能触发 13 文档的内存与耗时基线超差（+30% / −25% 容差） |
| 合规收益 | 只把「一个已签字的、文件级非传染的边界项」换成「自研代码的正确性风险」。**G-1/G-2/G-4 均不因 Eigen 而受损** → 合规收益为零 |
| 净结论 | **成本与风险极高，合规收益为零。不推荐。走 B-1，需法务签字。** |

### 5.2 COLMAP 的传递链（**最高风险点**）

12 文档 §2.4 记录的 COLMAP 保留子树为 `src/colmap/{feature,estimators,sfm,util,geometry}`。经逐模块核对 COLMAP 3.10 的 `PUBLIC_LINK_LIBS` / `PRIVATE_LINK_LIBS`，**该集合对依赖不封闭**，实际强制引入下列组件：

| 被强制引入的模块 | 因何被引入 | 其自身再引入 | 该组件的许可 | 判定 |
|---|---|---|---|---|
| `colmap_sensor` | `colmap_feature`（PRIVATE）、`colmap_estimators`（PUBLIC）、`colmap_scene`（PUBLIC）、`colmap_sfm`（PRIVATE，`incremental_mapper.cc` 直接 `#include "colmap/sensor/bitmap.h"`） | **`FreeImage`**（`bitmap.cc` 直接 `#include <FreeImage.h>`）、`colmap_vlfeat` | **FIPL-1.0 / GPL-2.0 / GPL-3.0 双许可** | ❌ **必须排除 FreeImage**（见下方处置） |
| `colmap_scene` | `colmap_feature`、`colmap_estimators`、`colmap_sfm`（PUBLIC） | `SQLite3`、`colmap_sensor` | SQLite3 = Public Domain；其余同上 | ⚠️ SQLite3 可接受（登记） |

### 6.2 选型结论（明确）

| 档位（05 §4.2.2） | 采用描述子 | 算法许可 | 专利结论 | 说明 |
|---|---|---|---|---|
| **快** | **ORB（256 bit）** | OpenCV 实现，Apache-2.0 | ✅ 无有效专利 | 匹配耗时是 SIFT 的约 1/11；ORB 论文本身以「无 SIFT/SURF 许可限制」为卖点。代价（弱纹理区分度下降）由 `sfm_match_ratio_threshold` 收紧至 0.90 补偿（08 G4） |
| **标** | **SIFT + rootSIFT（uint8 128）** | OpenCV 实现，Apache-2.0 | ✅ 可用（US 专利 2020-03-06 已到期） | rootSIFT 把 L2 距离转成余弦相似度，匹配质量优于裸 SIFT；uint8 存储使描述子内存降到 1/4，使分块加载可行 |
| **高** | **SIFT + rootSIFT（uint8 128）+ 特征数 20000** | 同上 | ✅ 可用 | 与标准档同描述子，靠**特征数**与 BA 迭代提升精度，不换描述子（换描述子会同时改变匹配统计特性，需重新标定全部阈值） |

### 6.3 深度特征（ALIKED / LoMa）的许可与体积影响（记录在案，v1 不采用）

| 维度 | 事实 | 影响 |
|---|---|---|
| **许可面** | ALIKED 代码与权重 = BSD-3-Clause；LightGlue / LoMa 代码与权重 = Apache-2.0。两者都在许可上可接受 | 但 ALIKED / LoMa 位于 COLMAP 的 `ONNX_ENABLED` 分支，而 **COLMAP 3.10 无 ONNX 支持**（3.10 无 `ONNX_ENABLED` 选项），需升级到 COLMAP 4.x 才能使用 → 触发一次完整的依赖升级与重新评估（§1.3 流程） |
| **ONNX Runtime 的许可** | **MIT**（`microsoft/onnxruntime`），许可本身无障碍 | 但 ONNX Runtime 携带 `ThirdPartyNotices.txt`，必须进许可聚合（§5.5） |
| **ONNX Runtime 的遥测** | 上游 README 明确：「Windows distributions of this project **may collect usage data** and send it to Microsoft」 | ⚠️ **与零网络策略（00 §8.9、11 §1.6）直接冲突**。若未来引入，必须使用源码构建并显式关闭遥测，且 CI 需新增 ONNX Runtime 的符号级网络检查。**这是不采用深度特征的首要工程理由** |
| **体积影响** | ONNX Runtime 移动端运行时 + ALIKED / LoMa 权重合计需按 **数十 MB 量级**估算；12 文档 §3.7 的包体积预算为单设备下载 34–50 MB | 引入后单设备下载体积将逼近或超出预算上限（+10% 容差）。**与 12 文档 §3.7 的体积门禁冲突** |
| **收益** | 深度特征在弱纹理 / 大视角变化下的匹配率优于 SIFT / ORB | 但本产品的弱纹理问题已由「侧向补光引导 + 泊松置信度标注 + 推断区标注」（00 §4.5.3 M6、05 §6.4）解决，不依赖深度特征；且 00 §4.5.1 的立场是「曲面精度主战场在 MVS 而非特征前端」 |
| **结论** | **v1 不采用。** 触发条件（三者同时满足才立项）：① 弱纹理物体场景下的匹配召回率经实测成为**精度验收的失败项**（14 文档）；② ONNX Runtime 可在关闭遥测的前提下源码内联；③ 包体积预算重新评估通过 | |

## 9. 第三方声明模板

### 9.1 页面结构（「关于 → 开源许可」，09 文档新增 U-11）

```
U-11 开源许可
├── 标题栏（返回按钮；无 Tab 栏）
├── 顶部说明区（静态文字，3 行）
│   「本 App 使用以下开源软件。全部许可文本完整列于下方。」
│   「本 App 不收集任何数据、不进行追踪、不含广告与统计组件。」
│   「完整许可文件：THIRD_PARTY_LICENSES.txt（随 App 一同分发）」
├── 分组一：随 App 分发的开源组件
│   └── 条目列表（可滚动，按 §9.3 的顺序）
│       └── 每条目 → 展开/进入详情页显示该组件的许可全文
├── 分组二：第三方平台组件（非开源，受各自 SDK 条款约束）
│   └── 条目列表（组件名 / 供应商 / 版本 / 条款 URL 静态文本）
├── 分组三：本项目自有许可声明
│   └── 「本 App 的源代码为专有许可。第三方组件的许可不影响本 App 的许可。」
└── 底部：本项目许可与版权（Copyright 行 + 保留所有权利声明）
```

### 9.2 展示格式规则

| 编号 | 规则 |
|---|---|
| D-1 | 许可全文**必须可完整查看**：不可折叠到「展开更多」按钮之后、不可只显示摘要、不可只给外链。允许「列表页显示摘要 + 详情页显示全文」的两级结构，但详情页必须能一屏内滚动看完 |
| D-2 | 许可文本**保持原始英文**，不翻译、不改写、不重新排版（改排版会改变条款的呈现义务）。中文界面下用中文说明文字解释每条组件的用途，许可原文附在其后 |
| D-3 | 每条目必须显示的 6 个字段：**组件名 · 版本/标签 · 精确许可标识 · 上游 URL · 本项目用途 · 是否有修改** |
| D-4 | 「是否有修改」为「是」时，必须在条目内直接写出修改内容摘要（Apache-2.0 §4(b) 的显著声明义务）。OpenCV 的表述固定为：「本项目裁剪了 OpenCV 的模块集合（保留 core / imgproc / imgcodecs / features2d / calib3d / flann / photo，highgui 仅桌面构建启用），未修改保留模块的源文件」 |
| D-5 | 许可全文以**预生成的单文件**（`THIRD_PARTY_LICENSES.txt`）嵌入 App 资源，运行时直接读取展示，**不依赖任何网络请求** |
| D-6 | 条目顺序固定：与 `cmake/ThirdParty.cmake` 的登记顺序一致；依赖内部按文件名字典序（与 12 §2.7 的生成顺序一致，保证「页面所见」与「生成文件」逐字节对应） |
| D-7 | 平台组件分组（分组二）的条目**不进**「开源许可」文件，放在「第三方平台组件」小节，各自注明条款 URL 的静态文本 |
| D-8 | 界面必须支持 20 个 locale（09 §6.1）；许可原文不随 locale 切换，中文 locale 下在原文上方增加中文用途说明 |
| D-9 | 页面不得出现任何营销文案、不得出现「我们使用了业界领先的开源框架」之类表述。许可页面是合规展示，不是产品宣传位 |
