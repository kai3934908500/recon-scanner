**明确不申请的项及理由**

| 键 | 结论 | 理由 |
|---|---|---|
| `NSMicrophoneUsageDescription` | **不申请** | 本产品**不录音**：`AVCaptureSession` 只添加 `AVCaptureDeviceInput(device: .builtInWideAngleCamera)` 音频轨，代码中不出现 `AVCaptureDevice` 的 `builtInMicrophone`、`AVAudioSession`、`AVAudioRecorder`、`AVCaptureMovieFileOutput`、任何 `AudioToolbox` 录音 API；不实现视频录制。**因此不需要写入该键**。若后续引入任何音频采集，必须先在本文新增该键并补充用途文案，且属于需求变更 |
| `NSPhotoLibraryUsageDescription` | **不申请** | 只使用 `PHPhotoLibrary.performChanges` + `PHAssetCreationRequest` 写入，属「添加」权限。对应键为 `NSPhotoLibraryAddUsageDescription`。读取相册需要 `PHAsset` 枚举，本产品不枚举任何相册资源 |
| `NSLocalNetworkUsageDescription` | **不申请** | 零网络（00 §1）。不存在 Bonjour、`NWBrowser`、`NetService`、`MultipeerConnectivity`、本地 TCP/UDP socket |
| `NSUserTrackingUsageDescription` | **不申请** | 不使用 IDFA、不做归因、不跨 App 追踪；隐私清单 `NSPrivacyTracking = false` |

### 1.3 权限申请时序

```
App 启动
  └─→ U-01 首页
        └─ 用户点「开始扫描」
              ├─→ 能力探测（U-02）         ← 不需要任何权限
              └─→ RequestingPermission
                    ├─ AVCaptureDevice.authorizationStatus(for: .video)
                    │     .notDetermined  → requestAccess → 决定分支
                    │     .denied         → 提示「没有相机权限，无法扫描」+「去设置」
                    │     .restricted     → 提示「此设备限制了相机使用」+「去设置」
                    │     .authorized     → 继续
                    ├─ PHPhotoLibrary.authorizationStatus(for: .addOnly)
                    │     仅在用户点「导出到相册」时检查，不在采集流程中申请
                    └─ CoreMotion：不申请授权，直接启动 deviceMotion/gyro 更新
```

| 编号 | 规则 |
|---|---|
| IOS-P-1 | 权限只在**用户触发相关功能时**申请，不在启动时申请 |
| IOS-P-2 | 相机权限被拒时，不自动反复申请；提示行内含「去设置」按钮，跳 `UIApplication.openSettingsURLString` |
| IOS-P-3 | 权限相关的用户可见文案取自 09 文档 §5.7，不得改写 |
| IOS-P-4 | 拒绝权限**不改变**管线分支（除相机被拒外）。运动权限在 iOS 侧不存在被拒场景 |

**原因码逐条对应**

| API 类别 | 原因码 | 本产品用途 | 触发点 |
|---|---|---|---|
| `NSPrivacyAccessedAPICategoryFileTimestamp` | `C617.1` | 读取 `sessions/<id>/manifest.json`、`index.bin` 的修改时间，用于：① 会话过期清理；② 02 §5.9 的落盘完整性校验（比对 `index.bin` 的时间戳与 `frames.bin` 尾部记录）；③ 恢复被系统杀进程的会话时判断数据是否可续算 | 会话开始/结束、App 启动扫描、冷启动恢复 |
| `NSPrivacyAccessedAPICategoryUserDefaults` | `CA92.1` | 读写本机 UI 偏好：界面语言（09 §6.1）、主题（跟随系统/浅色/深色）、专家模式开关、参数预设覆盖 `overrides`（08 §3.4）。**全部只在本机**，不写入 `NSUbiquitousKeyValueStore`（iCloud） | 启动读写、用户修改时写回 |
| `NSPrivacyAccessedAPICategoryDiskSpace` | `E174.1`、`85F4.1` | `E174.1`：在 U-10 导出界面显示「可用空间 3.2 GB」。`85F4.1`：采集开始前校验 `可用空间 ≥ 预估总量 × 1.5`（02 §5.6.5 DS-3），不足则拒绝开始；导出前校验可用空间 ≥ 预估大小 × 1.2 | U-10 显示、采集开始前、导出前 |
| `NSPrivacyAccessedAPICategorySystemBootTime` | `35F9.1` | 读取 `mach_absolute_time` / `sysctl KERN_BOOTTIME`，确定 session 时间轴原点（02 §3.3 的 `β_c` 求解起点）与 IMU 预积分的时间基准 | 采集会话开始时一次 |

> **诚实披露**：`NSPrivacyAccessedAPICategorySystemBootTime` 是本清单中**唯一有争议**的一项——它之所以被使用，仅因为 02 §3.6 的相机–IMU 联合对齐需要把 `CMSampleBuffer.presentationTimeStamp`（mach 时间基）与 `CMDeviceMotion.timestamp`（同为 mach 时间基但存在 `τ_cm` 融合滞后）归一到同一 session 原点。若后续实测证明两者的差值可用固定常数标定（02 §3.9.4 的 `τ_cm` 标定表），仍需 mach 绝对时间作为原点，因此**不能移除**。CI 需固定该声明，防止有人误删导致上架被拒。

### 1.6 零网络证明

#### 1.6.1 声明

| 项 | 值 |

| 出站连接 | 无（TCP / UDP / QUIC / WebSocket / DNS 全部无） |

#### 1.6.2 四条证明链

**证明链 A — ATS 无例外，TLS 能力也不使用**

```xml
<!-- Info.plist 中不存在 NSAppTransportSecurity 键 -->
```

| 检查项 | 判定 |
|---|---|
| `NSAppTransportSecurity` 键 | **整个键不写入** Info.plist（而不是写入后置 `NSAllowsArbitraryLoads = false`）。理由：键一旦存在就必须显式列出所有子键，缺一个即为配置错误；不写该键等价于使用系统默认的严格 ATS，且没有可被误改的例外位 |
| `NSExceptionDomains` | 不存在 |
| `NSAllowsArbitraryLoads` / `NSAllowsLocalNetworking` | 不存在 |

**证明链 B — 源码层无网络 API**

CI 脚本 `tools/network_audit.py`（新增，12 文档的 CI 一节挂接）扫描 `core/`、`platform/`、`ui/` 三棵源码树的全部 `.c/.cpp/.h/.mm/.m/.swift/.kt/.java`，命中下表任一符号即失败：

| 语言 | 禁止符号 |
|---|---|
| Swift/ObjC | `URLSession`（含 `URLSession.shared` / `URLSessionConfiguration`）、`URLRequest`、`URL(string:`、`NSURLConnection`、`CFNetwork`、`CFStream`、`NWConnection`、`nw_connection`、`Network.` 框架、`NetService`、`Bonjour`、`GCDAsyncSocket`、`Socket(`、`CFHost`、`getaddrinfo`、`gethostbyname`、`res_` |
| Kotlin/Java | `java.net.URL`、`HttpURLConnection`、`OkHttp`、`Retrofit`、`Socket(`、`DatagramSocket`、`InetAddress`、`WebView`（`WebView` 本身即视为违规，因为它可加载远程内容）、`android.webkit` |
| C/C++ | `socket(`、`connect(`、`bind(`、`send(`、`recv(`、`getaddrinfo`、`curl_`、`libcurl`、`mbedtls`、`openssl` 的网络函数、`OSCMessage`（`OSCMessage` 只做本地序列化，不是网络 API，但为避免歧义一并禁止） |

补充规则：

| 编号 | 规则 |
|---|---|
| NET-A-1 | 上述符号的**唯一允许出现位置**是 `tools/network_audit.py` 自身的匹配表，以及测试代码 `tests/unit/test_no_network_symbols.cpp`（该测试用 `nm`/`strings` 扫描最终产物） |
| NET-A-2 | `strings` 扫描最终 `.app` 可执行文件与 `.dylib`，命中 `http://`、`https://`（除出现在 URL 注释常量表、license 清单文本中）即失败。license 清单生成器会把依赖的许可证 URL 写进 `Licenses` 资源，这些 URL 必须集中在**一个**已知的 `licenses.json` 资源文件里，且审计脚本对白名单文件放行 |
| NET-A-3 | Swift 侧不得出现 `import Network`、`import CFNetwork`；Kotlin 侧不得出现 `okhttp3.`、`retrofit2.`、`com.squareup.`、`okio.` |
| NET-A-4 | 第三方依赖中唯一允许含网络栈的是 `third_party/colmap`（用于其 `known/geometry` 等与网络无关的模块）；构建必须 `-DFETCH_*=OFF`（00 §8.4），禁止编译 COLMAP 的网络下载代码 |

**证明链 C — 链接产物层无网络框架**

CI 在 iOS 构建产物上执行：

| 检查 | 命令要点 | 判定 |
|---|---|---|
| 动态链接库清单 | `otool -L Recon.app/Recon` | 只允许出现系统框架：`Foundation`、`UIKit`、`AVFoundation`、`CoreMedia`、`CoreMotion`、`CoreGraphics`、`Metal`、`MetalKit`、`MetalPerformanceShaders`、`QuartzCore`、`ARKit`、`RealityKit`、`Accelerate`、`CoreML`(可选不用)、`SwiftUI`、`Photos`、`UniformTypeIdentifiers`、`CoreImage`(可选)。出现 `CFNetwork.framework`、`Network.framework`、`Security.framework`(TLS 客户端侧不需要)、`WebKit.framework` 即失败 |
| 未定义符号扫描 | `nm -u` | 命中 `socket` / `connect` / `send` / `recv` / `getaddrinfo` / `SSLCreateContext` / `SSLWrite` / `SecTrustEvaluate` 即失败 |
| Android 侧 | `readelf -d librecon.so` + `aapt dump permissions app.apk` | `librecon.so` 的 `NEEDED` 中不得出现 `libssl` / `libcrypto`（除非明确用于本地文件哈希——本产品用系统 `MessageDigest`，不需要）；`aapt dump permissions` 输出中不得出现 `android.permission.INTERNET` |

**证明链 D — Android 侧无网络能力**

| 检查 | 判定 |
|---|---|
| `AndroidManifest.xml` | **不声明** `android.permission.INTERNET`（详见 §2.2）。未声明该权限时，任何 socket 创建在 Linux 层直接返回 `EACCES`，无需依赖代码自律 |
| Play Services for AR | `com.google.ar.core`（Java SDK）通过 Binder 与独立安装的系统服务 `com.google.ar.core`（Google Play Services for AR）通信。该服务**不在本 APK 内**，其网络行为由 Google 的服务条款与用户设置决定，不受本 App 沙盒约束（00 §8.9 已确认此边界）。本产品对 ARCore 的使用被限制在**纯本地**能力：`Session` + world tracking + Depth API。**明确禁止**：Cloud Anchors、`ArCoreApk.requestInstall` 的云锚点模式、`Session` 的 `cloudAnchorEnabled`（本 SDK 版本已无此 API，代码中不得出现任何 Cloud Anchors 类型）、设备指纹/共享锚点 |
| ARCore 可用性检查 | `ArCoreApk.getInstance().checkAvailability(context)` 是**本地**查询（读已安装服务状态），不需要网络。使用 `checkAvailability` 而非 `requestInstall` 做探测，避免触发 Play Store 下载流程 |
| Google Play 服务 | 不声明 `com.google.android.gms.permission.AD_ID`（广告 ID）。ARCore SDK 会引入 `com.google.android.gms:play-services-*` 的部分传递依赖，必须在 CI 校验最终 APK 的权限集合中不含 `AD_ID` |
| 崩溃上报 | 不集成 Crashlytics / Firebase / Bugsnag / Sentry。不集成任何 analytics SDK |

### 2.3 运行时申请时序

```
用户点「开始扫描」
  └─→ 能力探测（无权限）
        └─→ RequestingPermission
              ├─ ContextCompat.checkSelfPermission(CAMERA)
              │     ├─ GRANTED → 直接开相机
              │     └─ 否则 → ActivityResultContracts.RequestPermission()
              │           ├─ 授予 → 开相机
              │           └─ 拒绝 → 提示「没有相机权限，无法扫描」+「去设置」
              │              （拒绝后不再自动申请；用户可从「去设置」跳转）
              └─ POST_NOTIFICATIONS：不在此申请
                    └─ 仅当用户在 U-06 点「后台继续重建」时才申请
```

| 编号 | 规则 |
|---|---|
| AND-P-1 | 相机权限是**唯一**在采集流程中申请的权限 |
| AND-P-2 | 拒绝相机权限后，`POST_NOTIFICATIONS` 不再申请（避免连续弹窗） |
| AND-P-3 | `shouldShowRequestPermissionRationale` 为 true 时，先显示一行内联文字 `需要相机权限才能扫描`，再弹系统对话框 |
| AND-P-4 | 权限文案取自 09 §5.7，与 iOS 侧中文文案完全一致 |

### 2.4 分区存储下的导出路径策略

**Android 10（API 29）起强制分区存储。** 本产品的导出文件走两条完全不同的路：**模型文件**与**预览图**。

| 目标 | API 29+（分区存储） | API ≤ 28 |
|---|---|---|
| 模型文件（GLB / OBJ+MTL+贴图 / PLY） | **优先 app 私有目录** `context.getExternalFilesDir(null)/exports/<session_id>/`（无需任何权限，卸载即删除，符合 00 §1「卸载即彻底删除」） | 同左 |
| 模型文件 · 交给用户 | 通过 `FileProvider` + `ACTION_SEND` 分享，或 `ACTION_CREATE_DOCUMENT` 让用户选位置 | 同左 |
| 模型文件 · 落到公共目录 | `MediaStore.Downloads`（API 29+）：`DISPLAY_NAME` / `MIME_TYPE` / `RELATIVE_PATH = Download/3DScan/` / `IS_PENDING=1` → 写完置 0。**无需存储权限** | `Environment.getExternalStoragePublicDirectory(DIRECTORY_DOWNLOADS)` + `WRITE_EXTERNAL_STORAGE`（`maxSdkVersion=28` 已声明，需运行时申请）+ `MediaScannerConnection.scanFile` 通知系统 |
| 预览图（PNG） | `MediaStore.Images`（API 29+）：`RELATIVE_PATH = Pictures/3DScan/`，`IS_PENDING` 两段式提交。**无需读权限** | `MediaStore.Images.Media.insertImage()` 或直接写 `Pictures/3DScan/` + `WRITE_EXTERNAL_STORAGE` + 扫描通知 |
| 多文件导出（OBJ+MTL+贴图） | 全部写入 `getExternalFilesDir(null)/exports/...`，用 `FileProvider` 的 `getUriForFile` 逐个生成 content URI 交给 `ACTION_SEND`（`EXTRA_STREAM` 数组）。**不**用 MediaStore（MediaStore 不保证多文件同目录语义与命名） | 同左 |
| 缓存/中间结果 | `context.cacheDir/` 与 `context.getExternalFilesDir(null)/cache/`，`cacheDir` 由系统在空间紧张时清理 | 同左 |
| 重建中间结果（分块落盘） | `getExternalFilesDir(null)/recon_cache/<session_id>/`，**app 私有**，不占用公共存储配额，不触发 `MediaStore` 扫描 | 同左 |

| 编号 | 规则 |
|---|---|
| AND-S-1 | **app 私有目录是默认落点**，公共目录是用户显式选择后的结果 |
| AND-S-2 | 私有目录的 `getExternalFilesDir` 在应用卸载时自动删除，满足 00 §1「数据留存：全部落在应用沙盒目录，卸载即彻底删除」 |
| AND-S-3 | `MediaStore` 写入必须用 `IS_PENDING` 两段式（API 29+），写完再置 0，避免半文件被其他应用读到 |
| AND-S-4 | `FileProvider` 的 `authority` 固定为 `${applicationId}.fileprovider`，`paths.xml` 只暴露 `exports/` 与 `cache/`，不暴露整个外部存储 |
| AND-S-5 | 导出文件命名规则：`<会话名>_<时间戳>.<ext>`，如 `陶瓷杯_20261030T143012Z.glb`；`session_id` 保留原始形式 `20261030T143012_a7f3` 在 `recon_mesh_info.json` 中 |
| AND-S-6 | iOS 对应策略见 §4.5，两端在 `recon_mesh_info.json` 中记录相同的 `export.path` 与 `export.container`（`app_private` / `photos` / `files` / `user_picked`） |

### 2.5 前台服务决策

**结论：使用前台服务，但类型是 `dataSync`，**不使用** `FOREGROUND_SERVICE_CAMERA`。**

| 维度 | 论证 |
|---|---|
| 是否需要后台运行 | **需要**。高精度档典型重建耗时约 35 分钟（08 §2.4），用户在重建期间极可能切到其他 App。若无前台服务，进程在后台被系统回收的概率极高，重建中断且已产出的中间结果可能丢失，用户体验不可接受 |
| 为什么不用 `FOREGROUND_SERVICE_CAMERA` | 该类型用于「前台服务需要访问相机」。本产品的相机在 `recon_finish_capture()` 后已完全停止（`AVCaptureSession.stopRunning` / `CameraDevice.close`），重建阶段不再访问相机。声明 `FOREGROUND_SERVICE_CAMERA` 属于**超范围声明**，在 Play 审核中会被质疑，且会引入「相机在后台开启」的隐私疑虑 |
| 为什么用 `dataSync` | 重建是纯本地的数据处理任务，语义上属于数据同步类。Android 14 起 `dataSync` 有配额（前台服务累计 6 小时/24 小时），本产品单次重建远低于该上限 |
| `FOREGROUND_SERVICE_DATA_SYNC` | Android 14（API 34）起必须**同时**声明类型权限，否则 `startForeground` 抛 `SecurityException` |
| `POST_NOTIFICATIONS` | API 33+ 需要用户授权才能展示通知。**可选**：用户拒绝后前台服务照常运行，通知不展示（系统仍在任务管理器中显示）。因此拒绝不阻断功能，不需强引导 |
| 通知内容 | 纯文字：`正在重建模型 · 阶段 3/14 稠密匹配`；常驻，不可滑动（`setOngoing(true)`）；点击回到 U-06。禁止进度条动画、禁止缩略图 |
| 唤醒锁 | `WakeLock` 标签 `recon:rebuild`，`PARTIAL_WAKE_LOCK`，超时设为 `RECON_MAX_REBUILD_MS = 2 小时`，到时释放并写 `E_REBUILD_TIMEOUT`（见下） |
| 采集阶段 | **不使用**前台服务。采集时 App 在前台，相机在前景，不需要 |

**工程约束（诚实披露）**

| # | 约束 | 处置 |
|---|---|---|
| 1 | Android 12（API 31）起禁止从后台启动前台服务 | 重建服务只能由用户在 U-06 主动点「后台继续重建」触发（此时 App 在前台，允许）；系统不得自动拉起 |
| 2 | Android 8+ 要求前台服务必须 5 秒内调用 `startForeground`，否则 `ANR` | `startForegroundService()` 后在 `onCreate` 同步调用 `startForeground()`，通知构建失败时也要用占位通知兜底 |
| 3 | 厂商杀后台策略（MIUI / EMUI / ColorOS 等）会额外杀进程 | 依赖 §4.4 的检查点恢复：重建按阶段写检查点，被杀后从最近检查点续跑。**这是产品级承诺，不承诺「一定不被打断」** |
| 4 | `dataSync` 前台服务在 Android 15+ 对「长时间运行且无用户可见 UI」有额外限制 | 重建前台服务始终绑定一个可见通知（`setOngoing`），并在 `onTaskRemoved` 中保留检查点 |
| 5 | 超时 | 单次前台重建上限 2 小时；超时写 `E_REBUILD_TIMEOUT`，保留检查点，提示 `重建超时，已保留进度`（09 §5.5 R-13 同族） |

**Android 侧 `dataSync` 服务的声明**

    android:exported="false"
    android:foregroundServiceType="dataSync" />
```

### 2.6 零网络在 Android 上的加强

| 项 | 处置 |
|---|---|
| `INTERNET` 不声明 | 系统层面阻断所有出站 socket（`EACCES`）。这是比「代码自律」更强的保证 |
| `ACCESS_NETWORK_STATE` 不声明 | 应用无法查询网络状态，进一步避免「探测网络后决定是否上传」这类设计 |
| `WebView` 不使用 | 禁止引入 `android.webkit`。CI 校验依赖树中无 `androidx.webkit` |
| 依赖审查 | CI 校验最终 APK 的 `classes.dex` 中不含 `okhttp3/`、`retrofit2/`、`com/squareup/`、`okio/`、`java/net/URL`、`org/apache/http/`（Apache HttpClient 被 `org.apache.http.legacy` 剔除时一同移除） |
| ARCore SDK 的传递依赖 | ARCore Java SDK 会引入 `com.google.android.gms:play-services-*`。CI 校验最终 APK 权限集合不含 `AD_ID`；`play-services-*` 本身含少量网络栈符号（如 `play-services-basement` 的 `GmsCore` 通信），但这些符号位于 **Play Services 客户端库**内、由系统服务 `com.google.android.gms` 执行，**本 App 的 `INTERNET` 缺失使这些库无法建立自己的出站连接**。结论：保留 ARCore 不破坏零网络承诺 |

| 15 | `AVCaptureDevice.isSmoothAutoFocusEnabled` | — | `false`。连续自动对焦会导致帧间几何抖动 |

#### 3.1.2 格式选择算法（最高分辨率且支持 60fps）

**目标**：在满足 `cap_resolution_width` × `cap_resolution_height`（比例由用户设定，宽高比需与目标一致，允许 16:9 / 4:3 / 1:1）与 `cap_frame_rate` 的前提下，取**分辨率最大**的格式；若多个格式分辨率相同，取帧率上限更高者；再相同则取像素格式为 BGRA 者（避免 YUV→BGRA 转换）。

```
输入: device, targetWidth, targetHeight, targetFps
候选集 C = device.formats.filter { format in
    let dims = CMVideoFormatDescriptionGetDimensions(format.formatDescription)
    let w = dims.width, h = dims.height
    // 1) 分辨率不低于目标（允许向上取最近档，不允许低于目标）
    w >= targetWidth && h >= targetHeight
    // 2) 宽高比接近目标（容差 8%），否则会引入裁切
    && abs((w/h) - (targetWidth/targetHeight)) / (targetWidth/targetHeight) < 0.08
    // 3) 支持目标帧率
    && format.videoSupportedFrameRateRanges.contains { $0.minFrameRate <= targetFps
                                                     && $0.maxFrameRate >= targetFps }
    // 4) 可用于该输出
    && device.formats 已被 isVideoSupported 过滤
}
若 C 为空:
    降级 1: 放宽条件 3（取帧率最接近 targetFps 的区间），记 W_CAPTURE_FPS_FALLBACK
    降级 2: 放宽条件 2 到 20%，记 W_CAPTURE_ASPECT_FALLBACK
    降级 3: 放宽条件 1 到「不低于目标的 80%」，记 W_CAPTURE_RES_FALLBACK
    全部放宽后仍为空 → 报错 E_CAPTURE_SOURCE_FAIL
排序: 按 (w*h) 降序 → 按 maxFrameRate 降序 → 按是否 BGRA 降序
取第一个
```

| 项 | 说明 |
|---|---|
| 实际生效分辨率 | 选定格式后，`CMVideoFormatDescriptionGetDimensions` 的值才是真实分辨率，**必须回写**到 `manifest.json` 的 `capture.rgb_width/height`，并显示在 U-02 的传感器行 |
| 帧率回写 | 实际帧率 = 选定格式 `videoSupportedFrameRateRanges` 中包含 `targetFps` 的区间的 `maxFrameRate`。回写到 `manifest.json` 的 `capture.fps` |
| 60fps 可得性 | 60fps 通常仅在 1080p 及以下可用；4K 多数机型锁定 30fps。因此 `cap_frame_rate=60` + `cap_resolution_width=3840` 的组合在多数机型不可满足 → 触发降级 1/3，UI 必须显示实际帧率（U-02 传感器行） |
| 4K + 60 | 若某机型确提供 4K60 格式，按上述算法直接选中 |

#### 3.1.3 `AVCaptureVideoDataOutput` 的 delegate 队列与丢帧策略

| 项 | 配置 | 理由 |
|---|---|---|
| 像素格式 | `videoSettings = [kCVPixelBufferPixelFormatTypeKey: kCVPixelFormatType_32BGRA]` | 直接得到 BGRA8，与 `recon_frame_packet.rgb_data`（BGRA8，00 §7.2）契约一致，零转换 |
| delegate 队列 | 专用串行队列 `DispatchQueue(label: "recon.capture.video", qos: .userInitiated)` | **不得**放在主队列（主队列还要跑 UI）；**不得**用并发队列（帧序必须严格单调） |
| `alwaysDiscardsLateVideoFrames` | **`false`** | 00 R-PREC-3「关键帧只要对精度有增益即全量保留，不做自动剔除」。设为 `true` 会让系统在 delegate 忙时**静默丢弃帧**，直接违反 R-PREC-3 |
| 由此带来的背压处理 | 见下 | `false` 意味着系统不再替我们丢帧，慢的是我们自己，必须自行处理 |
| 帧缓冲所有权 | 回调内 `CVPixelBufferRetain` + 存入 `shared_ptr`（deleter = `CVPixelBufferRelease`），入队后立即返回 | 02 §2.4.1 的所有权规则 |
| 入队策略 | 有界环形队列，容量 = `cap_ring_buffer_frames`（默认 600）。**满了怎么办** | 见下 |

**手动背压（`alwaysDiscardsLateVideoFrames = false` 的必要配套）**

```
captureOutput(_:didOutput:from:)  // 在 recon.capture.video 队列上
  1. frame_id = 递增计数
  2. 若当前状态 != Capturing（Previewing / Reviewing）：
        直接 CVPixelBufferRelease（不 Retain），return     // 预览期不采帧
  3. 若队列已满（size == capacity）：
        丢最旧的一帧（释放其 CVPixelBuffer），stats.frames_dropped_writer++
        记 E_CAPTURE_BACKPRESSURE（warn）
        // 关键说明：丢的是「还没被核心层处理完的帧」，不是「已入库的关键帧」。
        // 已入库关键帧在磁盘上，不受此影响（R-PREC-3 不被违反）
  4. CVPixelBufferRetain，入队
  5. 返回（不阻塞）
```

| 编号 | 规则 |
|---|---|
| IOS-BP-1 | 丢帧只发生在「尚未交给核心层的预览级帧」上；**已通过质量门限、已写入 `index.bin` 的关键帧永不丢弃**（R-PREC-3） |
| IOS-BP-2 | 丢帧计数写入 `manifest.json` 的 `stats.frames_dropped_writer`，U-03 的帧计数旁在丢帧累计 > 0 时追加一行 `footnote` `txt.warning` `已丢弃 N 帧` |
| IOS-BP-3 | 队列深度上限与 `cap_ring_buffer_frames` 一致，用户改小该参数会**立即**生效（热更新，无需重建会话） |
| IOS-BP-4 | `recon.push_frame` 的核心层驻留上限 1000 ms（02 §2.4 M-2），超时强制释放并记 `E_CAPTURE_BACKPRESSURE` |
| IOS-BP-5 | 若背压持续 > 5 s（如存储卡极慢），UI 显示内联提示 `存储写入较慢`（09 §5.4 D-08） |

**速率上限的工程事实（必须诚实处理）**

> ⚠️ **本节曾引用两个不存在的 API**（`maximumDeviceMotionUpdateInterval` /
> `maximumGyroUpdateInterval`），2026-11-01 由 CI 真编译暴露（`CameraCapture.swift`
> 据此写出的代码报 `value of type 'CMMotionManager' has no member`）。
> **Apple 未提供任何查询传感器硬件最大采样率的接口** —— `CMMotionManager` 上的
> `gyroUpdateInterval` / `deviceMotionUpdateInterval` 都是**调用方写入的期望值**，
> 读回来只是自己刚写进去的数。故下表改为**实测经验值**，并明确它不可查询。

| API | 实测典型上限 | 说明 |
|---|---|---|
| `CMDeviceMotion` | **≈100 Hz** | 硬件融合输出，速率由 SoC 决定，多数机型固定在 100 Hz 附近。**只能实测**，无查询接口 |
| `CMGyro` | **≈100–200 Hz**（依机型） | 原始角速度。**只能实测**，无查询接口 |
| `CMAccelerometer` | **≈100 Hz** | 与 deviceMotion 同 |

**后果（必须遵守）**：因为不可查询，`recon_probe_data.imu_max_rate_hz` 在 iOS 侧
**写 0（未知）**，不得填任何「看起来像真的」的常量 —— 那是伪造事实。Android 侧
不受影响（`Sensor.getMaxDelay()` 是真实 API，可算出该值）。若需真实速率，唯一
诚实做法是在会话中**统计实际投递样本的时间戳间隔**（测量值）。

| 编号 | 规则 |
|---|---|
| IOS-IMU-1 | `cap_imu_rate_hz` 是**用户期望值**。平台层实际能达到的速率 = `min(期望值, 硬件上限)`，**必须回写**到 `manifest.json` 的 `device.imu_rate_hz`，U-02 的传感器行显示实际值（例：`陀螺仪 是 100 Hz`，用户设的是 200） |
| IOS-IMU-2 | 要达到 200–400 Hz（08 快速/标准/高精度档分别是 100/200/400），**必须用 `CMGyro` 的原始角速度**作为预积分输入，`CMDeviceMotion` 只用于「重力方向 + 磁北参考 + 姿态初值」。具体：`CMGyro` 提供 `rotationRate`（原始陀螺），`CMAccelerometer` 提供 `userAcceleration`（去重力后的加计），两者由核心层自行预积分（02 §3.5）。这与 Android 侧「陀螺 + 加计分传感器采样」的方案**结构一致**，保证两端 VIO 行为可比 |
| IOS-IMU-3 | `CMDeviceMotion.rotationRate` **不用于**预积分（它已是融合结果，含滤波延迟，无法回溯到采样瞬间），仅用于 UI 显示与航向参考 |
| IOS-IMU-4 | `CMMotionManager.authorizationStatus()` 返回 `.notDetermined` 时，**不主动请求**（`CMMotionActivityManager.requestActivityAuthorization` 才会弹窗，且我们不用它）。直接调用 `startDeviceMotionUpdates`，若系统返回错误则降级为无 IMU（`cap_imu_enabled` 等效置 0），并在 U-03 提示 `未授予运动权限，位姿精度会下降`（09 §5.7 P-03） |
| IOS-IMU-5 | `startGyroUpdates` 与 `startDeviceMotionUpdates` 同时开启会产生两次传感器中断（功耗翻倍）。因此：`cap_imu_rate_hz ≤ 100` 时只开 `deviceMotion`（用其 `rotationRate` 与 `userAcceleration`，精度足够）；`> 100` 时必须开 `gyro` + `accelerometer` 组合替代 `deviceMotion` |

**与核心层的对接**

| 量 | 来源 | 单位 | 送入 |
|---|---|---|---|
| 角速度 | `CMGyroData.rotationRate`（x, y, z） | rad/s | `recon_imu_sample.gyro` |
| 加速度 | `CMAccelerometerData.acceleration`（已含重力） | m/s² | `recon_imu_sample.accel`（核心层减重力） |
| 时间戳 | `CMGyroData.timestamp` / `CMAccelerometerData.timestamp` | s（mach 时间基） | `recon_imu_sample.timestamp` |

### 3.2 iOS：ARKit

#### 3.2.1 Session 配置

| 项 | API / 取值 | 理由 |
|---|---|---|
| 配置类型 | `ARWorldTrackingConfiguration` | 本产品需要设备位姿与世界坐标系 |
| `worldAlignment` | `.gravity` | 不用 `.gravityAndHeading`：后者依赖磁力计/方位，在部分设备上漂移大，且与定位权限相关 |
| `planeDetection` | `[]`（关闭） | 本产品用自有物体中心估计（03 §4.5），不需要平面检测；关闭可省 15–25% 功耗 |
| `environmentTexturing` | `.none` | 不做环境光照重建（那是环境理解，不是物体扫描） |
| `sceneReconstruction` | `.none` | **必须关闭**。`ARMeshAnchor` 面向实时环境理解，其网格精度不足以作为物体扫描产物（00 §8.1）；开启还额外消耗带宽 |
| `frameSemantics` | `[.sceneDepth, .smoothedSceneDepth]`（当 `supportsFrameSemantics(.sceneDepth)` 为真） | 提供 LiDAR 深度。注意：`sceneDepth` 是厘米级低精度（00 §8.1），仅用于尺度锚定 + TSDF 先验 + 低纹理区补全 |
| `videoFormat` | 从 `configuration.supportedVideoFormats` 中选，见下 | 同时决定 RGB 分辨率与是否支持深度语义 |
| `isAutoFocusEnabled` | `true`（连续自动对焦） | ARKit 模式下无法手动锁定曝光/对焦（见 §3.2.3） |
| `environmentBlendMode` | `.alpha` | 不需要 |

**`videoFormat` 选择算法**

```
候选 = ARWorldTrackingConfiguration.supportedVideoFormats.filter { fmt in
    // 支持深度语义的格式必须先筛出来：逐个尝试 configuration.frameSemantics 赋值，
    // 若抛异常则该格式不支持 sceneDepth
    fmt.supportsFrameSemantics(.sceneDepth)   // iOS 14+ 该属性在 ARVideoFormat 上
}
若需要 sceneDepth 而候选为空 → 深度等级降为 0（ALGO_DEPTH 或无深度），走 BRANCH_MONO
排序:
  1) fmt.imageResolution.width * height 降序
  2) 同分辨率下，framesPerSecond 降序（60 > 30）
  3) 同上，优先非 HDR（ARFrame.capturedImage 的动态范围更可控）
取第一个
```

| 项 | 说明 |
|---|---|
| ARKit 图像分辨率的现实上限 | `ARVideoFormat.imageResolution` 典型为 1920×1440 或更小，**明显低于 AVFoundation 的 4K**。这直接决定了 §3.3 的管线选择 |
| 回写 | 选定的 `imageResolution` 与 `framesPerSecond` 回写 `manifest.json` 的 `capture.rgb_width/height` 与 `capture.fps` |
| 深度分辨率 | `ARFrame.sceneDepth` 的分辨率由 `ARConfiguration` 与设备决定，通常独立于 RGB 分辨率（可能更低）。回写 `capture.depth_width/height` |

| 回调 | 队列 | 用途 |
|---|---|---|
| `session(_:didUpdate:)` | `ARSession.delegateQueue`（专用串行 `OperationQueue`，`maxConcurrentOperationCount = 1`，`qualityOfService = .userInitiated`） | 取 `frame.capturedImage`（BGRA/YCbCr 的 `CVPixelBuffer`）、`frame.sceneDepth` / `frame.smoothedSceneDepth`、`frame.camera.transform`、`frame.camera.intrinsics`、`frame.camera.trackingState`、`frame.timestamp` |
| `session(_:cameraDidChangeTrackingState:)` | 同上 | 追踪状态机（见下） |
| `session(_:didFailWithError:)` | 同上 | 致命错误 → `Failed` |

**追踪状态处理**

| `ARCamera.TrackingState` | 处置 | UI |
|---|---|---|
| `.normal` | 正常采帧 | — |
| `.notAvailable` | 停止采帧，等待 | 内联 `位置跟踪暂不可用` |
| `.limited(reason)` | `.initializing` → 等待；`.excessiveMotion` → 暂停采帧并提示 `移动太快`；`.insufficientFeatures` → 降级为纯视觉并提示 `场景特征不足，位姿精度会下降`；`.relocalizing` → 暂停采帧 | 见 09 §5.2 / §5.7 |
| 失追踪累计 > 10 s | 降级为纯视觉（`cap_imu_enabled` 保持，但 AR 位姿先验停止供给） | `已切换为纯视觉跟踪，位姿精度会下降`（09 P-07） |

### 3.3 ARKit 与 AVFoundation 的冲突与协调（核心方案）

#### 3.3.1 冲突的事实

| 事实 | 说明 |
|---|---|
| 独占性 | iOS 上相机是**独占资源**。`AVCaptureSession` 与 `ARSession` **不能同时**打开同一个相机。ARKit 运行期间，`AVCaptureDevice` 的 `AVCaptureSession` 启动会失败并抛 `AVErrorApplicationIsNotAuthorized` / `AVErrorSessionNotRunning` 类错误；反之亦然 |
| 能力不对称 | AVFoundation 提供：最高 4K/60 分辨率、手动曝光 / ISO / 白平衡 / 对焦锁定、`AVCapturePhotoOutput` 高分辨率单帧。ARKit 提供：设备位姿、世界坐标、LiDAR `sceneDepth`、平面与环境理解。**两者能力互补且不可叠加** |
| 数据通路 | ARKit 的 `ARFrame.capturedImage` 已经是相机原始流的 YUV 缓冲（不是「相机截图」），可以直接作为重建的 RGB 输入 |

#### 3.3.2 协调方案：`CameraSource` 单一实现 + 两种互斥后端

**决策：抽象出统一的 `CameraSource` 接口（L2 层），提供两个互斥后端，运行时二选一。选择由「用户需要的分辨率 + 是否需要深度」决定，并把选择结果明示在 U-02。**

```
                ┌───────────────────────────────┐
                │  CameraSource (L2 抽象)        │
                │  start / stop / configure     │
                │  onFrame(RGB, Depth, Pose?)    │
                │  onPose(Pose)                 │
                └───────┬───────────────┬───────┘
                        │               │
        ┌───────────────▼──────┐  ┌────▼──────────────────┐
        │ AVFoundationSource   │  │ ARKitSource           │
        │ (iOS, 无深度)        │  │ (iOS, LiDAR 深度)     │
        │ 4K/60 · 手动曝光     │  │ 1920×1440 · 位姿+深度 │
        │ AVVideoDataOutput    │  │ ARFrame.capturedImage │
        │ AVCapturePhotoOutput │  │ ARFrame.sceneDepth    │
        └──────────────────────┘  └───────────────────────┘
```

**后端选择决策表**

| 条件 | 选择后端 | 管线分支 | 深度等级 | 尺度来源 | UI 必须显示 |
|---|---|---|---|---|---|
| 设备支持 `sceneDepth` **且** 用户不需要 > 1920×1440 的纹理分辨率（默认档） | `ARKitSource` | `BRANCH_RGBD` | 3（`HW_LIDAR`） | LiDAR 锚定 + 可选参照物复核 | `重建管线 彩色+深度融合+多视图立体`；`纹理分辨率 1920×1440` |
| 设备支持 `sceneDepth` **且** 用户选了高精度档且 `cap_resolution_width ≥ 3840` | **AVFoundationSource**（放弃 LiDAR） | `BRANCH_MONO` | 0 | 参照物 / 手动 | `纹理分辨率 3840×2160` + 提示 `已关闭深度传感器以获取更高分辨率，尺度需要参照物标定` |
| 设备不支持 `sceneDepth` | `AVFoundationSource` | `BRANCH_MONO` | 0 | 参照物 / 手动 | `重建管线 单目+多视图立体（MVS）` |
| 用户在参数面板关闭 `cap_depth_enabled` | `AVFoundationSource` | `BRANCH_MONO` | 0 | 参照物 / 手动 | 同上 |
| 任意情况下用户手动强制 | 用户指定 | 按分支 | — | 用户指定 | U-02 显示当前生效后端 |

| 编号 | 规则 |
|---|---|
| IOS-AR-1 | **不做「ARKit 拿位姿 + AVFoundation 拿高分辨率图像」的组合**。该组合在 iOS 上物理不可行（相机独占）。任何声称能同时跑的实现都依赖非公开 API 或会崩溃 |
| IOS-AR-2 | 后端切换只在**会话开始前**发生（`Previewing` 状态内）。采集中途不切换。若用户在采集中改 `cap_resolution_width`，按 08 §3.3 A 类处理：提示 `需要重新开始采集` |
| IOS-AR-3 | 后端切换的时序：① `session.pause()`（ARKit）→ ② 等待 `ARSession` 的 `sessionInterruptionEnded` 或 500 ms 超时 → ③ `AVCaptureSession.stopRunning()` → ④ `commitConfiguration()` 启动另一后端 → ⑤ 等待第一帧回调 → ⑥ 恢复采集。总耗时 0.6–1.2 s，期间 UI 显示 `正在切换采集方式` |
| IOS-AR-4 | **反方向组合是允许且推荐的**：当使用 `AVFoundationSource` 时，位姿由**自研 VIO**（`core/vio`，MSCKF + IMU 预积分）提供，ARKit 完全不启动。当使用 `ARKitSource` 时，ARKit 位姿作为**先验**注入 VIO/SfM（00 §2 术语表：「仅作先验，不作为位姿真值」），VIO 仍然运行以获得高频位姿 |
| IOS-AR-5 | ARKit 模式下的 RGB 缓冲为 YUV（`kCVPixelFormatType_420YpCbCr8BiPlanarFullRange`）。为保持 `recon_frame_packet.rgb_data = BGRA8` 契约不变，转换在平台层的 Metal compute kernel 中完成（`platform/ios/MetalComputeBackend.mm` 的 `yuv_to_bgra`），1080p 单帧 GPU 转换 < 0.4 ms |
| IOS-AR-6 | 后端类型与深度等级必须写入 `manifest.json`（`capture.source` = `avfoundation` / `arkit`，`capture.depth_source`），供 14 文档验收追溯 |

#### 3.3.3 Android 侧同类问题的处理（对应关系）

| iOS | Android | 说明 |
|---|---|---|
| `ARKitSource` | `ARCoreSource`（`Session` + `frame.acquireCameraImage()`） | ARCore 也独占相机；`acquireCameraImage()` 返回 YUV_420_888 缓冲，分辨率通常 640×480 或 1920×1440（依设备与配置） |
| `AVFoundationSource` | `Camera2Source`（`CameraDevice` + `CameraCaptureSession` + `ImageReader`） | 可同时挂载 `ImageReader`(YUV) 与 `ImageReader`(DEPTH16)，**在同一个会话里同时拿到 RGB 与硬件 ToF 深度**——这是 Android 相对 iOS 的优势 |
| ARKit 位姿作先验 | ARCore `frame.camera.getPose()` 作先验 | 同构 |
| 无法同时用 ARCore 与 Camera2 | 同 | Camera2 直接路径下**不启动 ARCore**；ARCore 仅在「需要 AR 位姿先验且设备无硬件 ToF 直出」时单独启用 |

### 3.4 Android：相机（Camera2 直接路径为主）

#### 3.4.1 为什么用 ImageReader 而非 ImageAnalysis（论证）

**结论：帧流主通道使用 Camera2 直接路径 + `ImageReader`。`ImageAnalysis` 只在降级路径使用，且降级路径必然降低帧率上限（明确标注）。**

**论证一：CameraX `ImageAnalysis` 的背压模型与「全量保留帧」冲突**

| `ImageAnalysis.Builder.setBackpressureStrategy` | 行为 | 对本产品的影响 |
|---|---|---|
| `STRATEGY_KEEP_ONLY_LATEST` | 相机缓冲区满时**丢弃最旧的帧**，只保留最新帧 | **直接违反 R-PREC-3**（关键帧全量保留、不做自动剔除）。视角密度直接损失，MVS 的视图数 `mvs_num_views` 无法满足 |
| `STRATEGY_BLOCK` | 阻塞 `ImageAnalysis.Analyzer` 的 `analyze()`，相机管道停等 | 表面上「不丢帧」，实际上相机会**硬件级停流**，产生的后果是：① 帧时间戳间隔出现异常大空洞（触发 02 §3.8 的时间戳异常检测）；② 部分 SoC 的相机 HAL 在阻塞时会重置内部状态并丢帧；③ 帧率从 30 fps 掉到 5 fps，直接损失视差密度 |

**论证二：`ImageReader` 是唯一能「取走即入库」的输出**

| 特性 | `ImageReader` | `ImageAnalysis` |
|---|---|---|
| 输出本质 | Surface 消费者，应用主动 `acquireNextImage()` 取帧 | 相机帧被封装成 `ImageProxy` 推给 analyzer |
| 应用不取会怎样 | `maxImages` 个缓冲被占满后，相机**停止**送帧（阻塞，应用端感知明确） | 取决于策略：KEEP_ONLY_LATEST 丢帧 / BLOCK 阻塞 |
| 帧完整性 | 每帧独立、可完整取走、可立刻 `acquire()` 提升引用计数后异步处理 | `ImageProxy` **不得跨线程持有超过一帧**（02 §2.4.1），处理完必须 `close()` |
| 多输出 | **可与 DEPTH16 的 `ImageReader` 挂在同一个 `CameraCaptureSession`** | `ImageAnalysis` 只能一个，深度需另走 ARCore（→ 重新引入相机独占问题） |

**论证三：CameraX 无法挂载任意 `ImageReader`**

| 事实 | 后果 |
|---|---|
| CameraX 的一等公民输出是 `Preview` / `ImageCapture` / `VideoCapture` / `ImageAnalysis` 四个 UseCase，各自内部管理 `ImageReader` / `Surface` | 想拿到「全分辨率、连续、全量」的 YUV 流，没有公开 API |
| `Camera2Interop.Extender` 只提供 `setCaptureRequestOption` / `setSessionStateCallback` / `addStreamConfiguration`（后者仅在 `ImageCapture` 的场景下追加一路 Camera2 流） | 无法用它把一路自由配置的 `ImageReader` 挂到 CameraX 的会话上 |
| `CameraEffect`（CameraX 1.4+）的 `SurfaceProcessor` 能拿到 `ImageProxy` 但同样受 UseCase 生命周期与背压策略约束 | 不解决全量保留问题 |

**论证四：本产品还需要 Camera2 独有能力**

| 能力 | CameraX | Camera2 直接路径 |
|---|---|---|
| 手动曝光时间 / ISO | `CameraControl` 只能给 `setExposureCompensationIndex`（离散档位），无法精确设 `SENSOR_EXPOSURE_TIME` | `CaptureRequest.SENSOR_EXPOSURE_TIME` / `SENSOR_SENSITIVITY` 精确到 μs / ISO 单位，满足 08 `cap_exposure_time_us`、`cap_iso` 的连续可调要求 |
| 白平衡锁定 | `CameraControl.setLinearZoom` 等无 AWB 控制 | `CONTROL_AWB_MODE = OFF` 冻结当前增益（见 §3.4.4 的诚实说明） |
| 手动对焦距离 | `CameraControl.enableTorch` / 无 `LENS_FOCUS_DISTANCE` | `LENS_FOCUS_DISTANCE`（diopter）精确控制，满足 `cap_focus_distance_m` |
| 硬件 ToF 深度 | 必须走 ARCore（相机独占） | `ImageReader` + `ImageFormat.DEPTH16` 与 RGB **同会话**双流 |
| 高分辨率单帧 | `ImageCapture` 可用（见 §3.4.5） | 同 |

**最终架构决策**

```
主路径（Android 帧流）:
    CameraManager → CameraDevice → CameraCaptureSession
        surfaces = [ ImageReader(YUV_420_888, maxImages=cap_ring_buffer_frames/8),
                     ImageReader(DEPTH16, maxImages=4)  ← 仅当硬件 ToF 直出可用 ]
        ImageReader.setOnImageAvailableListener → 立即 acquireNextImage() → 入有界队列
    降级路径（Camera2 打开失败 / 厂商 HAL 缺陷）:
    CameraX: Preview + ImageAnalysis(STRATEGY_BLOCK) + ImageCapture
        明确标注: 帧率上限 15 fps，UI 显示 "已切换到兼容采集模式，帧率上限 15 帧每秒"
```

#### 3.4.3 格式选择（对应 iOS §3.1.2）

```
候选 = OutputConfiguration 集合.filter { it.format == ImageFormat.YUV_420_888
         && size.width >= targetWidth && size.height >= targetHeight
         && abs((w/h) - (targetWidth/targetHeight)) < 0.08
         && 输出组合总大小 <= 设备能力 }
Camera2 没有「格式内帧率范围」，帧率受 `CONTROL_AE_AVAILABLE_TARGET_RANGES` 与
`SENSOR_INFO_MAX_FRAME_DURATION` 约束 → 取该尺寸下最短的 frame duration:
    minFrameDuration = min over { SENSOR_INFO_MAX_FRAME_DURATION } 中的最短值
    若 1/minFrameDuration < targetFps → 该尺寸不支持目标帧率，剔除并记 W_CAPTURE_FPS_FALLBACK
排序: (w*h) 降序 → 支持的最大帧率降序
```

| 编号 | 规则 |
|---|---|
| AND-F-1 | Camera2 没有格式级帧率范围，必须用「该尺寸下最短 `SENSOR_INFO_MAX_FRAME_DURATION`」推算可得最高帧率 |
| AND-F-2 | 若目标帧率不可得，降级到该尺寸可得的最接近帧率，**回写 `manifest.json`** 并在 U-02 显示实际帧率（与 iOS 侧同样的回写规则） |
| AND-F-3 | 深度流尺寸独立选择：`ImageReader.newInstance(depthWidth, depthHeight, ImageFormat.DEPTH16, 4)`，`depthWidth/Height` 从 `SCALER_STREAM_CONFIGURATION_MAP` 中 `ImageFormat.DEPTH16` 的输出项取 |

#### 3.4.4 手动 AE / AWB / AF 的 Camera2 映射与诚实说明

| 参数（08 键名） | Camera2 请求字段 | 映射规则 | 诚实说明 |
|---|---|---|---|
| `cap_exposure_mode` = 1（手动锁定） | `CONTROL_AE_MODE = CONTROL_AE_MODE_OFF` + `SENSOR_EXPOSURE_TIME` + `SENSOR_SENSITIVITY` | `SENSOR_EXPOSURE_TIME = cap_exposure_time_us * 1000`（ns），并夹取到 `SENSOR_INFO_EXPOSURE_TIME_RANGE`；`SENSOR_SENSITIVITY = cap_iso` 并夹取到 `SENSOR_INFO_SENSITIVITY_RANGE` | 部分厂商 HAL 在 `AE_MODE_OFF` 下仍会覆盖曝光。**必须实测校验**：取回帧后比较实际亮度方差，偏差 > 20% 则记 `E_CAPTURE_AE_LOCK_FAILED` 并在 U-02 显示 `该设备不支持手动曝光锁定` |
| `cap_exposure_mode` = 2（AE 优先） | `CONTROL_AE_MODE = CONTROL_AE_MODE_ON` + `CONTROL_AE_PRIORITY` | `CONTROL_AE_PRIORITY` 设为 `CONTROL_AE_PRIORITY_EXPOSURE_TIME`（优先满足曝光时间） | — |
| `cap_iso` | `SENSOR_SENSITIVITY` | 模拟 ISO 与传感器增益的比值由 `SENSOR_INFO_SENSITIVITY_RATIO` 决定；`SENSOR_SENSITIVITY` 的单位是「等效 ISO」，厂商 HAL 内部再折算增益 | — |
| `cap_white_balance_mode` = 1（锁定） | `CONTROL_AWB_MODE = CONTROL_AWB_MODE_OFF` | **Camera2 公共 API 无法设置具体色温**。`CONTROL_AWB_MODE_OFF` 会冻结当前 AWB 增益，等价于「锁定当前白平衡」，但不是「锁定到 5200 K」 | **这是与 iOS 的能力差异，必须在 U-02 明示**：`该设备只能锁定当前白平衡，不能设定色温`。`cap_white_balance_kelvin` 在 Android 上**无效**，UI 上该控件置灰并标注 `本设备不支持设定色温`。UI 与文档不得声称两端等价 |
| `cap_white_balance_mode` = 2（仅白平衡锁定） | 同上 | 与 = 1 行为一致 | — |
| `cap_focus_mode` = 2（手动） | `CONTROL_AF_MODE = CONTROL_AF_MODE_OFF` + `LENS_FOCUS_DISTANCE` | `LENS_FOCUS_DISTANCE` 单位是 diopter，`d = 1.0 / cap_focus_distance_m`（米 → diopter），夹取到 `[0, min(1/LENS_INFO_MINIMUM_FOCUS_DISTANCE, ∞)]` | 部分 HAL 在 `AF_MODE_OFF` 下忽略 `LENS_FOCUS_DISTANCE`；同样需实测校验 |
| `cap_focus_mode` = 0/1 | `CONTROL_AF_MODE = CONTROL_AF_MODE_CONTINUOUS_PICTURE` / `CONTROL_AF_MODE_AUTO` | — | — |
| `cap_frame_rate` | `CONTROL_AE_TARGET_FPS_RANGE = Range(fps, fps)` | 夹取到 `CONTROL_AE_AVAILABLE_TARGET_RANGES` 中包含 `fps` 的区间 | — |
| `cap_rolling_shutter_correction` | 读 `SENSOR_INFO_TIMESTAMP_SOURCE` / `CameraMetadata.SENSOR_INFO_TIMESTAMP_SOURCE` 与厂商 `SENSOR_ROLLING_SHUTTER_SKEW` 扩展 | 有该扩展则按 02 的模型补偿；无则按全局快门处理 | 厂商扩展 key 是 `android.scaler.sensorRollingShutterSkew`（`SENSOR_INFO` 形式），非公开但被主流厂商实现。**读不到就当 0**（全局快门），不得猜测 |

| 编号 | 规则 |
|---|---|
| AND-AE-1 | 所有 Camera2 手动控制都必须在**目标机型实测**（14 文档的能力矩阵），实测不通过的能力在 U-02 明确标注为不可用，控件置灰 |
| AND-AE-2 | 任何因 HAL 不支持而无法执行的参数设置，**不得静默忽略**：写入 `manifest.json` 的 `capture.unapplied_settings` 列表，U-02 显示 `部分手动参数在本机不可用` |
| AND-AE-3 | `cap_imu_enabled`、`cap_depth_enabled` 等布尔参数在硬件不支持时同样走 `unapplied_settings`，不得假装生效 |

#### 3.4.5 `ImageCapture` / 高分辨率单帧（Android 对应 iOS `AVCapturePhotoOutput`）

| 项 | Android（CameraX `ImageCapture`） | iOS（`AVCapturePhotoOutput`） |
|---|---|---|
| 用途 | 定点模式的高分辨率锚点帧 | 同 |
| 配置 | `ImageCapture.Builder().setCaptureMode(ImageCapture.CAPTURE_MODE_MAXIMIZE_QUALITY).setJpegQuality(100)` | 见 §3.1.4 |
| 与帧流的关系 | `ImageCapture` 与帧流 `ImageReader` **属于不同会话**，不能共存于 Camera2 直接路径 | `AVCapturePhotoOutput` 与 `AVCaptureVideoDataOutput` 可共存于同一 `AVCaptureSession` |
| 结论 | Android 的主路径（Camera2 直接）**没有等价的高分辨率单帧能力**。定点引导模式在 Android 上若需要高分辨率锚点，必须用 `ImageCapture` 单独会话抓拍（相机独占 → 需暂停帧流） | — |
| 处置 | 定点引导模式在 Android 上**降级为「不抓高分辨率锚点」**，仅用帧流中质量最好的一帧（`q_total` 最高）作为锚点 | iOS 正常抓拍 |

| 编号 | 规则 |
|---|---|
| AND-PH-1 | 定点引导模式在两端能力不等价，**必须在 U-02 明示**：`定点引导（高分辨率锚点仅 iOS 支持）`。不隐瞒 |
| AND-PH-2 | 降级路径（CameraX）下可用 `ImageCapture` 抓拍，与帧流二选一（抓拍时暂停帧流 200–400 ms），该代价记入 `frames_dropped_platform` |

### 3.6 Android：SensorManager（陀螺 / 加速度计采样与 batching）

| 项 | API / 取值 | 说明 |
|---|---|---|
| 传感器 | `TYPE_GYROSCOPE`、`TYPE_ACCELEROMETER` | 与 iOS 的 `CMGyro` + `CMAccelerometer` 结构对应（IOS-IMU-2） |
| 采样周期 | `registerListener(listener, sensor, samplingPeriodUs, maxReportLatencyUs)` | `samplingPeriodUs = 1_000_000 / cap_imu_rate_hz`；`maxReportLatencyUs` 决定 batching |
| Batching | `maxReportLatencyUs = 20_000`（20 ms） | 允许传感器 HAL 把多个采样批成一次回调，减少唤醒次数与功耗 |
| 批内处理 | 回调中 `SensorEvent.values` 是**当前**采样；批内的历史采样通过 `SensorManager.getSensorManager().getDynamicSensorList`? 不对——历史批数据通过 `SensorEvent` 的 `timestamp` 逐事件到达 | 正确做法：启用 batching 后，每次回调收到**一个** `SensorEvent`；HAL 会把多个采样**合并丢失**。因此若需要全部原始采样，必须 `maxReportLatencyUs = 0` |
| **决策** | `maxReportLatencyUs = 0`（**关闭 batching**） | **本产品必须保留全部 IMU 采样**（预积分的精度直接依赖采样密度与抖动，02 §3.6.4 的 `σ_t` 项把「½ · Δt_IMU = 2.5 ms @200 Hz」计入误差预算）。开启 batching 会丢失中间采样，破坏这一预算。因此**明确关闭 batching**，以功耗换精度。这与 iOS 侧 `CMGyro` 逐样本回调的行为一致 |
| 若必须 batching 的降级 | `maxReportLatencyUs = 20000` 时，只使用**每个批次最后一个**采样 → 有效采样率降至 5–10 Hz → **不可接受**，直接拒绝该配置 | — |
| 线程 | 专用 `HandlerThread("recon.capture.imu")`，`Process.setThreadPriority(Process.THREAD_PRIORITY_DISPLAY)` | 回调必须快（只做值拷贝），不做计算（02 §2.4.1：IMU 采样为栈上 POD，值拷贝，立即释放） |
| 时间戳 | `SensorEvent.timestamp`（ns，elapsed realtime 时基） | 与 `Image.getTimestamp()` 同源，见 §4.3 |
| 时间戳来源 | `SensorManager.getTimestampSource(sensor)` → `SOURCE_REALTIME` / `SOURCE_SENSOR_CLOCK` / `SOURCE_UNKNOWN` | 02 §3.4 的处理规则；`SOURCE_UNKNOWN` 时拒用并触发 `E_SYNC_UNRELIABLE_CAM_TS` |
| 采样率校验 | 每 10 个样本统计一次实际速率，偏差 > 5% 触发 `E_SYNC_IMU_RATE_DRIFT` | 02 §3.8 |

| 编号 | 规则 |
|---|---|
| AND-IMU-1 | **不使用** `TYPE_GAME_ROTATION_VECTOR` / `TYPE_ROTATION_VECTOR` / `TYPE_MAGNETIC_FIELD`。这些是厂商融合输出，含不可回溯的滤波延迟，与 iOS 侧「原始陀螺 + 原始加计」的结构不一致，会造成两端 VIO 行为不可比 |
| AND-IMU-2 | **不使用** `TYPE_ACCELEROMETER` 的「含重力」值直接做预积分；必须先减去 `TYPE_GRAVITY` 或用低通估计重力，减去的重力分量需与 iOS `CMAccelerometerData.acceleration`（同样含重力）的处理一致 |
| AND-IMU-3 | 实际 IMU 速率回写 `manifest.json` 的 `device.imu_rate_hz`，U-02 显示实际值 |
| AND-IMU-4 | 传感器不可用（无陀螺）时，`cap_imu_enabled` 等效置 0，退化为纯单目，U-02 显示 `陀螺仪 否` |

### 4.3 时间戳对齐（承接 02 文档）

#### 4.3.1 iOS

| 时钟源 | 时基 | 与其他源的关系 |
|---|---|---|
| `CMSampleBuffer.presentationTimeStamp` | mach 绝对时间（秒） | 与 `CMDeviceMotion.timestamp` / `CMGyroData.timestamp` / `ARFrame.timestamp` **同基**，可直接相减 |
| `CMGyroData.timestamp` / `CMAccelerometerData.timestamp` | mach 绝对时间（秒） | — |
| `ARFrame.timestamp` | mach 绝对时间（秒） | — |
| `CMDeviceMotion.timestamp` | mach 绝对时间（秒），但**含融合滞后 `τ_cm`** | 02 §3.3.1 S5：标定后残余 300 μs，未标定取 15 ms。**只用于航向参考，不用于预积分**（IOS-IMU-3） |

**对齐公式**

```
1. 曝光中心:  t_exp_center = t_PTS + exposureDuration/2 + τ_pipeline
   - t_PTS  : CMSampleBuffer.presentationTimeStamp
   - exposureDuration: 由 AVCaptureDevice 的当前设置 + 每帧 EXIF 推导（AVCaptureVideoDataOutput
     的 sample buffer 不带 EXIF；用 AVCapturePhotoOutput 的 metadata 或 AVCaptureDevice
     的 exposureDuration 近似，误差计入 σ_t）
   - τ_pipeline: 机型标定表查得（02 §3.7 S3），未标定取 15 ms
2. IMU 插值: 在 t_exp_center 处对陀螺/加计做分段线性插值（ω 用 slerp，02 §3.6.2 步骤 3）
3. 残差: r_t = t_exp_center - t_imu_interp
   |r_t| > 3σ_t  → E_SYNC_RESIDUAL_LARGE
   |r_t| > 10σ_t → E_SYNC_RESIDUAL_REJECT
4. session 原点: t_session = t_mach - β_c，β_c 由会话开始时的对齐流程解算
```

| 编号 | 规则 |
|---|---|
| IOS-TS-1 | iOS 侧**不需要**仿射拟合（02 §3.2 的 `α, β` 解算主要用于 Android 的 `SOURCE_SENSOR_CLOCK` / `SOURCE_UNKNOWN`）。iOS 直接 `α = 1`，`β` 仅做原点平移 |
| IOS-TS-2 | `τ_pipeline` 与 `τ_cm` 必须来自**机型标定表**（02 §3.9.4）。表缺失时用保守值（`τ_pipeline = 15 ms`、`τ_cm = 15 ms`）并在 `manifest.json` 标记 `calib.missing = true`，U-03 内联提示 `该机型未标定，精度可能下降` |

#### 4.3.2 Android

| 时钟源 | 时基 | 说明 |
|---|---|---|
| `Image.getTimestamp()` | `elapsedRealtimeNanos`（或 `SENSOR_TIMESTAMP`） | 与 `SensorEvent.timestamp` 同源 → 直接可比 |
| `SensorEvent.timestamp` | `elapsedRealtimeNanos` | — |
| `ImageReader` 的 `Image.getTimestamp()` | 与 `CameraCharacteristics.SENSOR_INFO_TIMESTAMP_SOURCE` 声明的源一致 | 若为 `SOURCE_UNKNOWN` → 仿射拟合 |
| `SystemClock.elapsedRealtimeNanos()` | `elapsedRealtimeNanos` | 相机时间戳不可用时的回落（`E_SYNC_CAM_TS_FALLBACK`） |
| `ARCore Frame.timestamp` | ns | ARCore 文档保证单调。基准与 `elapsedRealtimeNanos` 的关系**需在真机校验**（见下） |

**对齐公式**

```
1. 若 SENSOR_INFO_TIMESTAMP_SOURCE == SOURCE_REALTIME:
       α = 1, β = 0，t_camera 直接使用
   若 == SOURCE_SENSOR_CLOCK 或 SOURCE_UNKNOWN:
       用最小二乘拟合 α, β（02 §3.2.2），要求 |α - 1| < 1e-4，
       否则触发 E_SYNC_UNRELIABLE_CAM_TS 并拒用该时间戳
2. t_exp_center = t_camera + exposureDuration/2 + τ_pipeline
   exposureDuration 由 ImageReader 的 Image 不直接给出 →
   用 CaptureRequest 中实际下发的 SENSOR_EXPOSURE_TIME（手动模式下精确已知）
   或用 AE 模式下相邻帧的时间戳差近似（误差计入 σ_t）
3. IMU 采样按 SensorEvent.timestamp 排序，按 t_exp_center 切分区间做预积分
4. 与 ARCore 帧的配对（仅 ARCore 路径）:
   采集开始后的前 30 帧内，用 ARCore 帧与相机帧做一次时间戳配对统计，
   求出 median(Δt)。若 |Δt| > 5 ms，则以该 Δt 作为常量偏移修正；
   若 Δt 的标准差 > 2 ms，则把 ARCore 帧的位姿按最近邻（≤ 半个帧间隔）配对，
   并在 manifest.json 记录 arcore_time_offset_ns 与 arcore_time_jitter_ns
```

| 编号 | 规则 |
|---|---|
| AND-TS-1 | ARCore `Frame.timestamp` 的时基基准**不假设**。必须在探测阶段实测配对，得出偏移与抖动，写入 `manifest.json`。这是诚实处理：不靠文档猜 |
| AND-TS-2 | `SOURCE_UNKNOWN` 时按 02 §3.2 做仿射拟合，**不做**「直接用主机时钟」的偷懒（那会把相机与 IMU 的漂移全部算进误差预算） |
| AND-TS-3 | 两端的最终误差预算必须落在 02 §3.7 的表内；超出即为实现缺陷，不得靠放宽阈值掩盖 |

### 4.4 进程被杀后的会话恢复（索引文件完整性检查）

**统一入口**：App 启动时扫描 `sessions/*/manifest.json`。

| 步骤 | 检查 | 处置 |
|---|---|---|
| 1 | `manifest.json` 的 `schema_version` 与当前版本 | 不匹配 → 标记 `unsupported_schema`，不加载，U-01 该行显示 `数据版本不兼容` |
| 2 | `state` 字段 | `recording` → 标记 `interrupted`；`cancelling` → 标记 `interrupted` 并执行目录清理；`completed` → 正常加载；`cancelled` → 删除目录 |
| 3 | `checksums["index.bin"]` 与实际 `index.bin` 的 SHA-256 | 不匹配 → 02 §5.9：截断 `index.bin` 到最后一个完整记录，**保留**已有数据供续算，记录 `E_DISK_FULL` 无关的 `W_SESSION_TRUNCATED` |
| 4 | `index.bin` 的 `frame_id` 连续性 | 断裂 → 在断裂点截断，记录 `W_SESSION_TRUNCATED` |
| 5 | `index.bin` 每条记录的 `rgb_offset + rgb_size ≤ frames.bin` 当前长度 | 越界的记录被丢弃（不指向不存在的字节） |
| 6 | `resume_cursor.last_keyframe_frame_id` 与 `index.bin` 的实际最大关键帧 id 一致 | 不一致 → 以 `index.bin` 实际值覆盖 `resume_cursor`，记录 `W_SESSION_CURSOR_FIXED` |
| 7 | 重建阶段的检查点文件 `recon_cache/<session_id>/checkpoint.json` | 存在且 `stage_status` 与当前阶段匹配 → 允许「从检查点续跑」；不匹配 → 从头重跑 |

| 编号 | 规则 |
|---|---|
| REC-1 | **不静默丢弃数据**。任何截断都在 U-01 的该项目行下方显示一行 `footnote` `txt.warning` `部分数据未完整保存，已保留可用部分` |
| REC-2 | `interrupted` 的会话在 U-01 显示 `已中断，可继续`，点「继续」进入 `Reviewing` 状态（自检清单仍然执行） |
| REC-3 | 检查点恢复**不跳过校验**：恢复后重跑导出前校验（06 §4.1 的 V1–V17） |
| REC-4 | 「继续」动作必须显式由用户触发，不自动开始重建（避免用户不知情时消耗大量电与存储） |
| REC-5 | 连续两次恢复失败 → 标记该会话 `broken`，U-01 显示 `数据已损坏，无法恢复`，提供「删除会话」 |

### 5.2 降级决策表

**核心约束（00 R-PREC-4 / R-PREC-5）：只允许降并发度、批大小、分块策略。不得降体素分辨率、特征点数、BA 迭代数、匹配阈值、泊松深度。**

| 触发条件 | 允许的处置（白名单） | 禁止的处置（黑名单） | 用户提示 |
|---|---|---|---|
| iOS `.serious` / Android `SEVERE` | `perf_thread_pool_size` × 0.5；`perf_gpu_batch_size` × 0.5；`perf_max_concurrent_tasks` × 0.5；`rgbd_max_blocks_in_memory` × 0.5 | 任何精度阈值 | `设备温度较高，已降低重建速度` |
| iOS `.critical` / Android `CRITICAL` | 上述 × 0.25；暂停采集（`Capturing` → `Previewing`，已采帧保留） | 任何精度阈值 | `设备温度过高，已暂停采集` |
| iOS `.fair` / Android `MODERATE` | `perf_thread_pool_size` × 0.75 | 任何精度阈值 | 不提示（避免打扰） |
| iOS 低电量模式 / Android 省电模式 | `perf_gpu_batch_size` × 0.75；`perf_max_concurrent_tasks` × 0.75 | 任何精度阈值；**不**关闭 GPU（关掉 GPU 会让泊松慢 10 倍，反而延长发热时间） | `已启用省电模式，重建速度降低` |
| 电量 < 15% 且未插电 | 采集阶段提示一次 | — | `电量较低，建议插电后再进行高精度重建` |
| 电量 < 15% 且未插电 + 高精度档 | 建议降档（用户确认） | 不自动降档 | `高精度重建耗电量较大，建议插电使用` |
| `cap_thermal_throttle_threshold_c` 用户阈值 | 与系统温度二选一，取更严格者触发降级 | — | 同上 |
| 采集期降级 | 同上 | — | `设备温度较高，已降低采集帧率`（仅降 `cap_frame_rate` 的**上限**，不降分辨率） |

| 编号 | 规则 |
|---|---|
| TH-1 | 系统温度触发的降级只改 `perf_*` 与 `rgbd_max_blocks_in_memory`（08 §1 G11 白名单）。**绝不**改 `rgbd_tsdf_voxel_size`、`mesh_poisson_depth`、`sfm_feature_count`、`vio_feature_count`、`sfm_ba_max_iterations`、`sfm_ransac_max_iterations`、`mvs_patch_size`、`mvs_num_views` |
| TH-2 | 温度降级是**临时的**：温度回落后自动恢复并发度（带 60 s 迟滞，避免抖动） |
| TH-3 | 每次温度降级在 U-06 显示降级提示行（09 §3.6.2），并写入 `recon_mesh_info.json` 的 `degradations` 数组，注明 `reason = "thermal_throttle"` |
| TH-4 | `cap_thermal_throttle_threshold_c`（用户可调，默认 42 / 45 / 40）只影响**本产品自己**的阈值；系统温度 API 的阈值不可调，作为附加约束叠加。两者取更严格者 |
| TH-5 | 电池温度高但 SoC 温度正常时（如充电中），以系统 API 为准（SoC 温度才是算力瓶颈） |

### 5.3 内存保护（承接 13 文档）

| 平台 | 触发回调 | 处置顺序（与 13 文档一致） |
|---|---|---|
| iOS | `UIApplication.didReceiveMemoryWarningNotification` | ① 释放帧环形队列中未处理的帧 ② 释放 `perf_cache_dir` 的非活跃部分 ③ `rgbd_max_blocks_in_memory` × 0.5 ④ `perf_memory_pool_prealloc_mb` × 0.5 ⑤ `perf_gpu_batch_size` × 0.5 |
| iOS | `UIApplicationExtensions` 下的 `UIApplication.didReceiveMemoryWarning` 在 scene 级别 | 同上 |
| Android | `Activity.onTrimMemory(level)`，`TRIM_MEMORY_RUNNING_LOW` / `TRIM_MEMORY_RUNNING_CRITICAL` | 同上 |
| Android | `ComponentCallbacks2.onTrimMemory(TRIM_MEMORY_COMPLETE)` | 写检查点后释放全部非必要缓存 |
| Android | `ActivityManager.getMemoryInfo()` 的 `lowMemory` 标志 | 同 `TRIM_MEMORY_RUNNING_LOW` |

| 编号 | 规则 |
|---|---|
| MEM-1 | 内存保护**禁止**通过丢弃已入库的关键帧或降低精度阈值实现（00 R-PREC-5） |
| MEM-2 | 每次内存保护在 U-06 显示 `内存紧张，缓存已写入磁盘`（09 §3.6.2） |
| MEM-3 | 内存保护动作全部落在 `perf_*`（白名单） |
| MEM-4 | iOS 的 `didReceiveMemoryWarning` 可能**随时**到来。因此重建期间的所有大块内存（泊松八叉树、UV 图集、烘焙缓冲）必须**分块分配 + 落盘 + 流式**（13 文档），不能在内存警告时"临时申请更多内存" |

## 6. 平台能力差异的诚实汇总（跨端不一致项）

| 能力 | iOS | Android | 处置 |
|---|---|---|---|
| 硬件深度 | 仅 LiDAR（`sceneDepth`，厘米级） | 硬件 ToF（`DEPTH16`，毫米级）或 ARCore 运动深度 | 已由 00 §4.2 的双源融合方案处理 |
| 最高 RGB 分辨率 | 4K（AVFoundation 后端）/ 1920×1440（ARKit 后端） | 由 `SCALER_STREAM_CONFIGURATION_MAP` 决定，通常 4K 或更高（Camera2 直接路径） | — |
| 手动曝光时间 / ISO | 精确（`exposureDuration` / `ISO`） | 精确（`SENSOR_EXPOSURE_TIME` / `SENSOR_SENSITIVITY`），但需实测 HAL 遵从性 | AND-AE-1 |
| 手动白平衡色温 | 可设 `whiteBalanceTemperature` | **不可设**，只能锁定当前增益 | U-02 明示；`cap_white_balance_kelvin` 在 Android 置灰 |
| 手动对焦距离 | 可设 `lensPosition` / `focusDistance` | 可设 `LENS_FOCUS_DISTANCE` | — |
| 高分辨率单帧抓取 | `AVCapturePhotoOutput`（与帧流同会话） | Camera2 直接路径下无等价能力；降级路径用 `ImageCapture` | AND-PH-1：定点引导模式在 Android 降级，U-02 明示 |
| 帧流与深度同会话 | 不可（相机独占） | **可**（`ImageReader` YUV + `ImageReader` DEPTH16） | Android 在 RGBD 分支上更优 |
| 位置跟踪先验 | ARKit | ARCore（仅 ARCore 独占路径） | 对称设计 |
| 后台重建 | 不支持 | 支持（`dataSync` 前台服务） | AND-L-1 |
| IMU 原始采样 | `CMGyro` + `CMAccelerometer` | `TYPE_GYROSCOPE` + `TYPE_ACCELEROMETER`，**batching 关闭** | 结构一致（IOS-IMU-2、AND-IMU-1） |
| 精度对齐 | 直接（无拟合） | `SOURCE_REALTIME` 直接；否则仿射拟合 | AND-TS-2 |
| 相机+IMU 融合滞后 | `τ_cm` 15 ms（未标定） | 无融合滞后（原始传感器） | 02 §3.7 S5 |
