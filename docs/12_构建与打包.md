## 1. 构建系统总览

### 1.1 三平台与统一入口

```
                     ┌──────────────────────────────────────┐
                     │        顶层 CMakeLists.txt           │
                     │  （选项聚合 + target 定义 + 依赖登记） │
                     └───────────────┬──────────────────────┘
                                     │
        ┌────────────────────────────┼────────────────────────────┐
        │                            │                            │
   ┌────▼─────┐              ┌───────▼────────┐          ┌────────▼────────┐
   │ Android  │              │     iOS        │          │  桌面验证机     │
   │ Gradle   │              │   Xcode        │          │  CMake 直出     │
   │ external │              │  (CMake 生成)  │          │                 │
   │ NativeBuild│             │               │          │                 │
   └────┬─────┘              └───────┬────────┘          └────────┬────────┘
        │                            │                            │
        ▼                            ▼                            ▼
  app-release.aab            Recon.xcframework            recon_cli
  (+ 各 ABI 的 .so)          (+ Recon.app)                (+ 单元测试)
```

| 项 | 规格 |
|---|---|
| CMake 最低版本 | **3.24.0**（需要 `CMAKE_OSX_SYSROOT` 多架构、`--preset` 稳定支持、`native` toolchain 透传） |
| C++ 标准 | **C++17**（`CMAKE_CXX_STANDARD 17`），不使用 C++20 特性以保证 NDK r28 / Xcode 15 双端一致 |
| 编译器 | Android：NDK r28 clang 17；iOS：Apple clang 15（Xcode 15.4）；桌面：GCC 11+ / Clang 14+ |
| 编译选项 | `-ffast-math` **禁止**；`-O3`（Release）；`-fno-omit-frame-pointer`（Release 保留，利于崩溃栈）；`-fvisibility=hidden` + 显式 `RECON_API` 导出 |
| 警告策略 | `-Wall -Wextra -Werror`（自研代码）；`third_party/` 关闭 `-Werror`，其警告不阻断 |
| 确定性构建 | 固定 `SOURCE_DATE_EPOCH`；`ar` 使用 `D`（deterministic）模式；产物中不嵌入构建绝对路径（`-ffile-prefix-map=${CMAKE_SOURCE_DIR}=.`） |

**分层依赖图（禁止反向依赖）**

```
recon_shaders_common  (INTERFACE, 无依赖)
        ▲
recon_shaders_vulkan / recon_shaders_metal
        ▲
recon_solver        (Eigen + Ceres + PoseLib + PoissonRecon + xatlas + jsoncpp)
        ▲
recon_vision        (OpenCV裁剪 + COLMAP feature/sfm 子集 + FLANN + nanoflann + DBoW2 + basalt)
        ▲
recon_core          (自研 L4/L5)
        ▲
recon_core_cabi     (对外唯一 C ABI)
        ▲
recon_platform_ios / recon_platform_android
```

> **为什么这样分**：`recon_core` 必须能单独链进桌面 `recon_cli`（用于黄金回归，见 §5），而桌面无 GPU 图形栈，因此着色器层必须下沉到独立 target，不能被 `recon_core` 直接依赖。

| iOS 本地化文案 | `Recon.app/locales/<locale>.json`（20 个） | App 包内 `locales/` 目录 | **必须是 folder reference**（`type: folder`）：`Localization.swift` 按 `subdirectory: "locales"` 查找。默认 `group` 会把它**展平到包根** → 20 个 locale 全部静默加载不到（见 §4.2 与 G17、P-8） |

> ⚠️ **库形态与平台强相关，不得一刀切**（第四十三轮实测，见 docs/14 缺口 S 的缺口 A）。
> `recon_core` / `recon_platform_android` 在 **Android 下是 `SHARED`**（产出上表的 `.so`），
> 在 **桌面与 iOS 下是 `STATIC`**（产出 `.a`）。原因：
> · **Android 必须 `SHARED`** —— `ReconApplication.kt` 用 `System.loadLibrary(...)`
>   加载，而 `loadLibrary` 只认 `.so` 文件名；`STATIC` 下**根本没有可加载的文件**，
>   真机启动第一步即 `UnsatisfiedLinkError`。此前全仓库 target 皆为 `STATIC`，
>   而这一缺口在编译期与全部静态闸门下**全绿**（静态库照样编、照样链接）。
> · **桌面必须 `STATIC`** —— `recon_cli` 与 28 个单测直接静态链接；
> · **iOS 必须 `STATIC`** —— §4.3 的打包链是 `libtool -static` 合并三个 `.a`
>   再用 `xcodebuild -create-xcframework -library`，该选项**只接受静态库**。
>
> 实现落点：根 `CMakeLists.txt` 的 `RECON_CORE_LIB_TYPE` 条件变量。
> 判据落点：`tools/check_android_contract.py` 的 **G-AND-2**（每个
> `loadLibrary("X")` 对应的 target 必须是 `SHARED`/`MODULE`）。

**`recon_vision` 与 `recon_solver` 的拆分理由**

> **⚠️ 实测口径修正（第四十二轮）：本拆分为「目标态设计」，尚未实现。**
> 经全仓库核对：根 `CMakeLists.txt` 把所有 `core/src/**` 收进**单一**
> `recon_core`，`recon_vision` / `recon_solver` **两个 target 不存在**
> （`grep -rn 'recon_vision\|recon_solver' --include='CMakeLists.txt'` 零命中）。
> 因此下述理由与 §3.7 体积表应按**目标态**读，而不是现状。分歧已登记于
> `docs/14_验收测试.md` §5.1.3 缺口 R，**不擅自裁决**（拆分与否属架构决策：
> 静态链接下 §1.4 自陈「无按需加载收益」，且当前所有 `.so` 体积均在单库内，
> 拆分收益主要在体积归因与符号边界）。

| 理由 | 说明 |
|---|---|
| 符号隔离 | COLMAP 与 Ceres 均有 `namespace colmap` / `ceres` 隔离，但两者都依赖 Eigen 的模板实例化；分开后 `librecon_solver.so` 集中承载 Eigen 实例，避免跨 .so 的模板 ODR 问题 |
| 按需加载 | iOS 上 `recon_vision` 仅在有深度分支时使用；但当前版本**全部链接进 App**（静态链接下无按需加载收益），此拆分的实际价值在于**体积可归因**与**符号可见性可控** |
| 与 §3.7 体积表对应 | 拆分后每个 .so 的体积可单独度量与单独做 16 KB 对齐检查 |

> **共享库拆分带来的额外约束**：所有导出符号必须用 `__attribute__((visibility("default")))` 显式标注（`RECON_API` 宏），未标注符号一律隐藏。跨 .so 调用一律经 `recon_c_api.h`（00 §7.1），**禁止** `core/` 内部头文件跨 target 暴露。

### 2.2 `VENDOR.yaml` 规范（每个依赖目录一份）

```yaml
# third_party/eigen/VENDOR.yaml
name: eigen
upstream_url: https://gitlab.com/libeigen/eigen.git
ref_type: tag            # tag | commit
ref: 3.4.0
commit: 8e4564e2c7b6f4b1a1f1e0f0e0a0b0c0d0e0f00   # 解析到的完整 SHA（40 hex）
license: MPL-2.0
license_spdx: MPL-2.0
vendored_subtree: [Eigen/]                 # 只 vendor 的子树
vendored_sha256: 9f1c4b8d2e6a70c3f5b9d8e1a4c7f0b2d5e8a3c6f1b4d7e0a3c6f9b2d5e8a1   # 子树内容归一化后的 sha256
modified: false                           # 是否对上游源码做过修改；true 时 PATCHES.md 必须非空
patches_file: PATCHES.md
```

| 字段 | 校验方 | 规则 |
|---|---|---|
| `ref` + `commit` | `tools/license_scan.py` | `commit` 必须是 40 位十六进制；tag 与 commit 必须一致（构建期校验：构建容器内不联网，因此由 vendor 阶段离线校验并把结果写入本文件） |
| `vendored_subtree` | `tools/license_scan.py` | 必须与目录实际内容一致；出现未登记文件即失败（防止夹带 GPL 源码） |
| `vendored_sha256` | `tools/license_scan.py` | 任何对内联源码的改动都会改变该摘要 → 强制走 `PATCHES.md` 流程 |
| `modified` | `tools/license_scan.py` | `true` 且 `PATCHES.md` 缺失或未覆盖全部改动文件 → 失败 |

### 2.5 Eigen 边界项 B-1 的处理方案

**事实认定（00 §8.5）**：Eigen 自 3.3 起为 **MPL-2.0**（Mozilla Public License 2.0），**文件级 copyleft，非传染型**。Ceres Solver（BSD-3）硬依赖 Eigen。Eigen **不在**用户指定的 MIT / Apache-2.0 / BSD 三类白名单内，单列为「白名单边界项 **B-1**」。

**合规处置（四条同时成立才算合规）**

| 编号 | 处置 | 落地方式 | CI 校验 |
|---|---|---|---|
| B1-1 | **静态链接** | Eigen 为纯头文件库（无 .cpp、无导出符号表），被 `ceres` / `recon_core` / `recon_solver` 静态吸收，最终进入 `.a` / `.so` / App 可执行文件 | §2.6 阶段 4：产物中 `nm -u` 不得出现 `Eigen` 相关未定义符号；`nm -D --defined-only` 不得出现 `Eigen3` 命名空间的动态导出符号；`third_party/eigen/` 下不得存在 `.cpp` / `.c` 文件 |
| B1-2 | **不修改 Eigen 源文件** | `third_party/eigen/VENDOR.yaml` 的 `modified: false`；`vendored_sha256` 锁定 | `tools/license_scan.py` 校验 `modified` 与摘要；不一致即失败 |
| B1-3 | **保留完整版权声明与 LICENSE** | `third_party/eigen/COPYING.MPL2` 与 `COPYING.README` 原样保留；`cmake/Licenses.cmake` 把二者全文嵌入 `THIRD_PARTY_LICENSES.txt` | 校验 `COPYING.MPL2` 的 sha256 等于上游 `3.4.0` 的值（记录于 `cmake/Licenses.cmake`） |
| B1-4 | **法务签字** | `docs/10_许可与合规.md` §B-1 记录签字人、日期、结论 | CI 检查该章节存在签字行且非空 |

**MPL-2.0 的具体义务与本项目的对应**

| MPL-2.0 条款 | 义务 | 本项目处置 |
|---|---|---|
| §3.1 | 保留版权声明、免责声明、许可证全文、指向 MPL-2.0 的指针 | `THIRD_PARTY_LICENSES.txt` 全文收录（§2.7） |
| §3.2 | 不得以「附加条款」限制 MPL 文件的行使 | 不修改文件 → 天然满足 |
| §3.3 | 对 MPL 文件的修改需公开源码 | **不修改** → 该条款不触发 |
| §3.4 | MPL 文件以「原样」方式单独分发 | 静态链接进更大作品属「 Larger Work」，不影响其他部分许可 | 产物是自研闭源代码 + 静态链接，与 MPL-2.0 §1.10 的 Larger Work 条款一致 |

> **诚实披露**：静态链接 MPL-2.0 库进入 App 二进制是常见做法且法律风险低，但**存在被质疑为「Modified Version」的空间**。因此 B1-2 的「不修改源文件」不是形式要求，而是本项目消除该风险的**唯一手段**。任何对 Eigen 的定制必须放在 `core/` 侧的包装层（`core/util/eigen_compat.hpp`），不得 patch Eigen 本身。

**备选方案（不推荐，仅记录）**：自研稀疏线性代数 + 自研 BA。工作量估算 ≥ 12 人日，且需重新标定 05 §4.7 的全部求解器配置与收敛判据，精度回归风险显著高于接受 B-1。**结论：走 B-1，需法务签字。**

```bash
    --root third_party \
    --registry cmake/ThirdParty.cmake \
    --licenses-cmake cmake/Licenses.cmake \
    --output build/license_scan_report.json \
    --fail-on-violation

# 【独立 job】只做四表一致性（不依赖编译，30 秒内出结果）
python3 tools/license_scan.py \
    --registry cmake/ThirdParty.cmake --check-registry

# 【发布闸门】校验已生成的许可清单与 third_party 逐字节一致
python3 tools/license_scan.py \
    --licenses-cmake cmake/Licenses.cmake \
    --licenses-text build/THIRD_PARTY_LICENSES.txt \
    --verify-licenses-cmake

# 【发布闸门前置】若尚无清单，先生成（configure 阶段会自动生成，此处为独立生成）
cmake -P cmake/Licenses.cmake -- build/THIRD_PARTY_LICENSES.txt
```

| 参数 | 必填 | 说明 |
|---|---|---|
| `--root` | 是 | 待扫描目录（`third_party`）；`--third-party` 为其历史别名 |
| `--registry` | 是 | 依赖登记真源（`cmake/ThirdParty.cmake`）。给出即**顺带**做四表一致性 |
| `--licenses-cmake` | 是 | 许可清单生成脚本（`cmake/Licenses.cmake`） |
| `--output` / `--json` | 否 | JSON 报告输出路径（CI 归档为构建产物） |
| `--fail-on-violation` | 否 | 检测到违规即非零退出（本工具默认行为，保留该开关以兼容 CI 写法） |
| `--check-registry` | 否 | **只**做四表登记一致性校验（见下「模式 A」） |
| `--verify-licenses-cmake` | 否 | **只**校验已生成的清单与 `third_party/` 逐字节一致（见下「模式 B」） |
| `--licenses-text` | 否 | 待校验清单路径；缺省按 `<build>/THIRD_PARTY_LICENSES.txt` 自动探测 |
| `--scan-artifact` | 否 | 额外扫描构建产物中的禁止符号（可重复，对应 §4.4–4.6） |
| `--no-build-only-in-release` | 否 | 校验 `build_only=true` 的依赖未进入 Release 产物 |

**三种运行模式**（`--check-registry` / `--verify-licenses-cmake` 互斥，均优先于全量扫描）：

| 模式 | 触发 | 输出 | 退出码 |
|---|---|---|---|
| A · 四表一致性 | `--check-registry` | 真源 ↔ docs/10 §2.1 ↔ docs/12 §2.1 ↔ `third_party/` 目录集合 逐项比对 | `0` 一致 / `3` 不一致 |
| B · 清单逐字节 | `--verify-licenses-cmake` | 已生成清单中的每个许可文件正文 ↔ `third_party/<dep>/<file>` 原始字节 | `0` 一致 / `2` 不一致 |
| C · 全量扫描 | 默认 | §2.6.2 五阶段 | `0` / `2` 违规 / `3` 登记不一致 |

**退出码**：`0` 通过；`1` 用法错误 / 必填参数缺失；`2` **检测到许可违规**（构建失败）；`3` 登记不一致（`VENDOR.yaml` / 登记表 / 文档表不符）。

#### 2.6.2 检测逻辑（实现级规格）

扫描器按以下五个阶段执行，**任一阶段命中违规即整体失败**：

**阶段 1 — 依赖目录枚举**

| 项 | 规则 |
|---|---|
| 1.1 | 遍历 `--root` 的一级子目录，每个子目录名必须与 `--registry` 中登记的 `name` 一一对应，多一个或少一个即退出码 3 |
| 1.2 | 每个依赖目录必须存在 `VENDOR.yaml`；`VENDOR.yaml` 的 `name` 必须与目录名相同 |
| 1.3 | 每个依赖目录必须存在**至少一个**许可文件。许可文件名匹配（大小写不敏感）：`LICENSE`、`LICENSE.*`、`LICENCE`、`LICENCE.*`、`COPYING`、`COPYING.*`、`NOTICE`、`NOTICE.*`、`LICENSE.txt`、`LICENSE.md` |

**阶段 2 — 许可文件内容扫描（黑名单关键词）**

对每个许可文件全文做**归一化**后扫描：

| 步骤 | 规则 |
|---|---|
| 2.1 归一化 | 去 UTF-8 BOM；统一换行为 `\n`；折叠连续空白为单空格；去除行首行尾空白；保留大小写（关键词匹配用**大小写不敏感**） |
| 2.2 强命中关键词 | 归一化文本中出现下列任一字符串 → **违规**：`GNU GENERAL PUBLIC LICENSE`、`GNU AFFERO GENERAL PUBLIC LICENSE`、`GNU LESSER GENERAL PUBLIC LICENSE`、`GNU LIBRARY GENERAL PUBLIC LICENSE`、`GPL-3.0`、`GPL-2.0`、`GPLv2`、`GPLv3`、`AGPL-3.0`、`AGPLv3`、`LGPL-3.0`、`LGPLv2`、`LGPLv3`、`Server Side Public License`、`SSPL`、`Business Source License`、`Elastic License`、`Commons Clause`、`CC-BY-NC` |
| 2.3 弱命中判定 | 若文本出现 `GNU General Public License` 但同一文件内同时出现 `MIT License` / `Apache License` / `BSD` / `MPL` 且 GPL 段落在**双许可声明**上下文中（形如 `either version X of the License, or (at your option) any later version`），记为 `warning`，不失败 |
| 2.4 传染性判定 | 命中 2.2 后，还需检查被命中的许可文件**是否属于被实际编译的源码子树**。若该文件位于 `VENDOR.yaml` 的 `vendored_subtree` 覆盖范围内 → **违规（退出码 2）**；若位于未编译的 `docs/`、`examples/`、`test/` 目录 → 记 `warning` 并要求在 `third_party/<name>/VENDOR.yaml` 的 `excluded_subtrees` 中显式登记该路径 |
| 2.5 MPL 例外 | `MPL-2.0` **不在**黑名单内（MPL-2.0 是文件级 copyleft，已由 B1-1~B1-4 处置）。但扫描器会额外校验：所有 `MPL-2.0` 依赖必须登记在 `cmake/ThirdParty.cmake` 的 `[boundary_items]` 段并带 `requires_legal_signoff = true` |

**阶段 3 — 登记一致性**

| 检查 | 违规条件 | 严重度 |
|---|---|---|
| 3.1 | `VENDOR.yaml` 的 `license_spdx` 与 `cmake/ThirdParty.cmake` 登记的 `license_spdx` 不一致。**期望值取自登记真源**（`--registry`），不再依赖脚本内硬编码表 | error |
| 3.2 | `VENDOR.yaml` 的 `ref` / `commit` 为空，或 `commit` 不是 40 位十六进制 | error（vendor 完成前为 warning） |
| 3.3 | `vendored_subtree` 声明的路径在目录中不存在 | error（vendor 完成前为 warning） |
| 3.4 | 依赖目录中存在**未被 `vendored_subtree` 覆盖**的 `.c/.cpp/.h/.hpp/.cc/.cu/.metal/.comp` 源文件 → 违规（防止夹带未审查的第三方源码） | error |
| 3.5 | `modified: true` 但 `PATCHES.md` 不存在，或 `PATCHES.md` 中未提及所有被改动的文件 | error |
| 3.6 | `--no-build-only-in-release` 模式下，标记 `build_only=true` 的依赖出现在 Release 产物依赖图中（通过 `nm`/`readelf` 检查符号来源） | error |
| 3.7 | **G6 参数契约**：`python tools/gen_g6_params.py --check` 退出码非 0。该命令做两层自包含校验：(a) §7.1 表自身一致性（键名合法、类型合法、默认值/档位值均落在合法区间）；(b) `tests/unit/g6_contract.inc` 与当前 §7.1 同步（内容逐字节比对，不依赖 git）。**原因**：G6 的 78 行规格由 §7.1 生成，若仅改文档不重跑生成脚本，注册表将静默漂移（08 §5.1.1）。**验证过敏感度**：改 §7.1 任一默认值不重生成 → 退出码 1 | error |
| 3.8 | **四表一致**（`--check-registry`）：登记真源 ↔ `docs/10 §2.1` ↔ `docs/12 §2.1` ↔ `third_party/` 目录集合。文档表解析失败记 info（不误报）；不一致记 error；未 vendor 的正式依赖记 warning | error / warning |
| 3.9 | **边界项法务签字**：`RECON_THIRD_PARTY_BOUNDARY_ITEMS` 中 `requires_legal_signoff=true` 的依赖，其 `third_party/<name>/VENDOR.yaml` 必须含 `legal_approval` 行。**注意**：`VENDOR.yaml` 是**每个依赖目录一份**（§2.2），不是 `third_party/` 根级单文件 | error（VENDOR.yaml 缺失时为 warning） |
| 3.10 | **黑名单不得进入登记真源**：以 `FORBIDDEN_REGISTRY_TOKENS`（GPL/AGPL/LGPL/FIPL 族、cgal、freeimage、siftgpu、lsd、sspl、commons clause、elastic/business source license、cc-by-nc、qt5/qt6、onnxruntime、faiss）扫描 `cmake/ThirdParty.cmake` **全文**（四个登记段全覆盖）。命中即违规。对应 docs/10 §6 检查项 3、docs/00 §8.4 的 CI 声明 | error |

> **空门修复记录（2026-10-31）**：3.1/3.9 原先存在两处**永不触发**的检查：(a) 3.1 用脚本内硬编码 `KNOWN_LICENSES` 而非登记真源 —— 违反「同一逻辑写两遍必然漂移」；(b) 3.9 只找 `third_party/VENDOR.yaml`（根级），而 §2.2 规定的是每依赖一份，故该检查恒不命中。两者均已修正，并用注入测试双向验证（缺 `legal_approval` → error；补上 → 0 错）。

**阶段 4 — 产物侧交叉校验**

| 检查 | 命令 | 违规条件 |
|---|---|---|
| 4.1 白名单许可 | `tools/license_scan.py --scan-artifact <so/a>` | 产物中出现 `gomp` / `omp` / `gcc_` 之外的编译器运行时**不作为许可问题**，但出现 `libCGAL` / `libgdal` / `Qt5Core` / `Qt6Core` / `onnxruntime` / `libfaiss` 的符号或字符串 → 违规 |
| 4.2 CGAL 残留 | `nm -C --defined-only <artifact> \| grep -i cgal` | 命中即违规（对应 §2.4 的 `CGAL_ENABLED=OFF` 生效性验证） |
| 4.3 网络库残留 | `readelf -d <so> \| grep NEEDED` | 出现 `libssl` / `libcrypto` / `libcurl` → 违规（与 §7.4 联动） |
| 4.4 FreeImage 残留（X-1） | `nm -C --defined-only <artifact> \| grep -iE 'freeimage'`；且 `third_party/colmap/src/colmap/sensor/` 下不得存在 `bitmap.{h,cc}` | 命中即违规（对应 §2.4.1 X-1：`FreeImage` = FIPL/GPL 双许可） |
| 4.5 LSD 残留（X-2） | `nm -C --defined-only <artifact> \| grep -iE 'lsd_'`；且 `third_party/colmap/src/thirdparty/LSD` 目录不得存在 | 命中即违规（对应 §2.4.1 X-2：`LSD` = AGPL-3+） |
| 4.6 SiftGPU 残留（X-3） | `nm -C --defined-only <artifact> \| grep -iE 'siftgpu'`；且 `third_party/colmap/src/thirdparty/` 目录不得存在（整棵子树不 vendor） | 命中即违规（对应 §2.4.1 X-3：`SiftGPU` = UNC 非商业许可） |

#### 2.6.3 门禁规则（CI 中生效）

| 规则 | 内容 |
|---|---|
| L-1 | `tools/license_scan.py --fail-on-violation` 的退出码必须为 0。非 0 → **整个流水线失败**，不进入编译任务 |
| L-2 | 该任务为**独立 job**，不依赖编译任务（`needs: []`），因此许可问题会在 30 秒内暴露，而不是等编译 20 分钟后失败 |
| L-3 | 扫描报告 `build/license_scan_report.json` 必须作为构建产物归档，保留期 ≥ 2 年（合规举证） |
| L-4 | 任何「新增依赖 / 升级依赖 / 改 license_spdx」的 PR，扫描器必须检出差异并强制人工复核（CODEOWNERS 指向法务） |
| L-5 | 扫描器自身（`tools/license_scan.py`）的匹配表**不得**被扫描器自身拦截（自引用豁免），豁免以 `# license-scan: self-exempt` 注释声明，扫描器只豁免**注释所在的匹配表数据行**，不豁免其他文件 |
| L-6 | 豁免机制本身受控：任何 `excluded_subtrees` 登记项必须在 `cmake/ThirdParty.cmake` 中有对应条目并附法务签字引用；扫描器校验条目数 ≤ 3（防止用豁免淹没扫描） |

### 2.7 许可清单生成（`cmake/Licenses.cmake`）

| 项 | 规格 |
|---|---|
| 产物名 | `THIRD_PARTY_LICENSES.txt` |
| 生成时机 | `configure` 阶段（**不依赖编译**）。`include(cmake/Licenses.cmake)` 即触发，产物落在 `${CMAKE_BINARY_DIR}`；亦可 `cmake -P cmake/Licenses.cmake -- <out>` 独立生成，或 `cmake --build <dir> --target licenses_manifest` 重生成 |
| **数据来源** | `include(cmake/ThirdParty.cmake)` —— 本文件**不得自带**依赖列表。一旦在 `Licenses.cmake` 内出现 `\|` 分隔的登记记录，`--check-registry` 直接判违规（防止「同一逻辑写两遍必然漂移」） |
| 内容顺序 | 按依赖在 `cmake/ThirdParty.cmake` 中的登记顺序，依赖内部按文件名字典序 |
| 每个依赖的条目格式 | ```\n===== <name> =====\n<license_spdx>\nUpstream: <upstream_url>\nRef: <ref> (<commit>)\nSubtree: <vendored_subtree>\n--- <file> ---\n<file 全文>\n``` |
| **尚未 vendor 的依赖** | 只输出头部与元信息，**不伪造**任何许可全文；文件末尾汇总到「尚未 vendor 的依赖」区；`configure` 阶段发 WARNING。发布构建该区必须为空 |
| 特殊处理 | Eigen 必须额外包含 `COPYING.MPL2` 与 `COPYING.README` **全文**（B1-3）；OpenCV 必须包含其 `LICENSE` 全文（其中已含 `3rdparty` 各库的声明） |
| 换行归一化 | 生成端把 CRLF/CR 统一为 LF，保证 Linux CI 与 Windows 本地产物**逐字节相同** |
| 嵌入位置 | iOS：`Recon.app/THIRD_PARTY_LICENSES.txt`（**包根**，见下方警示）；Android：`assets/THIRD_PARTY_LICENSES.txt`；桌面：`recon_cli` 同目录（由 `install(FILES ... COMPONENT licenses)` 按平台选目标，见 §1 平台变量） |

> ⚠️ **iOS 是扁平 bundle，没有 `Contents/` 这一层**（macOS 才有 `MyApp.app/Contents/Resources/`）。
> 本表原先把许可清单的 iOS 落位写进了 `Contents/Resources/` **这一不存在的层级** —— 那是**错误**的：
> `cmake/Licenses.cmake` 的 `RECON_LICENSES_EMBED_DEST` 实为 `Recon.app`（包根）。
> 该漂移 2026-11-01 由 **G15-d** 的文档面交叉对账抓出（原先 G15 只守代码侧三处，
> 文档写错无人看管 —— 与 G15 初建时「代码写错、文档跟着错」是同一类**双事实来源**问题，
> 只是方向相反）。与 metallib 落位（MT-1）、locale 展平（G17）同属
> 「编译期全绿、运行期加载不到」的静默失效族。
| UI 入口 | 09 文档的「关于 / 开源许可」页面必须能展示该文件全文（不可折叠隐藏，不可只显示链接） |
| CI 校验 | `tools/license_scan.py --verify-licenses-cmake` 确认**已生成的**清单与 `third_party/` 中的许可文件**逐字节一致** |

> **⚠️ 校验语义（重要的实现约束）**：`--verify-licenses-cmake` 校验的是**磁盘上已存在的那份清单**（`--licenses-text`，缺省自动探测构建目录），**不得**在每次校验时当场重新生成再比对 —— 那会构成自证循环：新清单必然等于新源文件，篡改源文件也永远「通过」（假阴性 100%）。正确语义是「清单先于源文件变动而生成；源文件一旦变动而未重生成清单，本校验即报红」。此点已用注入测试双向验证（篡改 1 字节 → 退出码 2；还原并重生成 → 退出码 0）。

| 步 | 动作 | 验证 |
|---|---|---|
| 1 | 选定上游 tag / commit，更新 `third_party/<name>/VENDOR.yaml` | — |

| 7 | 更新 `docs/10_许可与合规.md` 与本表 §2.1 | `tools/license_scan.py --check-registry` 通过 |

## 3. Android 构建

### 3.1 版本要求（硬性）

| 项 | 最低版本 | CI 锁定版本 | 理由 |
|---|---|---|---|
| **NDK** | **r28**（`28.0.13004108`） | r28b（`28.1.13356709`） | NDK r28 起默认产出 **16 KB 页对齐**的 `.so`（`max-page-size=16384`）。r27 及更早默认 4 KB 页对齐，需手工加链接参数 |
| **AGP** | **8.5.1** | 8.7.3 | AGP 8.5.1 是支持 16 KB 页大小构建产物的最低版本；8.7.3 固定使用 NDK r28 的默认行为并支持 `compileSdk 35` |
| **Gradle** | 8.7 | 8.9 | AGP 8.7.3 要求 Gradle ≥ 8.9 |
| **Kotlin** | 1.9.22 | 2.0.21 | 与 AGP 8.7 兼容 |
| **JDK** | 17 | 17.0.13（Temurin） | AGP 8.x 要求 JDK 17 |
| **compileSdk / targetSdk** | 35 / 35 | 35 | Play 上架要求 |
| **minSdk** | 24（Android 7.0） | 24 | ARCore 要求 API 24+；Camera2 `ImageReader` 稳定可用 |
| **CMake** | 3.24.0 | 3.31.6（NDK 内置 3.22.1 亦可，但本项目统一用自带版本） | 与 §1.1 一致 |
| **build-tools** | 34.0.0 | 35.0.0 | `zipalign` 的 `-P 16` 参数需要 build-tools 34.0.0+ |

> **NDK r27 及更早的替代方案（不采用，仅记录）**：可手工在链接参数加 `-Wl,-z,max-page-size=16384`，但这依赖每个 target 都正确传递链接选项，遗漏一个 target 即产生不合规 `.so`，风险不可接受。**因此 NDK 低于 r28 一律拒绝构建**（`android/gradle` 中做版本断言，见 §3.4.2）。

### 3.2 ABI 矩阵

| ABI | 支持策略 | 16 KB 页对齐 | 理由 |
|---|---|---|---|
| `arm64-v8a` | **完整支持（主力）** | **适用**，LOAD 段 Align 必须 ≥ `0x4000` | 全部主流现代机型（2018 年后）。绝大多数用户的设备 |
| `x86_64` | **完整支持** | **适用**，Align ≥ `0x4000` | x86_64 平板、Chromebook、模拟器真机测试。Google Play 16 KB 政策同样覆盖 64 位 ABI |
| `armeabi-v7a` | **保留支持（次要）** | **不适用**，保持 4 KB 页对齐 | 覆盖 2017 年前的老旧低端机（≤ 3 GB RAM，见 13 §1 极低端档）。**不得淘汰**：这些设备正是本产品「无深度机型也要一等精度」承诺的主要受众 |

**明确不做的事**

| 不做 | 理由 |
|---|---|
| 不淘汰 `armeabi-v7a` | 与产品承诺冲突：无深度机型的一等精度路径主要落在这批设备上 |
| 不在 `armeabi-v7a` 上做 16 KB 对齐 | 32 位 ELF 的页大小由设备 4 KB 页硬件决定；且 Google Play 的 16 KB 政策只针对 64 位 ABI（`arm64-v8a` / `x86_64`） |
| 不引入 `riscv64` | 生态成熟度不足，且 OpenCV / Ceres 的预编译生态缺失（且我们不引入预编译） |
| 不做 ABI 自动降级到 32 位 | 32 位路径会改变 `size_t` 与指针宽度，影响位姿优化的数值行为，引入难以复现的差异 |

**32 位路径的已知差异（须在回归中覆盖）**

| 项 | 64 位 | 32 位 | 影响 |
|---|---|---|---|
| `size_t` / 指针 | 8 B | 4 B | 稀疏矩阵索引计算路径不同，需单独回归 |
| `long double` | 80 位（x86-64）/ 64 位（arm64） | 64 位 | 不影响（Ceres 用 `double`） |
| 峰值内存 | 基准 | 约 +8% ~ +15%（索引结构用 32 位省下的量小于指针表开销） | 13 §1 的极低端预算需按 32 位口径预留余量 |
| GPU 着色器 | 64 位纹理与 buffer | 32 位 | Metal 不支持 32 位设备（仅模拟器），Vulkan 的 `shaderFloat16` 在 32 位设备普遍不支持 → `mvs` 的视差精度用 `float32` 而非 `f16`（05 §5.9.1 精度表需按 ABI 分支） |

> 上表最后一行是 **5 文档 §5.9.1 精度表的一处 ABI 依赖**，须在 14 文档的测试矩阵中按 ABI 分别记录（§4.2）。

### 3.5 16 KB 页大小合规（硬门禁）

**判定标准**

| 目标 | 判据 |
|---|---|
| `.so` 的 ELF LOAD 段 | 每个 `LOAD` 段的 `Align` 字段 **≥ `0x4000`**（16384） |
| APK / AAB 内 `.so` 的**存储**对齐 | `zipalign -c -P 16 -v 4 <apk>` 输出全部 `Verified` |
| 仅 64 位 ABI 适用 | `arm64-v8a`、`x86_64` 必检；`armeabi-v7a` 不适用 |

**检查命令（CI 中逐字执行）**

```bash
#!/usr/bin/env bash
# tools/check_16kb.sh —— 在 CI 的 Android 构建 job 中执行
set -euo pipefail

READELF="${ANDROID_NDK_HOME}/toolchains/llvm/prebuilt/linux-x86_64/bin/llvm-readelf"
ZIPALIGN="${ANDROID_HOME}/build-tools/35.0.0/zipalign"
APK_PATH="android/app/build/outputs/apk/release/app-release.apk"
AAR_PATH="android/app/build/outputs/aab/release/app-release.aab"
SO_ROOT="android/app/build/intermediates/stripped_native_libs/release/stripReleaseDebugSymbols/out/lib"

fail=0

# ---- 检查 1：ELF LOAD 段对齐（仅 64 位 ABI）----
for abi in arm64-v8a x86_64; do
  for so in "${SO_ROOT}/${abi}"/*.so; do
    [ -e "${so}" ] || continue
    name="$(basename "${so}")"
    # 输出形如： LOAD  Align 0x4000
    aligns="$("${READELF}" -lW "${so}" | awk '$1=="LOAD" {print $NF}')"
    for a in ${aligns}; do
      if [ "$(( a ))" -lt "$(( 0x4000 ))" ]; then
        echo "FAIL: ${name} (${abi}) LOAD Align=${a} < 0x4000"
        fail=1
      fi
    done
    echo "OK: ${name} (${abi}) LOAD Align = ${aligns}"
  done
done

# ---- 检查 2：APK 内 .so 的 16KB zip 对齐 ----
if [ -f "${APK_PATH}" ]; then
  if ! "${ZIPALIGN}" -c -P 16 -v 4 "${APK_PATH}" | grep -q "^Verification successful"; then
    echo "FAIL: ${APK_PATH} 未通过 zipalign -P 16 校验"
    "${ZIPALIGN}" -c -P 16 -v 4 "${APK_PATH}" || true
    fail=1
  else
    echo "OK: zipalign -P 16 ${APK_PATH}"
  fi
fi

# ---- 检查 3：release .so 未被 strip 掉 16KB 对齐所需的信息 ----
# strip 不改变 p_align，故仅校验文件存在与大小非零
for abi in arm64-v8a x86_64; do
  n=$(find "${SO_ROOT}/${abi}" -name '*.so' 2>/dev/null | wc -l)
  if [ "${n}" -eq 0 ]; then
    echo "FAIL: 未找到 ${abi} 的 .so 产物"
    fail=1
  fi
done

exit ${fail}
```

**检查 3 的补充：`armeabi-v7a` 的 4 KB 保持检查**

```bash
# armeabi-v7a 保持 4 KB 页对齐（不适用 16 KB），此处确认它没有"意外"变成 16 KB 以外的怪值
for so in "${SO_ROOT}/armeabi-v7a"/*.so; do
  [ -e "${so}" ] || continue
  "${READELF}" -lW "${so}" | awk '$1=="LOAD" {print "'"$(basename "${so}")"' " $NF}'
done
```

**Google Play 的 16 KB 政策要点（工程落地口径）**

| 项 | 说明 |
|---|---|
| 适用范围 | 2025-11-01 起，面向 Android 15+ 设备的**新 App 与更新**必须支持 16 KB 页大小 |
| 判定方式 | Play Console 自动检测上传的 AAB/APK 中的 `.so` 是否 16 KB 对齐，不通过则拒绝上架 |

### 3.6 混淆与资源压缩（R8）

**R8 配置（`android/app/proguard-rules.pro`）**

```proguard
# ===== native 库与 JNI 桥接：必须保留 =====
# JNI 方法由 C++ 侧按名字查找（RegisterNatives 或命名约定），R8 不得改名/移除
-keepclasseswithmembernames,includedescriptorclasses class * {
    native <methods>;
}
-keep class com.recon.scan.** { *; }
-keep class com.recon.scan.bridge.** { *; }   # ReconBridge.kt 所在包

# ===== ARCore 可选依赖 =====
# ARCore 以 optional 方式引入；保留类名，避免 ClassNotFoundException 的可读性下降
-keep class com.google.ar.core.** { *; }
-dontwarn com.google.ar.core.**

# ===== 反射 =====
# 平台层通过反射读取设备能力（11 文档 §5.1 的相机能力表）
-keepclassmembers class * {
    @android.hardware.camera2.CameraCharacteristics$* <fields>;
}

# ===== 去除日志（Release）=====
-assumenosideeffects class android.util.Log {
    public static *** v(...);
    public static *** d(...);
    public static *** i(...);
}
```

| 规则 | 原因 |
|---|---|
| `-keepclasseswithmembernames ... native <methods>` | **native 库必须有 `-keep` 规则**：C++ 侧通过 `Java_com_recon_scan_bridge_ReconBridge_xxx` 符号名或 `RegisterNatives` 绑定方法；R8 若重命名方法或移除类，JNI 绑定在运行时崩溃 |
| `-keep class com.recon.scan.**` | 本项目自有包整体保留（体量小，收益为零风险为零） |
| 不 keep 第三方 Java 依赖 | OpenCV Java binding **不使用**（Android 侧走 JNI + `librecon_core.so`，Java 只做 UI） |

**R8 对 native 库无影响**

| 事实 | 处置 |
|---|---|
| R8 只处理 `.dex`（Java/Kotlin 字节码），不触碰 `.so` | `.so` 的体积控制靠 §3.7 的构建配置，不靠 R8 |
| `shrinkResources true` 只移除未引用的 `res/` 资源 | 全部资源由 Compose 按名引用；`assets/` 与 `res/raw/` 下的 `.spv` / 许可清单用 `noCompress` 保护 |
| `noCompress 'spv', 'txt'` | Vulkan SPIR-V 与 `THIRD_PARTY_LICENSES.txt` 不压缩，便于运行时 mmap 直读与人工查阅 |

### 3.7 包体积预估

**体积构成与优化杠杆（只列不改变精度的手段）**

| 手段 | 节省 | 是否触碰精度 | 允许 |
|---|---|---|---|
| 关闭 `armeabi-v7a` | 减少约 1/3 体积 | 否 | ❌ 不允许（§3.2） |
| 关闭 OpenCV `photo` 模块 | ~1.5 MB | 否（`post_bake_blend_mode=poisson` 用的是 PoissonRecon 梯度域求解器，不依赖 OpenCV photo 的 `seamlessClone`） | ✅ 允许 |

| `-Oz` 替换 `-O3`（仅 `librecon_vision.so`） | ~8% | **可能**（数值路径不同 → 需重跑黄金回归） | ⚠️ 需回归验证 |

| 产物 | 体积（含 3 ABI） | 备注 |
|---|---|---|
| 通用 APK（`app-release.apk`） | **95 – 135 MB** | 不推荐分发；Play 侧必须用 AAB |
| AAB（`app-release.aab`） | **95 – 135 MB** | 体积与通用 APK 接近，但 Play 按设备下发单 ABI → 用户实际下载 **26 – 36 MB** |
| AAB + Play 的 ABI 拆分后单设备下载 | **26 – 36 MB** | 真实用户感知体积 |
| 加上资源、字体、Compose 运行时、assets | +8 – 14 MB | 单设备下载合计 **34 – 50 MB** |

> **口径说明**：上表为 **strip 后的 `.so` 体积**，不含 Play 的 zip 压缩效果（`.so` 在 AAB 中按 `useLegacyPackaging false` 以未压缩方式存储，故下载体积≈解压体积）。**全部数值为构建复杂度模型估算，需实测标定**（14 文档 §6.3 性能回归项）；实测后回填本表并把 ±20% 偏差写入 CI 的体积门禁基线。

### 4.2 Swift / C++ 混编配置

本项目的跨语言边界**唯一**是 `core/include/recon/recon_c_api.h`（00 §7.1）。因此混编方式选择 **module map + bridging header** 的组合：

> **D-2 修订（2026-10-31，App 容器用 XcodeGen 生成）**：本仓库中
> **`.xcodeproj`（`.pbxproj`）不进版本库** —— 它是数百 KB 不可审查的 XML，
> 任何手改都无法 diff 复核，Xcode 版本升级还会带来格式漂移。仓库只保留
> **纯文本可审查的容器定义** `platform/ios/Container/project.yml`（由
> `tools/gen_ios_project.py` 生成），在 macOS 侧用 **XcodeGen** 生成容器：
>
> ```bash
> brew install xcodegen
> xcodegen generate --spec platform/ios/Container/project.yml
> ```
>
> 生成得到 `Recon.xcodeproj`。因此下文所有 `-project platform/ios/Recon.xcodeproj`
> 的路径**都是生成产物**，执行前必须先跑一次 XcodeGen。容器单独放的原因：
> SwiftPM 明令禁止 target 源码位于包根之外，而 UI 层在 `ui/ios/`、不在
> `platform/ios/` 之内，故 `Package.swift` 无法直接包含它。

| 层 | 机制 | 文件 |
|---|---|---|
| C++ → Swift 暴露 | **module map**（供 Swift 侧 `import ReconCore` 的类型可见性） | `platform/ios/ReconCore/include/module.modulemap` |
| Swift → C++ 调用 | **bridging header**（单一入口，避免 `import` 循环） | `platform/ios/Recon/Recon-Bridging-Header.h` |
| ObjC++ 平台实现 | `.mm` 文件直接 `#include "recon/recon_c_api.h"` | `platform/ios/*.mm` |

**资源落位：`group` 与 `folder` 必须分清（2026-11-01 实测，第三例「静默失效」）**

`project.yml` 的 `sources` 里，**目录类**条目的 `type` 决定了产物形态：

| type | Xcode 语义 | 对 pod 内落位的影响 |
|---|---|---|
| `group`（**默认**，黄色组） | 只保留工程内的**逻辑分组** | 文件被**展平到 bundle 根**（子目录层级**丢失**） |
| `folder`（蓝色文件夹引用） | 引用整棵子树 | 目录**连同目录名**原样拷入 bundle |

两条**方向相反**的硬要求同时成立，是本项目最容易写错的地方：

- `ui/ios/Recon/Resources/locales` → **必须 `folder`**。因为
  `Localization.swift` 的 `LocaleCatalog.loadAll` 以
  `subdirectory: "locales"` 查找；用默认 `group` 会把 20 个 json 展平到
  包根 → **20 个 locale 全部**落进 `missingFiles` → 所有界面回退显示键名
  （如 `msg.export.title`）。**且编译、链接、签名、安装、启动全部正常**。
- `platform/ios/Recon` → **必须保持 `group`**。因为
  `Resources/PrivacyInfo.xcprivacy` 需要落到**包根**才符合 docs/11 §1.5；
  改成 `folder` 会让它落到 `Recon.app/Recon/Resources/`（上架校验项失败）。

判据：`check_ios_contract.py` 的 **G17**（含与 Swift `subdirectory:` 的**交叉
对账**，改任一侧即失败）、`stage_ios_ipa.py` 的 **P-8 / P-9**。

**多架构打包约束**

| 约束 | 内容 |
|---|---|
| XC-1 | xcframework 内每个 slice 的头文件目录必须**逐字节相同**，否则 `xcodebuild` 报 "conflicting headers" |
| XC-2 | 静态库内含多个架构时，Mach-O 的 `LIPO` 段需为 `arm64 x86_64`；可用 `lipo -info` 校验 |
| XC-3 | 模拟器 slice **只用于开发期**，不进入提审包（`xcodebuild -archive` 只打包 device slice） |
| XC-4 | `xcframework` 目录提交进仓库（源码内联原则的延伸：产物由源码确定性生成，但为保证可复现，允许把构建好的 xcframework 作为 CI 缓存而非仓库文件）→ **决定**：`xcframework` **不进仓库**，由 CI 从源码构建并作为产物归档 |
| XC-5 | 符号剥离：Release 下 `STRIP_INSTALLED_PRODUCT=YES` + `DEAD_CODE_STRIPPING=YES`；`dSYMs` 单独归档用于崩溃符号化 |

脚本 `tools/build_metal_shaders.sh` 的流程（每步都有独立失败判据，不静默跳过）：

| 步骤 | 动作 | 失败判据 |
|---|---|---|
| 0 | 先跑 `tools/shader_parity.py`（**不需要 macOS**） | 两端漂移 → 立即失败（先编译毫无意义，只会让「编译通过」掩盖「两端已不同」） |
| 0b | 解析部署目标并构造 `-target` 三元组（见下方「为什么必须传 `-target`」） | ① 部署目标 < 15.0（§4.6 下限）→ 失败；② SDK 不是 `iphoneos`/`iphonesimulator` → 失败。**这两条断言刻意前移到工具链探测之前**，使无 macOS 的机器也能对它们做负向注入验证 |
| 1 | 逐个 `shaders/metal/*.metal` → `.air`（`xcrun -sdk <sdk> metal -target <triple> -c`） | 源文件数为 0 → 失败 |
| 2 | 合并 `.air` → `default.metallib`（`xcrun -sdk <sdk> metallib`） | — |
| 3 | 校验产物存在且非空 | 空/不存在 → 失败 |
| 3b | `strings default.metallib` 校验**产物**覆盖 `shaders/common/gpu_algo.h` 声明的全部算法函数 | 有函数找不到 → 失败（源码写对了但没编进去，如某 `.metal` 被误排除） |

> **步骤 0 与 3b 的分工**：0 是**源码层**的 CT-6（算法名/布局/常量对齐），
> 3b 是**产物层**的 CT-6（真的编进去了）。两者都要有 —— 只看源码无法发现
> 「被误排除出编译列表」。

**为什么必须传 `-target`（D-42 修订，2026-11-01）**

| 项 | 结论 |
|---|---|
| 作用 | `metal` 编译器**从 `-target` 三元组的 OS 版本推出 `__METAL_VERSION__`**：目标 iOS 15 → Metal 2.4；目标 iOS 16 → Metal 3.0（Apple 工具链工程师论坛 thread/726165 原话）。语言的可用特性随该宏变化 |
| 三元组 | `air64-apple-ios<major.minor>`（真机）/ `air64-apple-ios<major.minor>-simulator`（模拟器）。架构恒为 `air64` |
| **不传的后果** | 编译器取 **SDK 默认语言版本**（Xcode 16.4 的 iOS SDK 默认 Metal 3.1/3.2）→ **假通过**：编译成功，但产物语言版本高于部署目标，真机（iOS 15）运行期抛 `Function is using language version 3.0 which is incompatible with this OS`。**这类错误 CI 编译期查不出来**，只有真机跑才暴露 |
| 不用的写法 | 无 `-std=`（`metal` 无此选项）、无 `-mios-version-min`（那是 clang 的） |
| 与 §4.6 的耦合 | 部署目标必须与既有的 §4.6（iOS 15.0）**同源**。Xcode Build Phase 传 `IPHONEOS_DEPLOYMENT_TARGET`（Xcode 注入的构建设置，与 target 的 settings 同源），CMake 路径传 `RECON_IOS_DEPLOYMENT_TARGET`；两条路径都不写第二份字面量 |
| 实证 | 本判据诞生于 CI run 9 的 8 个 `atomic_float` 错误 —— 详见 §4.4 下方「浮点原子」说明 |

**浮点原子：两端统一走定点整数（D-42 修订）**

`atomic_float` 是 **Metal 3.0 / iOS 16** 起才有的类型别名（MSL 规范 §2.6），而本项目部署下限是 **iOS 15.0**（§4.6）—— 在契约允许的最低平台上该类型**根本不存在**。故 MVS 融合的 S/W 累加在**两端**统一为定点整数原子：

```
value → round(value × RECON_GPU_FIXED_SCALE)   // scale = 2^12 = 4096
饱和于 ±RECON_GPU_FIXED_MAX                    // 2^30
反量化：float(buf[idx]) × RECON_GPU_FIXED_SCALE_INV
```

尺度与上界的推导登记在 `shaders/common/gpu_algo.h` 的 `RECON_GPU_FIXED_*` 段（单一事实来源，两端同名同值，闸门 P7 比对）。**两端的三段数学式必须逐字同构**，由闸门 **P13** 校验（`tools/shader_parity.py`）；任何一端少做饱和修正或把 `round` 换成截断都会产生无法归因的跨端数值偏差，而两端各自的单元测试都是绿的。

**无工具链时的行为（Windows / 未装 Xcode）**

`xcrun` 缺失时脚本**明确打印 SKIP 与原因**，并退出 0（或 `RECON_REQUIRE_METAL=1`
时退出 1）。它**刻意不创建空的 `default.metallib`** —— 空库会被
`makeDefaultLibrary()` 当成「库存在但无函数」，错误比「找不到库」更隐蔽
（本项目反复强调「静默丢弃最难查」）。

**Xcode Build Phase 挂载**

| Build Phase | 位置 | 脚本 | 输入 / 输出 |
|---|---|---|---|
| 「Compile Metal Shaders」 | Target `Recon` → Build Phases，位于「Compile Sources」之前 | `bash "$SRCROOT/../tools/build_metal_shaders.sh"` | 输入：`shaders/metal/*.metal`；输出：`$(BUILT_PRODUCTS_DIR)/$(CONTENTS_FOLDER_PATH)/default.metallib` |

**运行时加载**

```swift
// platform/ios/MetalComputeBackend.swift
guard let device = MTLCreateSystemDefaultDevice(),
      let library = device.makeDefaultLibrary() else {
    throw ReconError.backendUnavailable("Metal default library 未随 bundle 打包")
}
```

| 约束 | 内容 |
|---|---|
| MT-1 | `default.metallib` 必须位于 **`Recon.app/`（包根）**，`makeDefaultLibrary()` 才能自动找到。⚠️ **iOS 是扁平 bundle，没有 `Contents/` 这一层**（macOS 才有 `MyApp.app/Contents/Resources/`）。落位由 XcodeGen 的 `UNLOCALIZED_RESOURCES_FOLDER_PATH` 展开给出（iOS = 包根，macOS = `Contents/Resources`）。2026-11-01 修正：此前本文与 `gen_ios_project.py` 都写成 `${CONTENTS_FOLDER_PATH}/Resources`，在 iOS 上展开为 `Recon.app/Recon.app/Resources` → **编得过、CI 全绿、运行期永远加载不到**。判据：`check_ios_contract.py` 的 **G15**、`stage_ios_ipa.py` 的 **P-4 / P-5** |
| MT-2 | 不得使用 `makeDefaultLibrary(bundle:)` 的自定义 bundle 名（会让 App Extension 等场景失效），统一走默认 bundle |
| MT-3 | 着色器函数名与 `shaders/common/` 的算法名必须一致，由 `tools/shader_parity.py` 校验（§6.2） |
| MT-4 | 着色器内的常量（`mvs_gpu_tile_size` 等）**不得硬编码**；必须经 buffer 从 C++ 侧传入（Metal：`setBytes` / `MTLBuffer`；Vulkan：UBO / SSBO descriptor），以便 13 文档的降级能在不重编译着色器的前提下调整分块。唯一例外是 workgroup 布局限定符（`threadgroup_size` / `local_size_*`），着色器语言要求其为编译期字面量 —— 该例外由 `shaders/common/gpu_algo.h` 的 `RECON_GPU_WORKGROUP_*` 单点定义，闸门 P6 校验三方一致 |
| MT-5 | `MTLDevice.maxBufferLength` 与 `maxTextureDimension2D` 必须在启动时查询并作为 13 文档 §1 的显存预算输入 |

| 项 | 结论 |

### 4.6 最低部署版本

**结论：iOS 15.0**

| 候选 | 评估 | 结论 |
|---|---|---|
| iOS 14.0 | ARKit `sceneDepth` / `smoothedSceneDepth` 需 iOS 14+，但 iOS 14 上 `ARWorldTrackingConfiguration.supportsFrameSemantics(.sceneDepth)` 在部分机型返回 `false` 的比例明显高于 iOS 15；且 14 上 `ARSession` 的 `didUpdate` 回调频率不稳定，会直接影响 02 文档的时间同步精度（`τ_pipeline` 预算） | ❌ 排除 |
| **iOS 15.0** | `sceneDepth` 支持面完整；`ARFrame.sceneDepth` 语义在 15 上稳定（沿光轴 z，与 02 §5.5 F-1 一致）；SwiftUI 生命周期 API 完整；`ProcessInfo.thermalState` 四档可用（11 §5.1） | ✅ **采用** |
| iOS 16.0 | 相比 15 无任何精度或功能增益（`ARMeshAnchor` 分类、`RealityKit` 均不用于本产品）；仅提高系统覆盖面。代价：放弃一批仍在用 iOS 15 的设备，与"不淘汰老旧机型"的产品立场相悖 | ❌ 排除 |

| 项 | 说明 |
|---|---|
| 覆盖率口径 | iOS 15 的设备覆盖率随时间变化，**具体百分比需以 App Store Connect 的「最低版本分布」实测数据为准**，本文不给固定数字（避免过期数据误导）。发布前用 Play Console/App Store Connect 的实际统计复核 |
| 与 ARKit 的关系 | 11 文档 §1 已把 ARKit `sceneDepth` 定位为「尺度锚定 + 先验 + 补盲」，不是精度主项；因此 iOS 14 的 `sceneDepth` 差异不构成选 iOS 15 的**唯一**理由，iOS 15 的完整理由是「支持面 + 时间同步稳定性 + SwiftUI 生命周期完整性」三项叠加 |
| 与 32 位的关系 | iOS 15 起无 32 位设备，`arm64 only` 天然成立（§4.7） |
| 与静态库切片的关系 | **两条编译路径（CMake 静态库 / Xcode App 容器）必须解析到同一个部署目标。** CMake 侧要同时设 `CMAKE_SYSTEM_VERSION` **与** `CMAKE_OSX_DEPLOYMENT_TARGET`（见下），Xcode 侧由 `IPHONEOS_DEPLOYMENT_TARGET` 承担（`Container/project.yml`）。**第四十一轮的实测事故**：只设了前者，CMake 的 Xcode generator 便把后者留空 → 交给 SDK 默认值（当时是 **18.5**），于是 `libReconCore.a` 里每个 `.o` 都按 18.5 编，而 App 按 15.0 链接，链接器刷出上百条 `ld: warning: object file ... was built for newer 'iOS-simulator' version (18.5) than being linked (15.0)`。这不只是噪声：`.o` 的 min-version 高于链接目标时可能带出更高系统版本才有的弱符号绑定，即"本机编得过、装到 iOS 15/16 真机才炸"。修法是把 `CMAKE_OSX_DEPLOYMENT_TARGET` 钉成 `${RECON_IOS_DEPLOYMENT_TARGET}`（`cmake/toolchains/ios.cmake`），**不引入第二份字面量** |

#### 4.8.1 CI 未签名 IPA（与上面的带签名流程并存，**不是替代**）

**为什么需要它**：上面的三步流程**全部依赖 Apple 凭据** —— `-exportArchive`
强制要 `-exportOptionsPlist` 且强制签名，`-allowProvisioningUpdates` 会去联
Apple 服务。而本项目 CI 的契约是**未签名 + 零网络**（§1 B-3、11 §1.6），CI 上
**既没有也不应该有** `.p12` / API Key。于是 CI 永远产不出可交付的包 —— 而
"能不能产出一个装得上的包"恰恰是整条构建链最终的判据。

**它解决什么**：产出一个**未签名 IPA**，供使用**免费 Apple ID** 的个人用
AltStore / Sideloadly 等工具自签后装到自己的设备上（免费账号签名 7 天有效，
需周期性重签 —— 这是免费账号的固有限制，不是本流程的缺陷）。
带签名的正式分发路径（上面的 §4.8 主流程）仍由**持有凭据的机器**执行。

**两处必须对齐的差异**

| 项 | 带签名（§4.8 主流程） | 未签名（CI 链） |
|---|---|---|
| 归档开关 | `DEVELOPMENT_TEAM` + `CODE_SIGN_STYLE=Automatic` + `-allowProvisioningUpdates` | `CODE_SIGNING_ALLOWED=NO` / `CODE_SIGNING_REQUIRED=NO` / `CODE_SIGN_IDENTITY=""` |
| 打包方式 | `xcodebuild -exportArchive -exportOptionsPlist ...` | **手工** `Payload/` + zip（`-exportArchive` 在未签名下必然失败） |
| 上传 | `xcrun altool --upload-app` | `actions/upload-artifact`（不创建 GitHub Release：Release 是发布动作，须由 tag 触发并经人工决定，见 §7.3） |
| 产物 | `build/ios/export/Recon.ipa` | `build/ios/Recon-unsigned.ipa` |
| 消费方 | TestFlight / App Store | 免费账号自签后真机安装；结构回归 |

**实现与判据落点**（**单一实现**，勿在 YAML 重写）

- 打包 + 产物校验：`tools/stage_ios_ipa.py`（`stage` / `verify` / `--self-test`）。
  判据 **P-1..P-9** 全部读**产物**：容器结构 / `Info.plist` / **架构恰好
  arm64**（XC-3，含自研 Mach-O 解析 + `lipo` 交叉验证）/ `default.metallib`
  在包根 / 无 `Contents/` 层 / Bundle ID 与 `project.yml` 对账 / 无
  `_CodeSignature/` / **locale 落位与 `Localization.swift` 的 `subdirectory:`
  一致** / `PrivacyInfo.xcprivacy` 在包根。
- 流程纪律：`tools/check_ios_contract.py` 的 **G16**（device 归档 / 调用 stag-
  ing 脚本 / 无 `-exportArchive` / 产物上传 artifact）与 **G17**（locale 资源
  落位）、**G15**（bundle 落位：代码侧三处 + **G15-d 文档面交叉对账**）。
- 该脚本的 `--self-test` **不依赖 macOS**（纯标准库：`zipfile` + 自研 Mach-O
  解析），故在 `static-contract`（ubuntu）job 内独立跑；负向注入见

## 5. 桌面验证机（开发期）

### 5.1 为什么必须有桌面构建

| 理由 | 说明 |
|---|---|
| **不可能每次都真机测试** | 精度回归需要**每日**跑全量黄金数据集；真机采集一次会话需 10–20 分钟（03 文档 §4 的 16–18 点位采集），全量数据集跑一遍需数小时。桌面可把同一份落盘数据（`sessions/<id>/`）在 **≤ 60 s** 内重跑全管线 |
| 相机/IMU 行为**不能**用桌面替代 | 这部分由实机测试覆盖（14 §5.4）。桌面只覆盖**算法**：时间同步 → 质量门限 → 关键帧 → SfM → BA → MVS → 泊松 → 后处理 → 导出 |
| 编译速度 | 桌面构建（`-O3`）约 3–5 分钟；Android 全量构建约 12–20 分钟。日常开发迭代必须走桌面 |
| 调试能力 | 桌面可接 AddressSanitizer / UndefinedBehaviorSanitizer / `lldb`（14 §5.5） |
| 无 GPU 图形栈时的算法验证 | `core/compute/` 提供 CPU 回退（05 §5.9.4），桌面可直接跑 CPU 路径验证算法一致性 |

|---|---|
| FP-1 | 精度基线只在 **Linux x86-64 + GCC 12** 上产生。macOS（clang + arm64）与 Windows（MSVC）只跑"不超差"判定，容差放宽 3 倍（§14 §6.2） |
| FP-2 | 全部浮点计算用 `double`（05 §4.7），`float` 仅用于 GPU 纹理与视差中间量（05 §5.9.1）。禁止开启 `-ffast-math`（§1.1） |
| FP-3 | `Eigen` 的向量化路径在不同 CPU 上可能给出末位差异；BA 收敛判据（05 §4.8）按 1e-8 容差比较，差异不影响结论 |

### 6.3 性能基线与容差

| 指标 | 采集方式 | 基线存储 | 容差 | 超差处理 |

| 各阶段耗时（ms） | `recon_cli bench --repeat 3` 取中位数 | `tests/golden/perf_baseline.json` | 相对基线 **+30% / −25%** | 超上界 → 记 `perf_regression`，PR 需说明；连续 3 日超上界 → 阻断合并 |

|---|---|
| PERF-1 | 性能基线**独立**于精度基线。精度达标**不豁免**性能超差（14 §6.3） |

### 7.1 版本号规则

### 7.2 灰度与回滚

**Android（Play Console staged rollout）**

| 阶段 | 流量 | 观察时长 | 推进条件 |
|---|---|---|---|
| 内部测试 | 内部名单 | 2 天 | 无 P0/P1（§14 §7） |
| 封闭测试（`beta-acceptance`） | 机型矩阵机型 | 5 天 | 14 §4 矩阵全绿 + 精度基线在容差内 |
| 开放测试 | 5% | 3 天 | 崩溃率 < 0.3%，ANR 率 < 0.5% |
| 生产 1 | 20% | 3 天 | 同上 + 精度抽检（≥ 20 个真实会话，尺度误差 ≤ 1.0%） |
| 生产 2 | 50% | 3 天 | 同上 |
| 生产 3 | 100% | — | — |

| 规则 | 内容 |
|---|---|
| R-1 | **不得用 Play 的分阶段发布掩盖 P0**。任一阶段出现 P0 → 立即 Halt rollout（Play 的 "Halt rollout"），不是等 100% |
| R-2 | 崩溃率阈值取**本地统计**（崩溃上报 SDK 不集成，因此由 TestFlight 反馈 + 用户主动反馈 + CI 消毒器结果构成）。**这意味着崩溃率不可自动获取**，因此灰度阶段的推进**必须人工确认**，这是零网络策略的必然代价，需在发布评审中明示 |
| R-3 | 回滚 = 立即 Halt rollout + 用 Play 的 "Roll back to previous release"（**注意**：Play 不支持回滚到任意历史版本，只能回滚到上一个版本）。因此**必须保证上一个版本是可用的**：不允许连续两次发布都含 P0 修复 |

**iOS（TestFlight → App Store 分阶段发布）**

| 阶段 | 机制 | 说明 |
|---|---|---|
| TestFlight 外部测试 | `beta-acceptance` / `external-pilot` 组 | 机型矩阵执行 |
| App Store 分阶段发布 | 1% → 2% → 5% → 10% → 20% → 50% → 100% | 与 Play 相同的推进条件 |
| 回滚 | App Store **不支持回滚** | ⚠️ **这是硬差异**：iOS 侧只能"停止分发"（停止后新用户无法下载，已安装用户继续运行旧版）。因此 iOS 侧必须在灰度前完成全部机型验证，且 §7.5 的「构建期零网络验证」在 iOS 侧权重更高 |

**回滚预案**

| 场景 | 动作 | 恢复 |
|---|---|---|
| P0（精度不达标 / 导出错误 / 崩溃 / 违反合规） | Android：Halt + Rollback；iOS：停止分发 + 发布 Hotfix（走完整 CI，周期 ≤ 3 天） | 修复后重新走灰度 |
| P1（功能异常但不阻断主流程） | 不回滚，通过下个版本修复；UI 侧需有对应的用户可见提示 | — |
| 合规问题（许可扫描在发布后被人发现） | **立即停止分发 + 立即下架**（Android 可用 Play Console 停止分发；iOS 需提交更新移除） | 重新走 §2.8 流程 |

### 7.3 发布执行步骤（tag 触发）


### 7.4 构建期零网络验证（硬门禁）

**背景**：00 §8.9 指出「上架需声明隐私清单」与「零网络」存在表面矛盾，11 §1.6 给出四条证明链。本节定义**构建期**（而非运行时）的验证实现。

#### 7.4.1 符号级扫描

```bash
#!/usr/bin/env bash
# tools/check_no_network.sh —— 构建期零网络验证
set -uo pipefail
fail=0

# 禁止符号清单（与 11 §1.6.2 证明链 B / C 一致）
FORBIDDEN_RE='(^|[^A-Za-z0-9_])(socket|connect|bind|listen|accept|send|sendto|sendmsg|recv|recvfrom|recvmsg|getaddrinfo|gethostbyname|getnameinfo|res_query|res_send|SSLCreateContext|SSLConnect|SSLWrite|SSLRead|SecTrustEvaluate|SSLSetPeerHostName|CFStreamCreatePairWithSocket|CFHostCreateWithName|CFHTTPMessageCreateRequest|NSURLSession|NSURLConnection|NSURLRequest|URLSession|URLRequest)([^A-Za-z0-9_]|$)'

# ---- 检查 1：iOS 可执行文件与静态库中的未定义符号 ----
for artifact in \
    "build/ios/export/Recon.app/Recon" \
    "build/ios/ReconCore.xcframework/ios-arm64/libReconCore.a" ; do
  [ -e "${artifact}" ] || continue
  hits="$(nm -u "${artifact}" 2>/dev/null | grep -E "${FORBIDDEN_RE}" || true)"
  if [ -n "${hits}" ]; then
    echo "FAIL: ${artifact} 含网络相关未定义符号"
    echo "${hits}"
    fail=1
  else
    echo "OK: ${artifact} 无网络未定义符号"
  fi
done

# ---- 检查 2：Android .so 的 NEEDED 依赖 ----
for so in android/app/build/intermediates/stripped_native_libs/release/stripReleaseDebugSymbols/out/lib/*/*.so; do
  [ -e "${so}" ] || continue
  hits="$("${ANDROID_NDK_HOME}/toolchains/llvm/prebuilt/linux-x86_64/bin/llvm-readelf" -d "${so}" \
         | grep NEEDED | grep -E 'libssl|libcrypto|libcurl' || true)"
  if [ -n "${hits}" ]; then
    echo "FAIL: ${so} 依赖网络库"
    echo "${hits}"
    fail=1
  fi
done

# ---- 检查 3：iOS 链接的框架清单 ----
if [ -e "build/ios/export/Recon.app/Recon" ]; then
  hits="$(otool -L "build/ios/export/Recon.app/Recon" \
         | grep -E 'CFNetwork\.framework|/Network\.framework|Security\.framework|WebKit\.framework' || true)"
  if [ -n "${hits}" ]; then
    echo "FAIL: 链接了网络框架"
    echo "${hits}"
    fail=1
  fi
fi

# ---- 检查 4：二进制内的 URL 字符串（licenses.json 白名单除外）----
if [ -e "build/ios/export/Recon.app/Recon" ]; then
  hits="$(strings -a "build/ios/export/Recon.app/Recon" \
         | grep -E 'https?://' | grep -v -f third_party/licenses_url_allowlist.txt || true)"
  if [ -n "${hits}" ]; then
    echo "FAIL: 含 http(s) URL 字符串"
    echo "${hits}"
    fail=1
  fi
fi

exit ${fail}
```

```
https://github.com/colmap/colmap
```

| 编号 | 规则 |
|---|---|
| ZN-1 | `nm -u` 只检查**未定义符号**（外部依赖）。定义在自身二进制内的函数（如自研的 `send` 同名局部函数）不构成网络行为 |
| ZN-2 | `otool -L` 的允许框架清单按 11 §1.6.2 证明链 C 严格执行；`Security.framework` **被禁止**（TLS 客户端侧不需要） |
| ZN-3 | URL 字符串扫描的白名单**必须**显式列出，且白名单文件本身由 CODEOWNERS 保护 |
| ZN-4 | Android 侧的 Java/Kotlin 层符号扫描由 `tools/network_audit.py` 承担（dexdump / jadx），见 11 §7.2 第 8 项 |
| ZN-5 | **构建期零网络验证是硬门禁**：§7.3 第 4 步失败即终止发布，不允许"先发布后修" |

#### 7.4.2 源码层扫描（与 11 §1.6.2 证明链 B 对应）

```bash
python3 tools/network_audit.py \
    --sources core,platform,ui \
    --forbid 'URLSession,URLRequest,NSURLConnection,CFNetwork,CFStream,NWConnection,Network.,NetService,Bonjour,GCDAsyncSocket,CFHost,getaddrinfo,gethostbyname,res_,' \
```
