## 0. 本文档的边界与第一原则

### 0.1 边界

| 范围 | 内容 | 归属说明 |
|---|---|---|
| 覆盖 | 内存预算、峰值分析、背压/分块/落盘、水位监控、降级白/黑名单、温度电量、长时间稳定性 | 本文 |

### 0.2 第一原则（贯穿全文，不得违反）

> **内存上限是「内存保护阈值」，不是「精度降级阈值」。**
>
> 触达上限时的正确行为是：**分块处理 / 落盘 / 排队 / 降低并行度**。
> 错误行为是：**降低精度参数**。

这一区分不是措辞偏好，而是 00 §1.1 两条铁律的直接推论：

| 铁律 | 对内存问题的推论 |
|---|---|
| R-PREC-4 | 低端机降级只允许降低**并行度 / 批大小 / 分块策略**，不得降低体素分辨率、特征点数、BA 迭代数、匹配阈值 |
| R-PREC-5 | 内存保护优先使用「分块 + 落盘 + 流式」，不得通过丢弃精度数据来降内存 |
| R-PREC-3 | 关键帧只要对精度有增益即全量保留，不做自动剔除、不做自动降采样 |
| R-PREC-6 | 所有精度相关阈值必须可被用户覆盖，且覆盖后不发生静默回退 |

### 0.3 关键帧与「精度数据」的内存处置原则

02 §2.4.3 M-4 明确区分两个队列；03 §5.3.2 明确关键帧图像在采集期即落盘后释放引用。因此：

| 数据类别 | 内存超限时允许做什么 | 禁止做什么 |
|---|---|---|
| **关键帧图像（RGB / 深度）** | 保持落盘；重建期按需分批读入，读完即释放 | ❌ 丢弃关键帧（R-PREC-3、00 §1.2 黑名单「关键帧保留数量」） |
| **关键帧元数据（位姿 / 2D 特征点 / 描述子）** | 分块加载（05 §4.2.3）；块级落盘 | ❌ 丢弃关键帧 |
| **BA 稀疏矩阵** | 滑窗 BA 优先（03 §5.3.5）；全量 BA 的 Schur 补按相机数分块求解但**必须覆盖全部帧**（K-5） | ❌ 减少参与 BA 的帧数 |
| **MVS 深度图** | 分块（tile）计算；源视图深度图按 tile 分批重算 | ❌ 深度图降采样、截断（00 §1.2 黑名单） |
| **TSDF 体素** | 分块 + 落盘；块数上限 `rgbd_max_blocks_in_memory` | ❌ 提高体素边长（黑名单） |
| **泊松八叉树** | 分块泊松（06 §1.7 A）+ 按层落盘（C） | ❌ 降低 `mesh_poisson_depth` / `mesh_poisson_scale`（黑名单） |
| **UV 图集 / 纹理位图** | 图集按 chart 分批写入 + 落盘中间图 | ❌ 静默降低 `post_uv_atlas_size`（属「纹理质量」精度维度，需用户显式同意，见 §4.4） |

## 1. 内存预算总表

### 1.1 机型档位划分

| 档位 | 判定条件（设备物理内存） | 典型代表机型 | 备注 |
|---|---|---|---|
| **高端 T0** | RAM ≥ 8 GB | iPhone 14 Pro 及以上；Pixel 8 Pro；旗舰 Android | 可跑完高精度档（08 §2.4） |
| **中端 T1** | 4 GB ≤ RAM < 8 GB | iPhone 12/13；Galaxy A54/S 系列 | 高精度档需强制分块 |
| **低端 T2** | 3 GB < RAM ≤ 4 GB | iPhone SE 2/3；Galaxy A34 | 标准档可行；高精度档 UI 禁用 |
| **极低端 T3** | RAM ≤ 3 GB | iPhone 8 / SE 1；千元 Android 机 | 无深度机型为主，正是 §4.5 一等精度承诺的主要受众 |

> **档位边界的消歧（必须写死，不得歧义）**：用户口径的「低端 ≤4 GB」与「极低端 ≤3 GB」在 (3, 4] GB 区间重叠。本文档采用**互斥划分**：T2 = (3 GB, 4 GB]，T3 = ≤ 3 GB。实现时以同一张表为唯一真源，UI 与调度读同一份 `MemoryTier` 枚举。

**档位判定 API**

| 平台 | API | 用途 |
|---|---|---|
| iOS | `ProcessInfo.processInfo.physicalMemory`（`NSProcessInfo.physicalMemory`） | **档位判定**用物理内存（稳定，不随负载波动） |
| iOS | `os_proc_available_memory()`（`#include <os/proc.h>`） | **预算计算**用实时可用内存 |
| Android | `ActivityManager.getMemoryInfo()` 的 `totalMem` | **档位判定**用物理内存 |
| Android | `ActivityManager.getMemoryInfo()` 的 `availMem` | **预算计算**用实时可用内存 |
| Android | `ActivityManager.getLargeMemoryClass()` | `largeHeap` 上限，仅作记录，**不申请** `largeHeap`（见 §1.4） |

### 1.2 预算公式

```
M_budget(tier, platform) = clamp( F(platform, runtime), B_min(tier), B_max(tier) )

iOS:      F = os_proc_available_memory() × 0.55
Android:  F = min(availMem × 0.70, totalMem × 0.30)
```

| 参数 | 值 | 依据 |
|---|---|---|
| iOS 系数 0.55 | 取 `os_proc_available_memory()` 的 55% | `os_proc_available_memory()` 返回的是「进程被杀前还能申请的量」，已含系统与其它进程占用；留 45% 余量给 Metal 驱动的临时分配、纹理上传的双缓冲、UI 层的图片解码 |
| Android 系数 0.70 / 0.30 | 双约束取小 | `availMem` 是系统级可用（会被其它 App 抢占）；`totalMem × 0.30` 是本 App 的长期占用上限（超过会被 LMK 优先杀） |
| 采样周期 | 500 ms（重建期 200 ms） | 见 §3.4 |

> **描述子库上限 vs 描述子块常驻量**：前者是**该档位允许的描述子库总容量**（05 §4.2.3 的「可用常驻上限」口径），后者是**单块的实际常驻量**。二者之差（库上限 − 块常驻量）留给匹配过程的临时工作区。块常驻量由「描述子分块帧数」决定。
>
> **泊松分块块数的推导**：`块数 = ceil(块内峰值 / (泊松上限 × 0.6 / 块数))`，即在「每块峰值 ≤ 泊松上限 × 0.6」的约束下求最小块数。取整到 2 的幂。**块数增加不改变 `D` 与 `r`**（06 §1.7 A2 的硬要求）。

> **线程池 / GPU 批次 / 分批粒度**三行是 08 G11 白名单参数的档位默认值（`perf_thread_pool_size` 的 0=自动规则为「CPU 核数 − 1，上限 8」；本表在中端及以下收紧到 6/4/2，因为 CPU 核数与可用内存并不正相关，核多不等于内存多）。**这三行是性能类参数，与任何精度参数无关。**

**两条明确不做的事**

| 不做 | 理由 |
|---|---|
| 不申请 Android `largeHeap` | `android:largeHeap="true"` 会让系统放宽本进程的内存限制，但**不会**让 MVS/泊松这类 CPU 密集 + 显存密集的场景变快，只会让系统更难在其它 App 内存紧张时回收本 App，反而降低存活率。且 13/14 文档的内存预算模型基于「被杀则重建中断」这一前提，不基于「大堆永不被杀」 |
| 不因为内存水位下调 `cap_resolution_width` / `cap_frame_rate` | 采集分辨率与帧率是**精度一阶因子**（M1：全传感器分辨率采集不做降采样；`δZ ∝ Z²/(f·B)`）。02 §5.6.2 B-3 提到「优先把 RGB 存储分辨率降到 720p」，但那一条限定在「写入带宽导致采集线程调度延迟 > 5 ms」的场景，**不是内存场景**。内存不足时的正确做法是让采集**变慢**（阻塞），不是让采集**变糊** |

### 2.2 帧队列（采集期）

**两个队列必须分开看**（02 §2.4.3 M-4）：

| 队列 | 容量 | 字节（1080p BGRA8） | 满时行为 |
|---|---|---|---|
| 采集 → 核心 | **8 帧** | 63 MiB | **阻塞采集线程**（背压，见 §3.1） |
| 核心 → 写盘 | **64 帧** | 506 MiB | 先标 `pending_flush`；持续满 2 s → 阻塞核心线程（关键帧不丢弃） |
| IMU 环形 | 4096 样本 | 160 KiB | 覆盖最旧样本（4096 × 40 B @200 Hz = 20.5 s 窗口） |

**采集期峰值（02 §2.5.2 口径）**

```
M_peak = N_inflight × (S_rgb + S_depth + S_conf) + M_imu_ring + M_pipeline + M_platform_reserved
N_inflight = 11  (核心队列 8 + 平台在途 2 + 已移交写盘 1)
```

| 场景 | 采集侧合计（不含 `M_pipeline`） |
|---|---|
| 1080p + ToF 深度（iOS） | 11 × (7.91 + 0.59 + 0.29) + 0.16 + 23.7 = **120.6 MiB** |
| 720p 无深度（Android） | 11 × 3.52 + 0.16 + 4.0 = **42.9 MiB** |

> **口径警告**：平台相机池保留的 23.7 MiB（iOS 3 帧）在 `M_budget` 之外还是之内？**之内**——它是本进程的 RSS。`M_budget` 是「本进程在重建期间允许占用的 RSS 总量」，因此采集侧的 120.6 MiB 要从中扣除。`M_budget` 的公式已通过 0.55 / 0.70 系数隐含了这部分。

### 2.3 BA 稀疏矩阵

| 项 | 计算 | 标档（300 关键帧）数值 |
|---|---|---|
| 参数维度 | 相机 6 + 点 3 | N_cam = 300 → 相机参数 1 800 |
| Schur 补尺寸 | `6 × N_cam` | 1 800 × 1 800 |
| 稠密 Schur 补 | `1 800² × 8 B`（double） | **25.9 MB** |
| 稀疏 Schur 补（非零元估算） | 每相机约 60 个关联点 × 6×6 块 | 300 × 60 × 36 × 8 B = **5.2 MB** |
| 雅可比（稀疏） | 每观测 2 维 × 参数块稀疏存储 | 观测数 1.2e6 × 约 40 非零 × 16 B = **768 MB**（这是 BA 阶段的实际峰值来源） |
| 协方差（`ceres::Covariance`） | 完整 `Σ = (JᵀWJ)⁻¹` | 300 相机 + 1.2e5 点 → **偏大**，需按 §3.2 分块求解 |

**峰值结论**：BA 的峰值在**雅可比的构造**（稀疏但非零元多），不是 Schur 补。因此 BA 的内存优化手段是「**滑窗 BA 优先 + 全量 BA 分块**」，而不是「少放帧进去」。

| 项 | 规格 |
|---|---|
| BA 内存上限（§1.3 归入关键帧预算） | T0 300 MB / T1 160 MB / T2 80 MB / T3 40 MB |
| 超限处置 | ① 先切 `DENSE_SCHUR`→`SPARSE_SCHUR`（相机数 ≤ 200 时稠密更快且内存更省）；② 仍超则滑窗 BA 先行收敛，全量 BA 的 Schur 补按相机区间分块求解，**但每帧都必须在某一块中被优化**（03 K-5） |
| 禁止 | ❌ 减少参与 BA 的关键帧数；❌ 减少 BA 迭代次数（黑名单） |

## 3. 内存保护机制（不降精度）

### 3.1 背压（Backpressure）

**原则**：采集速率 > 重建速率时，**阻塞**而不是**丢帧**。

#### 3.1.1 三级背压链

| 级 | 位置 | 触发 | 动作 | 丢帧？ |
|---|---|---|---|---|
| **BP-1** | 采集 → 核心队列（容量 8 帧） | 队列满 | 采集线程**阻塞等待**（条件变量），等待期间不释放相机缓冲 | ❌ 不丢 |
| **BP-2** | 核心 → 写盘队列（容量 64 帧） | 队列满 | ① 帧标 `pending_flush`，核心线程继续（不阻塞）；② 队列深度 > 48 帧 → 记 `RECON_ERR_WRITE_QUEUE_BACKLOG`；③ 持续满且写盘连续 2 s 未下降 → **阻塞核心线程**（关键帧不丢弃） | ❌ 不丢关键帧；仅非关键帧可丢（W-4） |
| **BP-3** | 重建期关键帧读取 | 读盘速度 > 阶段消费速度 | 读盘线程**限速**（滑动窗口最多预读 N 个关键帧） | ❌ 不丢 |

#### 3.1.2 BP-1 的阻塞时序与超时

```
采集线程（相机回调）
  │ push 到无锁队列
  ├─ 队列未满 → 入队，返回（不阻塞，02 M-1）
  └─ 队列满 → 等待条件变量
       ├─ 核心线程 pop → signal → 采集线程唤醒，继续
       └─ 等待超过 T_block_max → 记 RECON_ERR_CAPTURE_BACKPRESSURE，
                                强制 pop 队头（最老帧）让出空间，
                                该帧标记 pending_flush 并转入写盘队列（不丢弃像素）
```

| 参数 | 值 | 说明 |
|---|---|---|
| `T_block_max`（单次阻塞上限） | **1 000 ms** | 02 §2.4.3 M-2 的硬上限 |
| 目标驻留时间 | ≤ 200 ms | 02 M-2 的目标值 |
| 阻塞期行为 | 采集帧率**自动下降**（相机回调变慢 → 系统相机池自动缓冲） | 不降分辨率、不降帧率参数；是采集速率的**自然结果** |
| 计数上报 | `CaptureStats.frames_captured` 不变；阻塞时长计入 `recon_profile.json` 的 `capture.blocked_ms` | 用于诊断「设备性能不足」 |

> **重要**：BP-1 导致的是**采集变慢**，不是**采集变糊**。UI 上表现为「帧率变低」，用户可自行决定是否改用更少视角。绝不可由内存水位自动改 `cap_frame_rate` 或 `cap_resolution_width`。

#### 3.1.3 BP-2 的写盘背压

| 项 | 规格 | 来源 |
|---|---|---|
| 队列满 | 帧标 `pending_flush`，核心线程继续处理下一帧 | 02 W-3 |
| 告警阈值 | 深度 > 48 帧 → `RECON_ERR_WRITE_QUEUE_BACKLOG` | 02 W-3 |
| 升级条件 | 队列满（64 帧）**且**写盘连续 2 s 未下降 | 02 W-4 |
| 升级动作 | **阻塞核心线程**；已采帧保留 | 02 W-4 |
| 唯一允许的丢弃 | 非关键帧，记 `frames_dropped_writer` | 02 W-4 |

**落盘带宽不足时的正确处置顺序**（R-PREC-5）：

| 序 | 动作 | 是否降精度 |
|---|---|---|
| 1 | 写盘线程提优先级（`QOS_CLASS_UTILITY` → `QOS_CLASS_USER_INITIATED` 之下、`QOS_CLASS_UTILITY` 之上不可得，故降到 `QOS_CLASS_BACKGROUND` 之上不可行，实际做法是保持 UTILITY 并减少其它线程的 CPU 竞争） | ❌ 否 |
| 2 | `writev` 合并 RGB+深度+置信度为一次系统调用（02 B-2） | ❌ 否 |
| 3 | `pwrite` + 提高 `fdatasync` 频率（02 W-5：4 MiB 或 200 ms 先到者） | ❌ 否 |
| 4 | 增大写盘队列容量（63 → 128 帧） | ❌ 否（代价是内存 +506 MiB，须在预算内） |
| 5 | 关闭 L2 上下文层落盘（02 §5.6.5 磁盘不足分级） | ❌ 否（已落盘数据不动；L2 是辅助帧） |
| — | ❌ 降低 `cap_resolution_width`（仅在 02 B-3 的「调度延迟 > 5 ms」场景、由用户决定） | **有** |

### 3.2 分块（Tiling）策略

**总原则（03 §5.3.5 K-4）**：分块只改变**调度与内存组织**，不改变任何精度阈值。

#### 3.2.1 TSDF 分块

| 项 | 规格 |
|---|---|
| 块尺寸 | `rgbd_voxel_block_size` = **32 / 64 / 128** 体素（快 / 标 / 高），08 G6 |
| 常驻块数上限 | `rgbd_max_blocks_in_memory` = 64 / 256 / 1024（快 / 标 / 高），**运行时按 §1.3 档位上限下调** |
| 块内存 | `block_size³ × 16 B`（64³ → 4.19 MB；128³ → 33.6 MB） |
| 边界处理 | 相邻块**重叠 1 层体素**（halo）；重叠区按 TSDF 距离与权重做加权平均融合，不是简单覆盖 |
| 融合顺序 | 按块中心到相机光心的距离由近及远，保证近处（精度高）的观测在重叠区占优 |
| 块淘汰 | 相机离开块的视锥范围后，该块可被淘汰（前提：该块的 TSDF 已写回落盘或已完成全局优化） |
| 禁止 | ❌ 调整 `rgbd_tsdf_voxel_size`（黑名单） |

**重叠区融合公式**

```
TSDF_fused(p) = (Σ_i w_i · TSDF_i(p)) / (Σ_i w_i)
w_i = weight_i(p) · d_i          # d_i = 1 / (1 + (dist_i / truncation)²)
```

> `d_i` 的引入保证近景块的贡献不被远景块稀释，这是 00 §4.2 决策「LiDAR/TSDF 只做先验与补盲，不主导几何」在融合层面的落地。

#### 3.2.2 MVS 分块

| 项 | 规格 | 来源 |
|---|---|---|
| tile 尺寸 | `mvs_gpu_tile_size` = 1024 / 1024 / 512（快 / 标 / 高）；**运行时按 §2.4 处置顺序可降到 512 / 512 / 256** | 05 §5.9.2 / 08 G5 |
| 分派层次 | 帧级 → tile 级 → 迭代级（红黑交替 2 dispatch/轮）→ 细化级 → 融合级 | 05 §5.9.2 |
| tile 重叠 | workgroup 覆盖 8×8 + **5 px halo**（`shaders/common` 统一） | 05 §5.9.1 |
| 边界处理 | 相邻 tile 重叠区的深度用**加权中值**融合（权重 = 支撑视图数），不是直接覆盖；几何一致性过滤（05 §5.6）在 tile 边界**放宽 1 个栅格**以避免边界效应误删 |
| 源视图深度图 | 按 tile 分批重算（05 §5.9.3），代价 ×1.6 | — |
| 视图选择不变 | `mvs_num_views` 不因分块调整（黑名单） | — |

#### 3.2.3 泊松分块

完整方案见 06 §1.7 方案 A，此处给内存落地参数：

| 步 | 算法 | 参数 |
|---|---|---|
| A1 | 沿最长轴 1D 切分，块边长 `L_block`，块间重叠 `m` | `m = 4·r`；`mesh_chunk_overlap_leaves` = 4 叶（08 G7） |
| A2 | 每块独立算 `D_block = ceil(log2(s·L_block / r_target))`，使 `r` 与全局一致 | `D_block ≤ D`，**分辨率不降** |
| A3 | 逐块泊松求解，块结果落盘 | 落盘粒度 = 1 块 |
| A4 | 缝合：重叠带内 ICP 对齐（点到面，阈值 `0.2·r`）+ 合并顶点（容差 `0.05·r`） | — |
| A5 | 接缝带二次修复（重叠带重跑局部泊松，`D` 同全局） | — |

**`L_block` 的内存反推公式**

```
L_block = L_max / ceil( L_max / L_block_target )
其中 L_block_target 由下式反推：
  N_cells_block = SurfaceArea_block / r²
  N_cells_block × 220 B ≤ M_poisson_budget × 0.6        (06 §1.7 决策流程)
```

**决策流程（06 §1.7 原文口径，本文档按档位代入）**

```
读取 M_poisson_budget（§1.3 档位值）
估算 N_cells = SurfaceArea / r²
估算 peak    = N_cells × 220 B
if peak ≤ M_poisson_budget × 0.6:   单块泊松
elif L_max ≤ 0.35:                  提高 D（若 D+1 仍可行），单块泊松
else:                                分块泊松 + 落盘，D 不变
```

| 档位 | `M_poisson_budget × 0.6` | 单块可行的 `D` | 高精度档（D=11，峰值 2 458 MB）的实际执行 |
|---|---|---|---|
| T0 | 1 843 MB | 10（594 MB ✓） | 分块 **2 块**，每块 ≈ 1 229 MB ≤ 1 843 MB ✓ |
| T1 | 737 MB | 10（594 MB ✓） | 分块 **4 块**，每块 ≈ 614 MB ≤ 737 MB ✓ |
| T2 | 307 MB | 9（147 MB ✓） | 分块 **8 块**，每块 ≈ 307 MB ≤ 307 MB ✓（余量为零，块内仍需落盘） |
| T3 | 154 MB | 9（147 MB ✓，余量 7 MB） | 分块 **16 块**，每块 ≈ 154 MB ✓；因余量过小，**一律分块**（连标准档 D=9 也分块，块内同时落盘） |

> **块数取整规则**：`块数 = 2^ceil(log2(总峰值 / (M_poisson_budget × 0.6)))`，向上取到 2 的幂。这保证「块数翻倍时单块峰值减半」，使块内峰值严格不超过预算判据。**块数不影响 `D` 与 `r`**（06 §1.7 A2）。

> **诚实披露（06 §1.7 已写明，此处重申）**：分块泊松**不是全局一致解**，接缝处法向与曲率可能不连续。因此启用分块时必须在 `recon_mesh_info.json` 记录 `poisson_chunked: true` 与 `poisson_chunk_count`，且接缝带必须经过 06 §2.4 非流形修复 + §2.6 法向矫正复核。**分块是内存硬约束下的唯一合法路径，不是精度提升手段。**

#### 3.2.4 描述子与匹配分块

| 项 | 规格 | 来源 |
|---|---|---|
| 空间分块 | 关键帧按物体中心 `C` 的方位/俯仰分 **24 块**，块内 + 相邻块匹配 | 03 §5.3.5 / 05 §4.2.3 |
| 每块加载帧数 | T0 160 / T1 80 / T2 40 / T3 20（§1.4） | 本文档 |
| 跨块匹配 | 通过位姿图 + 闭环检测补充，**不删帧** | 05 §4.2.3 |
| 匹配图边数上限 | 16N 对；超出时按「角点数量 × 空间距离」排序截断（**只删边，不删帧**） | 05 §4.3.1 MM-4 |

### 3.3 落盘中间结果（Spill to Disk）

#### 3.3.1 触发条件

| 条件 | 判据 | 动作 |
|---|---|---|
| **S-1 水位触发** | `M_rss / M_budget > perf_memory_high_water_ratio`（默认 0.85） | 启动 spill：把当前**可重建**的中间结果落盘 |
| **S-2 容量触发** | 某类缓冲的常驻量超过 §1.3 对应档位上限 | 该类缓冲立即转入落盘模式 |
| **S-3 告警触发** | iOS `didReceiveMemoryWarning` / Android `onTrimMemory(TRIM_MEMORY_RUNNING_LOW)` | 强制 spill + 收缩批大小（§3.5） |
| **S-4 显式触发** | 用户在参数面板开启 `perf_spill_enabled` | 常驻超过 `perf_memory_high_water_ratio × 0.7` 即 spill（提前量模式） |

#### 3.3.2 Spill 内容表

| 中间结果 | 落盘格式 | 路径 | 恢复方式 |
|---|---|---|---|
| TSDF 块 | `tsdf_blocks/block_%05d.bin`（头部 64 B 元数据 + 体素数组） | `<cache>/tsdf_blocks/` | 按块索引顺序读回并重新融合 |
| 描述子块 | `desc_blocks/block_%05d.bin`（帧 id 列表 + rootSIFT 数组） | `<cache>/desc_blocks/` | 按块加载 |
| MVS 深度图 | `mvs_depth/ref_%05d.f32`（含置信度与支撑视图数） | `<cache>/mvs_depth/` | 参考帧为单位读回 |
| 泊松块结果 | 06 §1.7 A3 的自定义二进制 | `<cache>/poisson_chunks/` | 按块缝合 |
| UV 图集中间图 | `uv/chart_%05d.png` | `<cache>/uv/` | 按 chart 读回合成 |
| 烘焙中间图 | `bake/chart_%05d.png` | `<cache>/bake/` | 同上 |
| BA 滑窗解 | `ba/window_%05d.bin`（位姿增量 + 协方差对角） | `<cache>/ba/` | 增量应用 |

#### 3.3.3 路径与命名

```
<app_sandbox>/cache/recon/<session_id>/
├── cache_manifest.json          # 记录每一项的路径、字节数、sha256、生成阶段
├── tsdf_blocks/
├── desc_blocks/
├── mvs_depth/
├── poisson_chunks/
├── uv/
├── bake/
└── ba/
```

| 项 | 规格 |
|---|---|
| 根目录 | `perf_cache_dir` 参数（08 G11，默认空 → 平台默认沙盒缓存目录） |
| 配额 | `perf_cache_max_mb`（默认 2 048 / 快 1 024 / 标 2 048 / 高 4 096）；超配额时按 **LRU 淘汰已消费的块**（不是关键帧原始数据） |
| 生命周期 | 会话取消或导出完成后**递归删除**（11 §4.5 释放清单） |
| 原子写 | 先写 `*.tmp` 再 `rename()`，避免崩溃产生半截文件 |
| 校验 | `cache_manifest.json` 中每项记 `sha256`；读回时校验，不匹配则重算该项 |

> **注意**：spill 目录与 02 §5.1 的 `sessions/<id>/` 是**两个不同目录**。`sessions/<id>/` 是**用户数据**（原始帧 + 关键帧，导出后可能保留供用户复看）；`cache/recon/<id>/` 是**可重建的中间量**（随时可删）。**用户数据不因内存压力被删除**。

#### 3.3.4 恢复逻辑

```
重建启动
  ├─ 读 cache_manifest.json
  │    ├─ 不存在 → 从头重建
  │    └─ 存在 → 逐项校验 sha256
  │         ├─ 校验通过 → 复用（跳过该阶段的计算）
  │         └─ 校验失败 → 删除该项，从头重算该阶段
  ├─ 校验失败项不阻断整体重建（降级为「重新计算」），但记 W_CACHE_ITEM_INVALID
  └─ 中断后恢复：从 cache_manifest.json 记录的最后完整阶段继续
```

| 约束 | 内容 |
|---|---|
| SP-1 | spill 是**性能优化**，不是正确性依赖。删除整个 cache 目录后重建必须得到**相同结果**（确定性要求见 §3.3.5） |
| SP-2 | spill 不得改变任何精度参数。若某项中间结果无法在不降精度的前提下复用（如泊松块缺少必要的邻域数据），则**不 spill 该项**，而是缩小块尺寸（白名单） |
| SP-3 | 恢复时必须校验 `manifest.json.sha256_of(index.bin)`（02 §5.3.3），不匹配则拒绝续算 |

#### 3.3.5 确定性要求（spill 的前提）

| 项 | 要求 |
|---|---|
| 块划分确定性 | 同一输入 + 同一参数 → 同一块划分（块的切分只依赖几何量，不依赖线程调度） |
| 融合顺序确定性 | 块融合按固定顺序（块索引升序），不依赖完成顺序 |
| 线程无关性 | 同一阶段的多线程计算结果必须与顺序执行**逐位一致**（对浮点累加敏感的实现必须用固定顺序归约） |
| 验证 | 14 文档 §6.2 的「关掉 spill vs 开启 spill，导出结果逐字节相同」作为回归项 |

> 若某算法无法满足逐位一致（例如 GPU 原子累加的顺序不确定），则该阶段的 spill 恢复只能保证**统计等价**，需在 `recon_mesh_info.json` 记录 `spill_equivalence: "statistical"`，并在 14 文档的容差中放宽该项。

### 3.4 内存水位监控

#### 3.4.1 采样

| 项 | 规格 |
|---|---|
| 采样周期 | **500 ms**（采集期与空闲期）/ **200 ms**（重建期，任一大块分配发生） |
| iOS 采样源 | `task_info` → `phys_footprint`（**不是** `resident_size`；前者是系统计费的真实占用） |
| iOS 可用内存 | `os_proc_available_memory()` |
| Android 采样源 | `Debug.getMemoryInfo()` → `getNativeHeapAllocatedSize()` + `getNativeHeapSize()`；进程 RSS 取 `/proc/self/status` 的 `VmRSS` |
| Android 可用内存 | `ActivityManager.getMemoryInfo()` → `availMem` |
| 跨进程一致性 | 同一进程内用同一 API 采样，不混用不同口径 |
| 上报 | 采样值写入 `recon_profile.json` 的 `memory.timeline[]`（每条：时间戳、RSS、峰值 RSS、可用内存、当前阶段、当前并发度） |

#### 3.4.2 阈值与响应（分级）

| 水位 `w = M_rss / M_budget` | 级别 | 响应 |
|---|---|---|
| `w < 0.60` | 正常 | 无 |
| `0.60 ≤ w < 0.75` | 预警 | ① 记录时间戳；② 预取策略收敛（读盘预读窗口减半）；③ 不改变并发度 |
| `0.75 ≤ w < 0.85` | 降并行 | ① `perf_max_concurrent_tasks` × 0.75；② `perf_gpu_batch_size` × 0.75；③ `perf_block_batch_size` × 0.75；④ 启动 spill（S-1） |
| `0.85 ≤ w < 0.92` | 强降 | ① 上述再 × 0.75；② `perf_memory_pool_prealloc_mb` × 0.5；③ `rgbd_max_blocks_in_memory` × 0.5；④ `perf_thread_pool_size` × 0.75（最低 1）；⑤ 强制 spill |
| `w ≥ 0.92` | 紧急 | ① 全部批大小 × 0.5（最低 1）；② 暂停**非关键**阶段（只保留当前阶段做完）；③ 释放 `perf_cache_dir` 的非活跃部分；④ 记录 `RECON_ERR_MEMORY_PRESSURE` |
| `w ≥ 1.00` | 溢出 | 主动抛出 `RECON_ERR_OUT_OF_MEMORY`（由 C ABI 返回错误码，不崩溃）；已落盘数据保留；UI 提示「内存不足，请关闭其他应用后重试」 |

> **所有响应动作全部落在 `perf_*` 与 `rgbd_max_blocks_in_memory`（08 G11 白名单）**。没有任何一项触碰精度参数。这是 00 R-PREC-4 的直接落实，11 §7.2 第 15 项的运行时断言测试会逐条校验这一点。

#### 3.4.3 迟滞（防止抖动）

| 机制 | 参数 |
|---|---|
| 升级立即 | 水位上升越过阈值 → 立即响应 |
| 降级迟滞 | 水位下降到 `阈值 − 0.08` 且持续 **60 s** 才恢复一级（与 11 TH-2 的温度迟滞一致） |
| 恢复上限 | 每 60 s 最多恢复一级（防止在阈值附近来回震荡） |
| 恢复记录 | 每次恢复写入 `recon_profile.json` |

### 3.5 平台内存告警回调

**与 11 §5.3 的一致实现（本文档给出具体参数与顺序）**

| 平台 | 回调 | 本文档的响应 |
|---|---|---|
| iOS | `UIApplication.didReceiveMemoryWarningNotification` | ① 释放帧环形队列中未处理的帧（**只释放未入关键帧的帧**，不触碰已入库关键帧的落盘数据）；② 释放 `perf_cache_dir` 的非活跃部分；③ `rgbd_max_blocks_in_memory` × 0.5；④ `perf_memory_pool_prealloc_mb` × 0.5；⑤ `perf_gpu_batch_size` × 0.5 |
| iOS | scene 级别的 `didReceiveMemoryWarning` | 同上 |
| Android | `Activity.onTrimMemory(TRIM_MEMORY_RUNNING_LOW)` | 同 iOS 的 ①–⑤ |
| Android | `onTrimMemory(TRIM_MEMORY_RUNNING_CRITICAL)` | 上述 + `perf_max_concurrent_tasks` × 0.5（最低 1）+ `perf_thread_pool_size` × 0.5（最低 1） |
| Android | `onTrimMemory(TRIM_MEMORY_COMPLETE)` | 写检查点后释放全部非必要缓存；当前阶段做完即暂停 |
| Android | `ActivityManager.getMemoryInfo().lowMemory == true` | 等同 `TRIM_MEMORY_RUNNING_LOW` |

| 约束 | 内容 |
|---|---|
| M-1 | 内存保护**禁止**通过丢弃已入库的关键帧或降低精度阈值实现（00 R-PREC-5） |
| M-2 | 每次内存保护在 U-06 显示 `内存紧张，缓存已写入磁盘`（09 §3.6.2） |
| M-3 | 内存保护动作全部落在 `perf_*`（白名单） |
| M-4 | 重建期间的所有大块内存（泊松八叉树、UV 图集、烘焙缓冲）必须**分块分配 + 落盘 + 流式**，不能在内存警告时「临时申请更多内存」 |
| M-5 | `didReceiveMemoryWarning` 可能**随时**到来。因此**不能**依赖它来触发 spill——必须由 §3.4 的水位监控主动预防 |

### 3.6 绝对禁止的内存优化手段清单

> **以下手段在本项目中一律禁止出现在任何自动路径（内存压力、温度、电量、后台、低存储等任何触发源）中。**
> 违反即为 P0 缺陷（14 §7）。

| # | 禁止的手段 | 触犯的铁律 | 为什么看起来诱人 | 为什么仍然禁止 |
|---|---|---|---|---|
| **F-1** | **丢弃关键帧**（只保留最近的 N 帧 / 只保留前 N 秒） | R-PREC-3；00 §1.2 黑名单「关键帧保留数量」 | 直接省最多内存（每帧 7.91 MiB） | 关键帧是精度的一阶来源。丢弃会以「优化不完全」的形式隐性降低精度，且用户无法察觉。**替代**：落盘 + 分块读回 |
| **F-2** | **提高 TSDF 体素边长**（`rgbd_tsdf_voxel_size` 2 mm → 4 mm） | R-PREC-4；00 §1.2 黑名单「TSDF 体素边长 / 分辨率」 | 内存按边长立方缩减（4× → 64×） | 体素边长直接决定几何分辨率（08 G6 高档 0.5 mm）。**替代**：块级 spill + 更小的 `rgbd_max_blocks_in_memory` |
| **F-3** | **降低 `mesh_poisson_depth`** / `mesh_poisson_scale` | R-PREC-4；00 §1.2 黑名单「泊松重建深度 / 缩放系数」 | 内存 ×4 / 层（06 §1.3） | 泊松深度是几何精度一阶因子；05 §6.1.3 显示 D=11 时泊松偏差占形状误差的 40%。**替代**：分块泊松（06 §1.7 A） |
| **F-4** | **减少特征点**（`sfm_feature_count` / `vio_feature_count`） | R-PREC-4；00 §1.2 黑名单「特征点提取数量上限」 | 描述子内存线性下降（05 §4.2.3） | 特征点数是弱纹理区匹配召回的直接决定项。**替代**：描述子分块（05 §4.2.3：每块 20/40/80/160 帧） |
| **F-5** | **减少 BA 迭代数**（`sfm_ba_max_iterations`） | R-PREC-4；00 §1.2 黑名单「BA 迭代次数 / LM 容差」 | BA 内存与耗时同时下降 | 迭代数不足表现为「位姿误差上升」，且不报错。**替代**：滑窗 BA 优先 + Schur 补分块 |
| **F-6** | **减少 RANSAC 迭代数** / 放宽内点阈值 | R-PREC-4；00 §1.2 黑名单 | 匹配阶段耗时下降 | RANSAC 迭代数不足 → 几何验证不充分 → 误匹配进入 BA。**替代**：分块匹配（限峰值而非限总量） |
| **F-7** | **深度图降采样 / 用平滑深度替代原始深度** | R-PREC-4；00 §1.2 黑名单「深度图降采样、深度图平滑替代原始深度」；00 §4.2 步骤 A 明文「保留原始深度副本，不做降采样」 | MVS 显存与点云量大幅下降 | 直接损失深度分辨率（`δZ ∝ Z²/(f·B)`）。**替代**：`mvs_gpu_tile_size` 减半 + 源视图深度图分批重算 |
| **F-8** | **降低 `mvs_image_scale` / `mvs_patch_size` / `mvs_num_views` / `mvs_patch_iterations`** | R-PREC-4（匹配阈值与视差精度属精度参数） | 显存与耗时同时大幅下降 | 直接降低曲面精度。**替代**：分块 + 并发度下调。**注意**：`mvs_image_scale` 在 08 §2.4 中端处置里被提到，但那是「用户在知情后选择降档 / 降分辨率」的路径，**不是自动路径** |
| **F-9** | **降低 `cap_resolution_width` / `cap_frame_rate`** 以省内存 | R-PREC-3；00 §4.5.3 M1 | 帧内存按面积/帧率线性下降 | 采集分辨率决定 MVS 深度精度上限。**替代**：背压让采集**变慢**（§3.1） |
| **F-10** | **静默降低 `post_uv_atlas_size` / `post_bake_texture_size`** | R-PREC-4（纹理质量属精度维度）+ R-PREC-6（无静默回退） | 图集内存按面积平方下降（8192² → 4096² 是 4×） | 属精度降级。**替代**：chart 级分批 + 中间图落盘（§3.3.2）。若用户主动要求降纹理分辨率，须走参数面板并记入 `recon_mesh_info.json` 的 `clamped_params` |
| **F-11** | **关闭 `mesh_poisson_confidence`**（省内存） | 06 §1.2（关闭会失去裁剪依据） | 省一份 confidence 数组 | 会失去 §1.6.2 外推区裁剪的依据 → 虚假面激增。**替代**：`mesh_poisson_prune`（剪空八叉树分支，纯内存优化，不改有效分辨率） |
| **F-12** | **关闭 `post_normal_area_weighted` / 简化法向计算** | 精度项 | 省法向计算 | 06 §2.6 法向一致性是拓扑验收项之一。**替代**：分批后处理 |
| **F-13** | **对已落盘的关键帧原始数据做「瘦身」（重采样 / 重压 / 删除 L2 层）** | R-PREC-3；02 §5.6.5 DS-1 | 省磁盘与读盘时间 | 已落盘关键帧是重建的唯一真值来源。**替代**：不删，只调整读盘批大小 |
| **F-14** | **把 `mesh_chunked_enabled` 关闭以「看起来精度更高」** | R-PREC-5 | 单块泊松无接缝 | 在内存不足时这是 OOM 路径。**规则**：分块与否由内存预算决定（06 §1.7 决策流程），**不得**为了「看起来更好」而关闭；用户主动要求单块泊松时，UI 必须先展示所需内存并要求确认 |

| W-9 | （本文档补充）**L5 并发任务数** | `perf_max_concurrent_tasks` | × 0.5，最低 1 | L2 / L3 |

**W-4 的严格限制**：图像金字塔层只允许在**首轮粗搜**中下降，且必须记录 `mvs_pyramid_offset` 到 `recon_mesh_info.json`。细化轮必须回到完整金字塔，否则细化结果本身就不一致。这是最容易被误用为「降精度」的一条，因此单列。

### 4.4 需要用户确认的「精度相关」降级

有三条路径会触及精度参数。按 00 R-PREC-6（覆盖后不发生静默回退）与 08 §2.4 P5，必须**由用户显式确认**，不得自动执行：

| 场景 | 涉及参数 | 处置 |
|---|---|---|
| T3 极低端 + 4K 输入，MVS 显存不足 | `mvs_image_scale` 0.75 | UI 弹出确认框，说明「降低图像分辨率会降低曲面精度」，用户确认后才生效；记录 `clamped_params` 与 `degradations` |
| 用户主动要求「在当前设备上跑高精度档」但内存不足 | `mesh_chunked_enabled`（不是精度参数，但影响结果一致性） | UI 说明「分块泊松接缝处精度略降」，用户确认；记录 `poisson_chunked: true` |
| 用户主动要求「降低纹理分辨率以节省内存」 | `post_uv_atlas_size` + `post_bake_texture_size` | **仅用户显式设置路径**；自动路径（§4.2）**不做**此动作。UI 提示「纹理分辨率降低」 |

**确认对话框文案（09 §3.6.2 / §5.5）**

| 场景 | 文案 |
|---|---|
| MVS 分辨率 | `当前设备内存不足。降低匹配图像分辨率可继续，但曲面精度会降低。是否继续？` |

### 4.5 降级不得静默

| 编号 | 要求 |
|---|---|
| D-1 | 每次降级必须写入 `recon_mesh_info.json` 的 `degradations` 数组，每项含 `stage`、`reason`、`detail` |
| D-2 | `reason` 取值必须是**受控枚举**：`memory_high_water`、`memory_warning`、`gpu_oom`、`thermal_throttle`、`thermal_critical`、`power_saver`、`low_battery`、`background_suspend`、`cache_spill`、`chunked_poisson`、`chunked_tsdf`、`chunked_mvs`、`user_confirmed_scale_down` |
| D-3 | 降级状态必须在 UI 状态文字中提示（09 §3.6.2 的五行文案），**不得**只写文件不提示 |
| D-4 | 降级提示必须说明「**精度不受影响**」或「**精度会下降**」二者之一，不得含糊。W-1..W-10 属前者（并发/批/分块不改精度阈值）；分块泊松属后者（接缝精度略降） |
| D-5 | `recon_mesh_info.json` 必须含 `degradation_summary`，给出 `max_level`（L1/L2/L3）、`duration_ms`、`precision_impact`（`none` / `seam_local` / `user_approved`） |
| D-6 | 每次降级的发生与恢复都必须进 `events.jsonl`（02 §5.8.1 的 `type` 取值新增 `degradation` / `degradation_recovered`） |

**`recon_mesh_info.json` 的降级片段（示例）**

```json
{
  "degradations": [
    { "stage": "S2_poisson", "reason": "chunked_poisson",
      "detail": "poisson_chunk_count=4, D=11, L_block=0.075m, r=0.161mm",
      "level": "L1", "precision_impact": "seam_local", "t_ms": 412300 },
    { "stage": "S9_bake", "reason": "memory_high_water",
      "detail": "rss=1840MB, budget=2200MB, ratio=0.836, action=batch_size x0.75",
      "level": "L1", "precision_impact": "none", "t_ms": 1289000 }
  ],
  "degradation_summary": {
    "max_level": "L1",
    "duration_ms": 1701300,
    "precision_impact": "seam_local",
    "blacklist_touched": []
  }

```

### 4.6 恢复策略

| 降级类型 | 自动恢复？ | 规则 |
|---|---|---|
| **W-1 线程池并发数** | ✅ 自动 | 水位下降到阈值 − 0.08 且持续 60 s → 恢复一级；每 60 s 最多恢复一级 |
| **W-2 GPU 批次大小** | ✅ 自动 | 同上 |
| **W-5 后处理分批粒度** | ✅ 自动 | 同上 |
| **W-6 内存池预分配** | ✅ 自动 | 同上 |
| **W-9 并发任务数** | ✅ 自动 | 同上 |
| **W-10 读盘预读窗口** | ✅ 自动 | 同上（且重建阶段结束后必然恢复） |
| **W-3 MVS tile 尺寸** | ⚠️ **半自动** | 在**当前阶段内**不恢复（已完成的 tile 结果组织方式已定）；**阶段结束后**自动恢复到档位默认值 |
| **W-3b TSDF 块尺寸** | ⚠️ 半自动 | 同上（阶段结束即恢复） |
| **W-8 TSDF 常驻块数** | ✅ 自动 | 同 W-1 |
| **W-3c / W-7 泊松分块** | ❌ **不自动恢复** | 分块数由 06 §1.7 决策流程在**网格化阶段开始前**一次性判定。阶段内不恢复。跨阶段不恢复（下一个阶段用的是别的内存模型） |
| **S-1 spill** | ❌ 不自动「恢复」 | spill 的产物在重建结束后删除。下次重建从头算（保证确定性，见 §3.3.5） |
| **用户确认的精度降级**（§4.4） | ❌ 不自动恢复 | 需用户在参数面板显式改回；改回后需重跑对应阶段 |

**恢复的通用规则**

| 编号 | 规则 |
|---|---|
| R-1 | 恢复必须**逐级**、**每 60 s 至多一级**，禁止一次性跳回原值（防止抖动） |
| R-2 | 恢复动作同样必须写入 `degradations`（`reason` 追加 `_recovered` 后缀）与 `events.jsonl` |
| R-3 | 恢复**不得**触碰任何精度参数（因为恢复只涉及白名单） |
| R-4 | 若在降级期间用户修改了某个 `perf_*` 参数，则以**用户的新值**为恢复目标的上限（用户意图优先于自动策略） |
| R-5 | 重建阶段结束后，所有 `perf_*` 参数**不自动复位**（保持用户可见的当前生效值），但 `recon_mesh_info.json` 记录 `params_effective`（08 §4.4），使下次重建从当前值开始 |

## 5. 温度与电量

### 5.1 温度

| 平台 | API | 档位 |
|---|---|---|
| iOS | `ProcessInfo.processInfo.thermalState` | `.nominal` / `.fair` / `.serious` / `.critical` |
| iOS | 用户阈值 `cap_thermal_throttle_threshold_c`（08 G1，默认 45/42/40 快/标/高） | °C |
| Android | `PowerManager.getCurrentThermalStatus()`（API 29+） | `NONE` / `LIGHT` / `MODERATE` / `SEVERE` / `CRITICAL` / `EMERGENCY` / `SHUTDOWN` |
| Android | `PowerManager.getThermalHeadroom()`（API 30+） | 1.0 ~ ∞ 的预测值 |

**阈值与响应（承接 11 §5.2，只降并发度）**

| 触发 | 响应（全部在白名单内） | 精度 | 用户提示（09 §3.6.2） |
|---|---|---|---|
| iOS `.nominal` / Android `NONE` | 无 | — | — |
| iOS `.fair` / Android `LIGHT` | `perf_thread_pool_size` × 0.75 | 不变 | 不提示（避免打扰） |
| iOS `.serious` / Android `SEVERE` / headroom ≥ 1.0 | `perf_thread_pool_size` × 0.5、`perf_gpu_batch_size` × 0.5、`perf_max_concurrent_tasks` × 0.5、`rgbd_max_blocks_in_memory` × 0.5 | 不变 | `设备温度较高，已降低重建速度` |
| iOS `.critical` / Android `CRITICAL` | 上述 × 0.25；**暂停采集**（`Capturing` → `Previewing`，已采帧保留） | 不变 | `设备温度过高，已暂停采集` |
| Android headroom ≥ 2.0 | 视同 `SEVERE` | 不变 | 同上 |
| 用户阈值命中 | 与系统 API **取更严格者** | 不变 | 同上 |
| 电池温度高但 SoC 温度正常（如充电中） | **以系统 API 为准**（SoC 温度才是算力瓶颈） | — | — |

| 编号 | 规则 |
|---|---|
| TH-1 | 温度降级只改 `perf_*` 与 `rgbd_max_blocks_in_memory`。**绝不**改 `rgbd_tsdf_voxel_size`、`mesh_poisson_depth`、`sfm_feature_count`、`vio_feature_count`、`sfm_ba_max_iterations`、`sfm_ransac_max_iterations`、`mvs_patch_size`、`mvs_num_views`、`mvs_image_scale` |
| TH-2 | 温度降级是**临时的**：温度回落后自动恢复并发度（**60 s 迟滞**，与 §4.6 R-1 一致） |
| TH-3 | 每次温度降级写入 `recon_mesh_info.json` 的 `degradations`（`reason = "thermal_throttle"` / `"thermal_critical"`）并在 U-06 显示提示行 |
| TH-4 | `cap_thermal_throttle_threshold_c` 只影响本产品自己的阈值；系统温度 API 的阈值不可调，作为附加约束叠加 |
| TH-5 | 采集期温度降级：**只降 `cap_frame_rate` 的上限**（不是分辨率），且该动作由用户在参数面板的「采集帧率上限」显式设置区间决定，**不由温度自动改写**。系统级「降低采集帧率」由相机 HAL 的热保护自动完成，属平台行为，不在本产品的参数层面 |

### 5.2 电量

| 触发 | 响应 | 精度 | 用户提示 |
|---|---|---|---|
| iOS `isLowPowerModeEnabled` / Android `isPowerSaveMode()` | `perf_gpu_batch_size` × 0.75、`perf_max_concurrent_tasks` × 0.75。**不关闭 GPU** | 不变 | `已启用省电模式，重建速度降低` |
| 电量 < 15% 且未插电 | 采集阶段提示一次 | 不变 | `电量较低，建议插电后再进行高精度重建` |
| 电量 < 15% 且未插电 + 高精度档 | **建议降档（用户确认）**，不自动降档 | 不变 | `高精度重建耗电量较大，建议插电使用` |
| 电量 < 8% 且未插电（任意档） | 采集阶段提示 + 重建阶段 `perf_max_concurrent_tasks` × 0.5 | 不变 | `电量很低，重建速度已降低` |

> **为什么省电模式不关 GPU**：关掉 GPU 会让泊松慢约 10 倍（05 §5.9.4 的 CPU 回退耗时 40–90 min vs GPU 的 60–150 s），**反而延长发热时间与总耗电**。这是 11 §5.2 已定的策略，本文重申。

### 5.3 温度/电量与内存的联合优先级

多个触发源同时命中时，按下表取**最严**的一档执行，不叠加（避免过度降级导致无法完成重建）：

| 优先级 | 触发源 | 理由 |
|---|---|---|
| 1（最高） | 内存紧急（L3，`w ≥ 0.92`） | 内存不足会直接 OOM，进程被杀则全部工作丢失 |
| 2 | 平台内存告警（`didReceiveMemoryWarning` / `onTrimMemory(CRITICAL)`） | 同上 |
| 3 | 温度 `.critical` / `CRITICAL` | 持续高温会触发系统杀进程（iOS thermal shutdown） |
| 4 | 内存强降（L2） | — |
| 5 | 温度 `.serious` / `SEVERE` | — |
| 6 | 内存降并行（L1） | — |
| 7 | 省电模式 / 低电量 | 只影响速度 |
| 8（最低） | 温度 `.fair` / `LIGHT` | 几乎不影响 |

**不叠加的实现方式**：降级器维护一个**单一**的 `effective_level ∈ {L0, L1, L2, L3}` 与 `effective_trigger` 字段。每次触发时重算「应达到的级别」，取最严的，然后从**基线值**（档位默认值）一次性算出目标参数值，而不是在当前值上再乘系数。这样避免多次触发导致过度降级。

## 6. 长时间运行的稳定性

### 6.1 连续采集的内存增长检测

#### 6.1.1 泄漏检测方法（四层）

| 层 | 方法 | 覆盖 | 何时跑 |
|---|---|---|---|
| **L1 静态**：ASan + LeakSanitizer | `RECON_ENABLE_ASAN=ON` 构建，`LSAN_OPTIONS=detect_leaks=1` | 堆分配泄漏、UAF、越界 | 每日 CI（12 §6.4） |
| **L2 静态**：Valgrind massif | `--tool=massif --massif-out-file=massif.out` | 堆增长曲线（不只泄漏，还有**累积增长**） | 每日 CI，桌面 Linux runner |
| **L3 动态**：RSS 曲线 + 线性回归 | 采集期与重建期按 §3.4.1 采样 `phys_footprint` / `VmRSS`，对**稳态段**做线性回归 | 运行期累积增长（缓存未释放、容器未回收） | 每次 PR 的采集模拟 + 实机长跑 |
| **L4 动态**：稳态重复性 | 同一会话重复「采集 → 重建 → 导出」3 次，比较第 2、3 次的峰值 RSS | 资源未释放 / 句柄泄漏 | 每次 PR |

#### 6.1.2 判据

| 指标 | 判据 | 失败级别 |
|---|---|---|
| 稳态段 RSS 斜率 | 采集期（帧号 > 200 后到结束）与重建期各拟合一次；**斜率 ≤ 1.0 MB / 100 帧**（采集）与 **≤ 1.0 MB / 分钟**（重建） | P1；> 5 MB/100 帧 → P0 |
| 峰值 RSS 重复性 | 第 2、3 次重建的峰值 RSS 相对第 1 次的偏差 ≤ **+5%** | P1；> +20% → P0 |
| ASan/LSan | 0 泄漏报告 | **P0** |
| Valgrind massif | 重建结束时的堆大小 ≤ 峰值堆的 **1.05 倍**，且终止态与初始态差 ≤ 32 MB | P1 |
| 句柄数（见 §6.2） | 重建结束后句柄数 ≤ 重建开始时 + 5 | P1 |
| GPU 资源 | 重建结束后 Metal/Vulkan 分配计数回到进入重建时的水平（± 2%） | P1；泄漏持续增长 → P0 |

#### 6.1.3 长跑测试规程

| 项 | 规格 |
|---|---|
| 采集长跑 | 连续采集 **30 分钟**（自由环绕模式，60 fps，1080p），全程不退出；记录 RSS 曲线 |
| 重建长跑 | 同一会话重建，**不中断**，直到导出完成；记录 RSS 曲线 |
| 重复次数 | 同一天 3 次独立会话（验证 §6.1.2 L4） |
| 设备矩阵 | iOS：iPhone 15 Pro（8 GB，T0）、iPhone 12（4 GB，T1）、iPhone SE 2（3 GB，T3）、iPhone 8（2 GB，T3）；Android：Pixel 8（8 GB，T0）、Galaxy A54（6 GB，T1）、4 GB 低端机（T2）、3 GB 低端机（T3） |
| 通过判据 | 全部设备全部机型满足 §6.1.2 |
| 频次 | 每次 release 前必跑；每日 CI 跑桌面模拟版 |

### 6.3 长时间运行的其它稳定性要求

| 项 | 要求 |
|---|---|
| 时间戳漂移 | 02 §3.8 / 08 `sync_max_drift_ppm`（默认 200 ppm）。30 分钟采集若漂移超限 → 中止并提示（02 §3.8） |
| 句柄上限 | iOS `proc_pidinfo` 的 `pti_numopenfiles`；Android `/proc/self/fd` 计数。采集期增长必须为线性且斜率 < 1 文件/分钟 |
| 磁盘增长 | 采集期磁盘写入速率应与 02 §5.6.2 的理论值一致（1080p+ToF = 115 MiB/s）。实测偏差 > 50% → 说明有重复写入，需排查 |
| 线程数 | 采集 + 重建期间总线程数 ≤ `perf_thread_pool_size` + 平台线程（相机/IMU/GPU 驱动）+ 8。超过说明线程池未复用 |
| watchdog | 重建阶段每阶段有超时上限（见下表），超时 → 抛错误码，不无限挂起 |

**阶段超时上限（保守默认值，需实测标定）**

| 阶段 | 超时上限 | 超时行为 |
|---|---|---|
| 特征匹配 | 30 min / 300 关键帧 | `RECON_ERR_STAGE_TIMEOUT` |
| 全局 BA | 60 min | 同上（保留上一阶段解并告警） |
| MVS（单参考帧） | 15 min | 同上（跳过该参考帧并记 `E_MVS_INSUFFICIENT_VIEWS`） |
| 泊松（单块） | 20 min | 同上 |
| UV 展开 | 5 min | 走球面/平面投影回退（06 §2.8 已规定） |
| 纹理烘焙 | 20 min | 用顶点色回填并记 `W_MESH_TEX_PARTIAL` |
| 导出 | 10 min | 抛错误码，保留已写出的部分并标注 |

> 超时上限的触发**不涉及精度降级**：超时是错误处置，不是「降精度继续跑」。
